Gappler Test Bench

The test bench is a set of automatic checks for the robot's software. It never moves the robot. It tells us which parts of the software work, which are broken, and which haven't been tested yet.

How the checks work

The checks come in six levels, from quick paperwork checks to a real run. Each level only makes sense once the one before it passes. The comparison to building a machine is only a rough guide.

LevelWhat it asksLike checking a machineWhere
Tier 0Names match Do the programs still agree on the names they use to talk to each other? Part numbers match across all the drawingsAny computer, seconds
Tier 1Code checks Is each file readable, and does everything it points to exist? Each drawing is complete and references real partsAny computer, seconds
PreflightLab computer ready Does the lab computer have the graphics card, software, model files and network setup it needs? The workshop has the tools and materialsLab computer, looks only
Tier 2Build Does the code turn into working programs? The parts can be madeLab computer
Tier 3Fake inputs Does one program do the right thing when we feed it made-up sensor data? One subassembly on a test rigLab computer, sealed off from the robot
Tier 4Real data Record real camera and LiDAR data once, then replay it in every later test. A supervised trial runLab computer, person at the robot

How the simulated arm works

The bench tests the arm's software on a computer model of the arm. The real programs run, but the motors are fake, so nothing physical moves.

What runs

PieceReal or stand-inWhat it does in the test
Arm modelStand-in The RM65 and gripper's shape and joints, from the robot's own description file. The motors are replaced by "fake hardware": each joint accepts a position command and reports it has arrived. There is no physics, so no weight, no gravity and no contact with objects.
MoveItReal The motion planner, with the robot's own settings. It works out a path for the arm that avoids the table and the safety walls, then sends it to the fake motors.
Grasp controllerReal The program that decides what the arm does next (grasp_state_machine). Unchanged. It asks MoveIt for every move.
Camera, object finder, gripperStand-in The test script plays these. It sends the camera's settings and the "object is here" messages that SAM 3 would send, and records the gripper commands instead of acting on them.

Two tests use it

TestWhat it testsQuestion it answers
sim_moveit.shMoveIt on its ownCan the planner move the arm to the two home positions and to zero without hitting anything?
state_machine_sim.shThe grasp controller, with MoveIt underneathDoes the controller go through the right steps, in the right order, for one grasp?

One simulated grasp, step by step

This is what happened in the 11 Sep run of state_machine_sim.sh. "Test" is the bench script, "controller" is the grasp controller.

  1. Controller starts. It adds invisible safety walls and the table to MoveIt's picture of the world.
  2. Arm goes home. The controller asks MoveIt to move to the home position. The fake motors report the arm arrived, 0.0001 rad off. The controller announces IDLE, meaning "waiting for an object". On the real robot this happens within seconds of starting, without being asked (B4).
  3. Test: "object straight ahead, 0.30 m away". This is the message SAM 3 would send from the wrist camera.
  4. Controller approaches. It homes again, switches to SELECTING, and asks MoveIt for a 4 cm step toward the object. The simulated arm moves.
  5. Test: "object now 0.15 m away". That's closer than 0.18 m, so the controller switches to EXECUTING.
  6. Gripper opens. The controller sends "open" (position 1000). The test records it.
  7. Final move, gripper closes. The arm moves 10 cm toward the object, then the controller sends "close" (speed 200, force 150).
  8. Arm carries the object. MoveIt moves the arm to the carry position. The controller announces "grasp done, take me back to the user".
  9. Expected: back to IDLE for the next object. Actual: stuck in EXECUTING. This is bug C7, and why it handles one object per start-up.

What the simulation can't tell us

Whether the real arm, gripper and camera behave the same. Whether the gripper actually holds the object, because there is no contact. And nothing about AnyGrasp: today the controller skips its grip suggestions and simply moves straight toward the object's centre.

Words used here

Only the software terms this page can't avoid.

ROS
The software framework the robot's programs use to send messages to each other. Each program does one job, such as reading the camera or planning an arm move.
Channel (topic)
A named line that programs send messages on. For example, /goal_pose carries "drive here" commands to the base. If one program renames a channel and the others don't, nothing arrives and nothing reports an error.
Sealed-off channel
The tests run on their own ROS network number, so their messages can't reach the real arm or base.
Simulated arm
A computer model of the RM65 arm with fake motors. The real software moves the model instead of the real arm. See "How the simulated arm works" above.
Coordinate frame
The point a position is measured from, such as the map, the base or the arm. Mixing up frames sends the robot to the wrong place.
Nav2
The navigation software that drives the base to a target. The navigation tests use a fake Nav2 that only notes the target and never drives.
MoveIt
The software that plans the arm's path to a target without hitting anything.
AnyGrasp
The program that looks at a camera image and picks where to grip the object.
LiDAR
The spinning laser sensor on the base that measures distances. It's used to build the map and find the robot on it.
Build
Turning source code into programs the computer can run, like making parts from drawings.

Running the bench

For whoever runs the checks. Connect to the lab computer from anywhere with:

ssh -o HostKeyAlias=10.91.242.76 rcp2026@100.87.133.60

Work only in the ~/rcp-Gappler folder. The folders rcp-desktop, rcp-github and rcp-old-ros-wkspace are old copies. Read them, but never change them.

Safety. Every test that starts a robot program runs on a sealed-off channel. It refuses to start if anything else is already on that channel. None of the tests talk to the real arm or base.
