2. What the failure means

[code + observed] Round B received 2,941 cloud messages: 1,471 default-empty LIO heartbeats (excluded by the existing rule), 419 typed-empty VIO clouds, and 1,051 nonempty clouds with 141,401 finite XYZ points in total. The 419 have width 0, height 1, point_step 32, zero data bytes and fields x/y/z/rgb. They remain invalid under the existing contract; they have not been reclassified as harmless.

[code] publish_frame_world builds coloured clouds only from points projecting into the camera image. Its VIO path converts a typed PCL cloud even when that cloud is empty. Its LIO path in LIVO mode publishes a default message instead. These two source paths explain the different message layouts, but do not prove why so many VIO clouds are empty.

[observed] The visual module created map points but every logged retrieval returned zero. [code] computeJacobianAndUpdateEKF returns immediately when total_points == 0. Thus image publication is not evidence of camera-derived pose corrections. Removing the cloud failure alone would still leave the positive-retrieval requirement unmet.

[code] LIVO synchronisation cuts LiDAR data around camera timestamps and alternates LIO/VIO processing. Our 30 Hz images versus the public bag's approximately 10 Hz images explain different processing cadence; larger counts alone do not establish a defect.

Working control: the earlier public-bag PASS 20261016T175305Z-433728 used the same image ID and recorded 663 positive retrievals, 663 nonempty clouds with 9,182,028 points and zero invalid outputs. Different scene, calibration and sensor configuration mean this is a control, not a one-variable causal experiment.
