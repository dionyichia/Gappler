Run `t59-replay-20261019T080101Z-12426`, image
`sha256:ac276ad768d6ca1907b7b407789574a38f9aebe66216f466d656eb301d546183`, public bag
`Bright_Screen_Wall_raw`, `bright_screen_wall.yaml` + `camera_pinhole.yaml`, rate 0.25,

regression by anything in this record; the failure condition is a single undelivered message at the
end of the bag. Both statements are supported below and neither is used to excuse the other.

## 1. What failed

Two harness errors, one root cause:

```
callback drain timed out; terminal callbacks/log inactivity not established
input callback coverage /left_camera/image: missing=1 unexpected=0
```

`replay_progress.CallbackTracker.tails_seen()` requires, for every subscribed input topic, that the
**last expected stamp** has been observed. The mapper received 667 of the bag's 668
`/left_camera/image` messages, missing the final one at expected stamp `1661405918.291177`. That
message is the **last message in the recording**: its stored time `1661405918.202350` is exactly the
bag metadata end (`1661405918.2023504`), and its header is `1661405918.1911774`. The expected stamp
is `header + 0.1 s`, the configured `time_offset.img_time_offset: 0.1` which the pinned mapper adds
before it logs; the +0.0888 s "past the bag end" that this record first quoted is therefore the
harness's own image offset minus 0.0112 s of record-versus-header latency, **not** a message from
outside the recording. See §7 for the full audit. `tails_seen()` therefore
stayed false, and `drain_state()` returned `waiting` until its hard 120 s deadline, then `timeout`.
The estimator itself was idle for that whole window: callback counts and file sizes were flat from
wall 270.7 s to 380.9 s. Elapsed 388.3 s = the control's ~277 s + the 120 s drain, i.e. the timeout
is the entire time difference.

### 7.2 What was compared against the control's own terminal behaviour

- **Delivery of the terminal message:** control 668/668 received at `1661405918.291177`; this run
  667/668, the missing stamp being exactly the terminal one. In the control the terminal camera
  callback was already present when the drain began (camera 646 at wall 263.0 s, 668 by drain start
  273.1 s) — it arrived during normal playback, not during the drain.
- **Whether the loss is publisher- or subscriber-side:** the pinned mapper subscribes with
  `create_subscription<sensor_msgs::msg::Image>(img_topic, 200000, …)` — depth 200,000, RELIABLE
  (LIVMapper.cpp:310). A one-message subscriber-side drop with that queue depth is implausible, and
  the harness has no second input subscription to cross-check with: the drain's `callback_counts`
  and the coverage rows both come from `tracker.observed`, i.e. from the mapper's own log. The
  leading mechanism is therefore the publisher end — `rosbag2_player` reaching EOF and exiting with
  its final sample unacknowledged. **This is the leading mechanism, not a proven one**; the retained
  evidence cannot separate it from a transport loss at the same instant.
- **Shutdown behaviour:** identical in both runs. Same two pre-existing `imu loop back` ERROR lines
  (offsets 0.000505 and 0.000405), mapper exit 0 with the final line
  `signal_handler(SIGINT/SIGTERM)`, `camera` node exit 0, `player` exit 0 having exited by itself
  (`cleanup_requested: false` in both). Only the *trigger* differs: the control was torn down after
  5 quiet seconds (wall ≈ 278 s), this run after the 120 s drain deadline (wall ≈ 390 s). No teardown
  difference, no crash, no OOM.
- **The RGB count, attributed:** the pinned mapper publishes `/rgb_img` unconditionally once per
  LIO/VIO iteration (`publish_img_rgb`, LIVMapper.cpp:1342, called at line 508 right after
  `publish_frame_world`), and `[T35_DIAG_CLOUD]`, printed inside that same call path, is 664 in both
  runs. Mapper-side publication count is therefore equal; the monitor's 401 against the control's 606
  sits on a BEST_EFFORT monitor subscription, and its deficit is already 18 by the first printed
  snapshot (wall 10.7 s: monitor rgb 3 against cloud 21) and grows monotonically to 261. That is a
  monitor-side observation loss, not an estimator-side difference. Independent of the drain timeout,
  the criterion as written ("665 odometry / 664 cloud / 606 RGB, zero invalid") is not met by count,
  although its validity clause is (`invalid = 0` on all three streams).

## 8. Outcome of the audit

Both conditions the operator attached to treating this as a harness-tolerance issue fail: no
pre-declared tolerance covers the terminal message (§7), and a written criterion — `668/668 images` —
is unmet (§1, §7.1). **The verdict stands as FAIL.** Accordingly: no replay is staged, stationary02 A
and B stay unstarted, and nothing has been tuned — no QoS edit, no tolerance change, no replay-input
change, no acceptance relaxation, no image retag.

Open for the investigation, and requiring a decision before either happens:

1. Whether the publisher-end loss reproduces at all — observable only by running the same bytes
   again, which is not authorised.
2. Whether the harness should distinguish "terminal input message lost at playback EOF" from other
   failures, and surface it as its own condition rather than as a coverage gap plus a 120 s timeout.
   That is a harness change: it would alter `replay.py`/`replay_progress.py` bytes and require a
   re-frozen harness plus the operator's authorisation.

### 11.1 Why the terminal message cannot change any result

In every run, including the four passes, the terminal camera message postdates the final LiDAR
callback: last LiDAR `1661405918.099318`, terminal camera `1661405918.291177` — **0.192 s later**.

## 12. Harness fix: one bounded terminal-message allowance (declared before the re-run)

Authorised by Sherman ("fix the harnass"). The change touches `replay_progress.py` and `replay.py`
only; no config, QoS, tolerance, rate, bag or image byte changed.

### 12.1 The rule

A run may record `terminal_message_lost` and still pass coverage only when **all** of these hold:

1. The LiDAR topic has `missing = 0` and `unexpected = 0` — the scan stream is complete.
2. Exactly one other input topic has a gap, and that gap is exactly **one** message.
3. The missing stamp is that topic's own last expected stamp — the bag's final message for it.
4. That stamp is **strictly later** than the last observed LiDAR callback.
5. Every other input topic has `missing = 0` and `unexpected = 0` (the IMU prestart allowance is
   applied first, unchanged).
6. No unexpected duplicates on any topic.

Everything else still fails: an earlier stamp, two missing messages, a lost LiDAR frame, any
duplicate, a gap on a second topic, or a terminal stamp at or before the last scan time.

### 12.2 Why it is bounded, and why it is recording rather than relaxing

The accepted stamp is inert by construction: it postdates the last LiDAR callback, and VIO runs per
scan, so no frame can consume it — which is exactly what the four runs show (663 retrievals and 664
coloured rows whether it arrives or not). It is recorded, not hidden: the coverage row still reports
`missing = 1`, and `result.json` gains
`terminal_message_lost = {topic, stamp, seconds_after_last_lidar}` plus `input_lidar_topic`. The drain
now ends at five quiet seconds instead of waiting out the 120 s window, so a loss costs ~5 s rather
than ~112 s. The rule is falsifiable: any earlier or repeated gap falls outside it and fails.
