# T3.5f: why the live odometry closed 0.32 m and 0.37 m, against 12 mm in T3.5d (2026-10-21)

> **SUPERSEDED 2026-10-21 (late).** The cause of the 0.32 m "closure error" is **placement, not odometry**: the base was put down at two
> places 0.32 m apart, and the two runs were driven between them in opposite directions (a P/Q swap). FAST-LIVO2 itself closed to
> **about 1 cm** in both runs. Everything below this block is kept as the record of how we got here. Its ranking ("favourable outlier",
> "run 2 attitude", "marks distorted") is withdrawn. Two items survive: the 0.15 s stamp latency (own section below) and the
> timing and attitude facts in the tables (they are measured and unchanged).

## Superseding finding: placement (P/Q swap) `[measured]` unless tagged

Sherman confirmed: one tape mark A, and run 2 started exactly where run 1 ended (the robot was not moved between runs).

**1. The decisive cross-run check.** Raw LiDAR, sensor frame, no odometry and no map, 3 s windows, 6-DOF point-to-plane (the frozen
prototype's `icp_plane`), identity start plus a ring of 8 starts 0.5 m out. Script `closure_independence.py`, output
`out/closure_independence.txt` (3 s windows, range 0.5 to 40 m).

| Registration (source onto target) | Fit | Inliers at the fit (at identity unfitted) |
|---|---|---|
| Run 2 first 3 s onto run 1 last 3 s | (-0.006, +0.010) m, 1.2 cm, yaw +1.74 deg | 0.987 (0.946) |
| Run 2 last 3 s onto run 1 first 3 s | (-0.007, +0.013) m, 1.4 cm, yaw +0.07 deg | 0.994 (0.994) |

All 8 ring starts converge to the same fit in both. Run 2 began where run 1 ended and ended where run 1 began, to 1 to 1.4 cm. The
two closure vectors are opposite because the runs are the two directions of one trip, P to Q and Q to P (P = run 1 start, Q = run 1 end
= run 2 start). They are not drift.

**2. Independence check (is the 0.32 m a guess-biased fit?).** Last 3 s onto first 3 s of the same run, from IDENTITY (the "came
back" hypothesis) and from the odometry answer. Windows are stationary (odometry maximum excursion in a window: run 1 1 mm and 4 mm,
run 2 7 mm and 10 mm).

| 1 | odometry (+0.246, -0.202) | (+0.247, -0.202) m, 0.319, yaw -0.74 deg | 0.953 / 16 mm | 0.953 / 16 mm |
| 2 | identity | (-0.243, +0.210) m, 0.321, yaw -0.94 deg | 0.917 / 17 mm | 0.614 / 46 mm |

Both starts land on the same answer (0.000 m apart) with high inliers, and the fit forced to zero displacement is clearly worse

**4. Which hypothesis: was the start on A (H2), or the return on A (H1)?** Marks from `floor_marks.txt` (tape: AB 2.00, AC 2.00, BC
about 2.80, plus or minus 0.05) against run 1 odometry (start S = (0.001, 0.000), loop end Q = A_end = (0.245, -0.203), B (2.262,
-0.124), C (-0.045, 1.991)):

| Distance | Odometry | Tape | Residual |
|---|---|---|---|
| \|B-C\| (start independent) | 3.130 | 2.80 | **+0.330** |
| H1 (A = Q): \|B-A\| / \|C-A\| | 2.019 / 2.213 | 2.00 / 2.00 | +0.019 / **+0.213** |
| H2 (A = S): \|B-A\| / \|C-A\| | 2.264 / 1.992 | 2.00 / 2.00 | **+0.264** / -0.008 |

RMS residual over the three distances: H1 0.23 m, H2 0.24 m. **The marks do not separate H1 from H2.** Each fits one of B and C and
misses the other: under H1 mark C is inconsistent (AC +0.21), under H2 mark B is (AB +0.26). Under both, the pair B and C is 0.33 m
too far apart (six times the stated error), which no choice of A can fix. A free A that makes AB = AC = 2.00 exactly sits at
(0.267, 0.015): 0.22 m from Q and 0.27 m from S, between the two. Reading `[inferred]`: the mark tour (13 and 92 "HARD time lag"
self-syncs before the B and C readings, see the timing note below) or the visual placement of B and C carries the 0.33 m, and it is
the same in both hypotheses, so it is a separate unexplained item and not evidence about placement.

The operator notes: run 1 "base centre judged about on A at the end of the loop, not tape-measured"; run 2 "Start on taped outline at A" and
"return ~2 cm left of taped outline at A". With run 2 start = run 1 end, H1 contradicts one note (run 2's 2 cm return) and H2 contradicts
two (run 2's start, run 1's end). Weak lean towards H1 `[inferred]`, not a result. **One question settles it, no data needed:** at the
start of run 1, was the base on the taped outline? (If not, H1. If yes, H2 and both end-of-loop eyeball notes were wrong by 0.3 m.)
A tape measurement on the next session removes the doubt for good (place on the outline, record 5 s, move away, return, record 5 s,
`start_end_check.py`).

One small loose end: the earlier levelled 4-DOF registration of run 2's first 3 s onto run 1's first 3 s (step 0a, unfinished job,
log only) gave (+0.287, -0.221) = 0.36 m, 4 cm more than the sensor-frame 6-DOF chain (0.319 plus 0.012). Run 2 started tilted (3.0
deg pitch, 1.1 deg roll) and 4-DOF levelling does not remove that. `[inferred]`, not chased.

## Separate real item: pose stamps run 0.15 s late `[measured]` (cause of the lag `[inferred]`)

Independent of placement. `time_offset_sweep.py` on three recordings: best DELTA +0.15 s median (see the route analysis note, section 3).
The mapper's `/aft_mapped_to_init` stamps look like publish time, about 0.15 s after the pose they carry. The bridge copies the stamp
unchanged (`fastlivo_odom_bridge.py`, `_publish`), so `odom -> robot_base_link` inherits it. Effect: surfaces smear by speed times 0.15 s,
about 4 cm at 0.28 m/s, for anything that pairs a scan with the TF by stamp. Not a cause of the closure.

**Proposed change (made, default off):** parameter `stamp_offset_s` (default 0.0 in `config/fastlivo_bridge.yaml`), applied to the TF and the
optional `/odom` stamp through `shift_stamp`, exact integer nanoseconds. Proposed value -0.15. Tests in `bench/test_fastlivo_odom_bridge.py`:
the shift borrows and carries across the second boundary, is exact at epoch size, is zero at 0.0, and the shipped default is 0.0.
**Not proven:** (a) the 0.15 s is an inferred stamp convention, the mapper source was not read; (b) a mapper patch to stamp measurement
time would make -0.15 wrong, so the two must change together; (c) consumers that look up TF at the newest scan time (SLAM Toolbox) would need
a transform timeout of at least 0.15 s once the stamps move back, untested on the robot. Before setting -0.15: record `/tf` with it on
and re-run `time_offset_sweep.py` on that bag (expect best DELTA near 0), and run the SLAM Toolbox pairing with no extrapolation errors.

### Timing note on item 4

- No warning falls inside the run 1 drive window (16:37:40 to 16:38:56). The first one is at 16:40:10, 8 s after the F1 reading file was written (16:40:02). The headline return error was therefore read before the lag began, and the bag's last pose (0.246, -0.202) equals it. `[measured]`
- The B (16:44:27), C (16:46:02) and A (16:47:30) readings each sit in a quiet gap: no warning within 10 s of any of them. `[measured]` So the lag was **not** present at the moments those marks were read.
- But 13 "HARD time lag" self-sync lines happened before B and 92 before C. FAST-LIVO2 re-aligns its IMU clock to the LiDAR clock when the gap exceeds 1 s (`LIVMapper.cpp` self sync, `[code]` per the printed message, not re-read in the source today). Whether that shifted the pose between the end of the loop and B or C is `[unverified]`. It would be one reason B and C disagree with the end-of-loop A.
- Run 2 has 97 warnings, 5 of them in the last 7 s of the drive (0.50 to 0.52 s), and no HARD-lag lines.
- Run 1's mapper log covers 27 minutes (the retry started at 16:29, stopped 16:56), so the whole-log counts above are not drive counts. Only the in-window counts are.

## Other items in the brief

- **"Camera model not correctly specified" on the first start of run 1:** the stderr of the aborted start was overwritten by the retry, so the cause stays `[unverified]`. T3.5d used the same helper and started cleanly. A discovery race (the mapper asks the camera-info helper before the parameter service is visible) is the working guess `[inferred]`.
- **"Aborted (core dumped)" on Ctrl-C:** the stderr of run 2 ends with `terminate called after throwing an instance of 'rclcpp::exceptions::RCLError'`, `could not create publisher: rcl node's context is invalid`. This is the same teardown abort T3.5d recorded (2 of 4 stops). The "core dumped" wording comes from the container's shell. `[measured]` Not a cause of the drift: it happens after the pose stream ends.

## Ranked likely cause

1. **The T3.5d 12 mm closure is the favourable outlier, not the norm.** `[inferred]` T3.5d revisited one small patch for two minutes; FAST-LIVO2 matches against a local voxel map, so revisits help. The T3.5e write-up already says the closure holds "at the end, not in between". Two single-loop runs both land near 2 % of path. Nothing in the inputs, timing or push speed differs. Weight: leading, not proven.
2. **Run 2 only: attitude and pre-recording motion** (items 2 and 3). `[measured]` that it happened, `[inferred]` that it contributes.
3. **Mapper lag and clock self-sync after the drive** (item 4). Cannot touch the drive-window error, `[measured]`. May touch the B and C readings, `[unverified]`.

Not supported by the data: a driver or config change, IMU units, dropped frames, extra CPU load during the drive, or a faster push.
