## Required recording

| Stream | Required evidence |
|---|---|
| MID-360 LiDAR | `livox_ros_driver2/msg/CustomMsg`, point count, per-point offset times, `timebase`, frame and header timestamps |
| MID-360 IMU | `sensor_msgs/msg/Imu`, delivery counts/rate, units and timestamp behaviour |
| D455 colour | Raw images, actual dimensions/encoding/rate, serial pinned to the base camera |
| D455 calibration | Matching `CameraInfo`: K/D/R/P, distortion model, dimensions and optical frame |
| Provenance | Actual executables/libraries, package metadata, parameters, QoS, device identities, host time and recording settings |

Preserve native sensor headers and the original bag. Do not apply guessed time
offsets or reuse the authors' Avia camera calibration for the D455. Camera depth
is optional for this FAST-LIVO2 capture; it is not needed to prove colour/IMU/
LiDAR delivery. Any depth recording has its own explicit storage budget.

## Procedure gates (commands issued one stage at a time)

1. **Attendance/custody:** operator at the stationary robot, sensors secured,
   agreed sensor window, physical stop/power arrangement understood. No vehicle,
   arm, teleop, SLAM, Nav2 or manipulation launch is part of this task.
2. **Environment:** use the existing isolated T3.5 workspace; do not edit the
   lab's main checkout or replace its installed overlay. Check runtime resource
   conflicts, lock ownership, free space, and an empty private ROS domain.
3. **Driver-only preparation:** inspect installed launch/configuration first.
   The owned `lidar_only.launch.py:19` forces `xfer_format=0` (PointCloud2),
   unsuitable here. The vendor `msg_MID360_launch.py:8` selects custom format;
   verify the actual installed/source launch, IPs and absence of other actions.
   Existing quick-start `nav` starts localisation; `grasp` starts arm/wrist
   processes. Neither is a sensor-only capture procedure.
4. **Operator startup:** operator starts only the reviewed LiDAR/IMU and
   serial-pinned D455 drivers. Automation does not start hardware drivers.
   Confirm actual topics/types/QoS, CameraInfo and frames before recording.
5. **Short proof capture:** record all required streams simultaneously into a
   new non-overwriting bag after warm-up. Check size and all stream counts
   before a longer stationary recording. Stop only the operator's own groups.
6. **Offline analysis:** reconcile topic counts, header/receipt time spans,
   backwards timestamps/gaps, CustomMsg point timing and finite sensor values.
   Describe clock domains and observed offsets; a stationary bag alone cannot
   prove physical synchronisation, time-delay calibration or accurate extrinsics.
7. **Close-out:** preserve bag/configuration/parameter evidence, verify driver
   shutdown and custody, then update T3.5b from measured results. T3.5c remains
   gated on recording characterisation and T5.5 calibration.

Use installed `ros2 bag` tooling before adding a recorder or dependencies.
Exact capture topics, profiles, QoS and duration remain to be verified; they
are not inferred from the public recording or from old driver defaults.
