## Procedure gates (commands issued one stage at a time)

1. **Attendance/custody:** operator at the stationary robot, sensors secured,
   agreed sensor window, physical stop/power arrangement understood. No vehicle,
   arm, teleop, SLAM, Nav2 or manipulation launch is part of this task.
2. **Environment:** use the existing isolated T3.5 workspace; do not edit the
   lab's main checkout or replace its installed overlay. Check runtime resource
   conflicts, lock ownership, free space, and an empty private ROS domain.
3. **Driver-only preparation:** inspect installed launch/configuration first.
   The owned `lidar_only.launch.py:19` forces `xfer_format=0` (PointCloud2),
   unsuitable here. The vendor `msg_MID360_launch.py:8` selects custom format;
   verify the actual installed/source launch, IPs and absence of other actions.
   Existing quick-start `nav` starts localisation; `grasp` starts arm/wrist
   processes. Neither is a sensor-only capture procedure.
4. **Operator startup:** operator starts only the reviewed LiDAR/IMU and
   serial-pinned D455 drivers. Automation does not start hardware drivers.
   Confirm actual topics/types/QoS, CameraInfo and frames before recording.
5. **Short proof capture:** record all required streams simultaneously into a
   new non-overwriting bag after warm-up. Check size and all stream counts
   before a longer stationary recording. Stop only the operator's own groups.
6. **Offline analysis:** reconcile topic counts, header/receipt time spans,
   backwards timestamps/gaps, CustomMsg point timing and finite sensor values.
   Describe clock domains and observed offsets; a stationary bag alone cannot
   prove physical synchronisation, time-delay calibration or accurate extrinsics.
7. **Close-out:** preserve bag/configuration/parameter evidence, verify driver
   shutdown and custody, then update T3.5b from measured results. T3.5c remains
   gated on recording characterisation and T5.5 calibration.

Use installed `ros2 bag` tooling before adding a recorder or dependencies.
Exact capture topics, profiles, QoS and duration remain to be verified; they
are not inferred from the public recording or from old driver defaults.

## Offline analysis (`rosbag2_py` + `rclpy` deserialisation)

Numbers below were re-verified on the primary bag by the strict asserting
[`analyze_bag.py`](tools/fastlivo/analyze_bag.py) (`ANALYSIS_OK`, exit 0); it
supersedes the scratch `analyze_proof3_ros.py` (defective units and checks).

- **LiDAR** (`livox_ros_driver2/msg/CustomMsg`, frame `livox_frame`,
  `lidar_id` 192): 10 Hz nominal, header span 73.90 s, max gap 106 ms, zero
  backwards stamps. `point_num` 19,872–20,160 (mean ~20,000).
  `timebase` equals header stamp (max abs diff 0.000000 s). Per-point
  `offset_time` is nanoseconds spanning 0 to ~100 M (~94–100 ms per scan);
  points are **not** time-sorted within a scan (global monotonicity false on
  all sampled messages) — recorded as a characteristic for T3.5c, since the
  authors' Avia bag is sorted. All sampled points finite; lines 0–3 present.
  Receipt lags header by ~104 ms mean; scan accumulation is a possible
  contributor, not an independently measured cause. See the full-bag audit below
  for zero-range returns; finite coordinates alone do not make every return usable.
- **IMU** (`sensor_msgs/msg/Imu`, frame `livox_frame`): 200.0 Hz, span
  74.03 s, max gap 11 ms, zero backwards, zero non-finite. Gyro mean
  (−0.0116, 0.0020, 0.0075) rad/s, std ≤ 0.0014 — plausible stationary.
  Accel mean (0.001, −0.010, 0.990), |a| = 0.990: as-published units read as
  g-scale, while `sensor_msgs/Imu` expects m/s². **Do not rescale the bag;**
  T3.5c must decide unit handling at the consumer. Orientation is constant
  identity (driver provides none).
- **Images** (`rgb8`, 640x480, step 1920, little-endian, frame
  `camera_color_optical_frame`): 30.0 Hz, span 74.00 s, max header gap
  33.4 ms, zero backwards, constant 921,600-byte payloads. Receipt lags
   header 31.7 ms median (corrected by the full-bag audit).
- **CameraInfo**: 1:1 with images, zero stamp mismatches, `plumb_bob`,
  640x480, K/D/R/P stable across the bag:
  K=[385.09, 0, 324.92, 0, 384.57, 248.54, 0, 0, 1],
  D=[−0.0559, 0.0661, 0.0002, 0.0002, −0.0215], R=identity,
  P=[385.09, 0, 324.92, 0, 0, 384.57, 248.54, 0, 0, 0, 1, 0].
- **Cross-sensor**: first headers within ~20 ms (image −6 ms vs LiDAR,
  IMU +14 ms vs LiDAR, CameraInfo == image exact). Offered QoS per
  `metadata.yaml` on all four topics.
- Residuals: point-ordering effect on deskew is unproven until T3.5c replay;
  IMU unit handling is a consumer decision, not a bag defect; stationary data
  cannot prove physical time-sync, delay calibration or extrinsics (T5.5).
