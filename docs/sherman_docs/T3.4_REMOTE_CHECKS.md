## Re-run remotely (software only)

Use an approved test checkout, leaving other users' branches/processes unchanged.
From that checkout's root, first check no other bench/CI job is using the box:

```bash
ps -eo pid,user,etime,args | grep -E '[R]unner.Worker|[b]ench/run.sh|[t]est_velocity_smoother|[t]est_nav_nodes'
```

If another job appears, wait and coordinate. Then run one at a time:

```bash
python3 bench/test_t34_guard.py
python3 bench/test_t34_launch.py
bash bench/velocity_smoother.sh
```

Expected: guard/wiring unit tests OK; software PASS cases with measured timings; final
`guards ok` after cleanup. Exit 1 means failure/refusal, exit 3 means dependency SKIPPED.
Do not weaken a guard to make a test run. Do not join the private domain during its run.
The runner sources ROS only and opens no hardware. Test logs are under `log/`.

For real launch-description construction only, source an existing nav environment:

```bash
source nav/nav_env.sh
python3 bench/test_t34_launch.py --runtime
```

This verifies the installed config path and builds launch actions in memory; it does not
execute them. A missing overlay/config is a setup failure, not evidence of LiDAR health.

## Bounds and failure meaning

The smoother uses 20 Hz, maximum +/-0.05 m/s and +/-0.15 rad/s, acceleration 0.1 m/s²
and 0.3 rad/s², deceleration magnitudes 0.2 and 0.6, and 0.25 s stale-input timeout.
Tests require correct nonzero direction, bounded output and zero within 0.65 s after input
loss or explicit zero. Keyboard-to-output silence must zero within 1.0 s. Normal exits
restore terminal settings. Killing teleop is tested only with the smoother still alive.

These are message-level limits, not physical braking guarantees. Killing the smoother,
network failure and the chassis watchdog remain unverified. A final zero publication can
be lost; Ctrl+C is not a hardware stop. Key release is not directly available in an ordinary
terminal. Initial key-repeat delay may cause a pause; this is not a true hold-to-run switch.
