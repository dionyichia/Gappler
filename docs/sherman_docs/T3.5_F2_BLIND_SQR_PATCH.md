# F2 — `preprocess.blind` cannot act: patch, build and measurement

2026-10-19. Follow-up to [`T3.5_CONFIG_SWEEP_20261019.md`](T3.5_CONFIG_SWEEP_20261019.md) §3 F2.
Decision (Sherman, 2026-10-19): **patch**, as a separately tagged experimental image, with the
pinned image kept as the control. Nothing in the pinned binary, the frozen pair or the accepted
image is modified by this note.

## 1. Defect, restated in one paragraph

`preprocess.blind: 0.1` is meant to drop returns closer than 0.1 m. The AVIA/CustomMsg path applies
it at `preprocess.cpp:194` as `x² + y² + z² >= blind_sqr`. `blind_sqr` is declared
(`include/preprocess.h:185`) and read 14 times, and **never assigned** anywhere in the fork; the
member is uninitialised. Upstream computes it immediately after its parameter block
(`hku-mars/FAST-LIVO2` `LIVMapper.cpp:116`). The port dropped exactly that line. Our staged pair
takes this path (`preprocess.lidar_type: 1`, CustomMsg), and the recorded bag carries 51.84 %
zero-range `(0,0,0)` returns, whose fate at this gate is therefore undefined.

## 2. The patch

One behaviour line, restored where upstream has it, plus one tagged print of the threshold in
force. Applied to the byte-identical pinned `LIVMapper.cpp` (`sha256:815b5f89…`):

```cpp
  this->node->get_parameter("publish.dense_map_en", dense_map_en);
/* T35_BLIND_SQR */ // F2: restore the line the port dropped; without it the gate at
/* T35_BLIND_SQR */ // preprocess.cpp:194 reads an uninitialised member (config sweep 2026-10-19).
/* T35_BLIND_SQR */ p_pre->blind_sqr = p_pre->blind * p_pre->blind;
/* T35_BLIND_SQR */ std::cout << "[T35_BLIND_SQR] blind=" << p_pre->blind << " blind_sqr=" << p_pre->blind_sqr << std::endl;
}
```

`patch_blind_sqr.py` refuses any other source bytes, refuses a repeated application (the result no
longer matches the pinned hash), fails closed if the anchor is absent or ambiguous, and tags every
added line so that stripping the tagged lines recovers the original byte-for-byte.
`readParameters` is called once from the constructor (`LIVMapper.cpp:30`, `readParameters` at `:53`),
so the print appears once at startup and the assignment precedes every scan.

**Declined, with reasons.**

- *Initialising the member in `preprocess.h`* (`blind_sqr = 0.0` or `0.01*0.01`). Either value
  merely picks a fate for the gate; it does not restore the configured threshold, and a silent
  `0.0` would keep every zero-range return — the same "config value that does nothing" this whole
  line of work is about. The assignment is the fix.
- *A third `T35_VIO_REPAIR` stage.* The knob is named for VIO repairs; this is a LiDAR-path fix. The
  mislabel would be the defect class F1 already recorded (a name that tells an operator to look in
  the wrong place).
- *Instrumented counters.* Unnecessary: the pinned binary already prints the post-gate count
  (`[ Preprocess ] Output point number:`, `preprocess.cpp:200`, once per handled message), so the
  control run needs no new build.
- *Patching the frozen `t35b_proof3` pair or the accepted image.* Both are evidence of runs that
  really happened; the fix is a new image, and the pair that uses it is staged separately.

## 4. The measurement

**Status, 2026-10-19: built, control measured, patched replay done and confirmed.**

**Which patched image was measured.** Sherman chose the combined candidate for T3.5c, so the gate was
measured on `ac276ad7…` (`T35_COMBINED_REPAIR=1`) — both visual repairs plus this patch — rather than
on the F2-only image `81f1c3c2…`. The F2-only image is a superseded spare: it is byte-verified but has
no run. See `T3.5c_COMBINED_BUILD.html` for the parent/tag/source gates.

The control is the **already-built accepted image**, and a valid control replay was already on disk
(`replays/t59-replay-20261018T062144Z-511887`: accepted image `sha256:d0dcfa8a…`, bag
`t35b_proof3`, pair `t35b_proof3_lio.yaml`, 740 handled messages, verdict PASS), so the measurement
costs one build and one replay.

The build succeeded on 2026-10-19: `Finished <<< fast_livo [1min 31s]`, `State.ExitCode 0`,
`OOMKilled false`, `source.patch` exactly the four tagged lines, container `NetworkMode: none`,
8 GiB / 8 GiB swap, 2 CPUs, 512 PIDs, no privileges or mounts, and the commit
`sha256:81f1c3c2a6dc030c7c58e34eae2f30cfb56b92b21a8f1dde152277c0d5d382cf` under the tag
`t35-fastlivo-blind-sqr:experimental`, from the accepted image ID. The patched source inside the
container hashes to `e61bbdeda3ea578d…`, byte-identical to the patch applied locally on the Mac

`tools/fastlivo/EVIDENCE_f2-blind-sqr-build-20261019.sha256` (42 files) plus the control replay's
`result.json` and `mapper.stdout.log`.

Observable: `[ Preprocess ] Output point number:` in `evidence/mapper.stdout.log`. It is the point
count after the whole `avia_handler` loop — after the `line < N_SCANS` gate (the bag's `line` is in
[0,3] and `scan_line: 4`, so nothing is dropped there) and after sampling (`point_filter_num: 1`).
So for a given bag it is exactly the count that survives the range gate.

Full-bag audit (`T3.5_INPUT_FREEZE_20261017.md`, `T3.5_CONSUMER_CONTRACT.md` §2): 14,799,936 points,
of which 7,672,813 (51.84 %) are `(0,0,0)`. The bag carries **740** handled messages at ~20,000

(14,799,936 points = 154,166 × 96-point packets) over 740 handled messages is 208.3 packets per
message, and 19,968 = 208 × 96 exactly — so the median *is* the full packet count, not a filtered
one. It is the same on the three images that have a run of this bag (accepted pinned `d0dcfa8a`
under both config pairs, VIO-diagnostic `3cd781a6`, visibility `ba66a419`) — four runs, no
variation. (The visibility-voxel image `2fa9f264` has a run of the *public* recording only, so it is
outside the control set; recorded rather than glossed over.) The gate therefore dropped **nothing**:
every replay run of this bag so far has mapped all 51.84 % zero-range returns. This is the gate-off
branch, confirmed before the patched image was ever replayed.

Evidence: `tools/fastlivo/EVIDENCE_t35c-f2-runtime-20261019.sha256` (31 files: the whole run directory

**Falsification.** The fix is confirmed if the patched run's counts sit at 0.48 ± 0.02 of the
control's *and* the banner reports `blind_sqr=0.01`. It is contradicted if the patched counts equal
the control's (the gate is not on this path), if the banner is absent from the binary, or if the
patched counts are lower than 0.48 of the control's (something else is dropping points too, and this
measurement cannot attribute the drop). **The confirmation above is on this bag only, and it is not a
ratio to reuse.** `t35b_proof3` is 51.84 % zero-range; `stationary02` is 35.92 %, so its post-gate
fraction must be measured there and not predicted by scaling from here.

## 5. What this does not prove

- Nothing about mapping quality, pose drift or moving-map behaviour. A short stationary bag with
  fewer points in the map is not an accuracy result; T5.5/T5.6 and the T3.5d/e runs own that. The
  F2 run says only that the gate removes the zeros it was meant to remove, on one bag, offline.
- Not own-data acceptance. The gate was measured on the old `t35b_proof3` bag; `stationary02` has not
  been replayed on the combined image yet.
- Not the pinning decision. If the fix is adopted, the pinned image stays the control, the frozen
  pair stays byte-unchanged, and the pairing used for any future accepted run needs its own
  reviewed statement (contract §8).
- Not the public recording's behaviour. The combined image still has to pass the retained public
  visual regression, where the same gate will also drop near-range returns.
- The uninitialised read is not made non-undefined by this note; it is made **irrelevant** to the
  fixed build. The pinned build's actual value stays whatever the allocator left there — which is
  precisely what the control run measures.
