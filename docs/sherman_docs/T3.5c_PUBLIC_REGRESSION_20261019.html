1. The failure, one paragraph

The harness requires every input topic's last expected stamp to have been seen (CallbackTracker.tails_seen()). The mapper received 667 of the bag's 668 /left_camera/image messages. The missing one is the last message in the recording: its stored time 1661405918.202350 equals the metadata end 1661405918.2023504, its header is 1661405918.1911774, and its expected stamp 1661405918.291177 is header plus the configured time_offset.img_time_offset: 0.1. One gap kept the drain in waiting until its hard 120 s deadline. The estimator was idle throughout (callback counts and log sizes flat, wall 270.7 s → 380.9 s). 4. Control comparison, including where the loss can and cannot be placed

  • Terminal delivery: control received the stamp during normal playback (camera 646 at wall 263.0 s → 668 by drain start 273.1 s), not during the drain.
  • Publisher or subscriber? The pinned mapper subscribes to the image topic with depth 200,000, RELIABLE (LIVMapper.cpp:310), so a one-message subscriber-side drop is implausible — and there is no second input observer to cross-check: the drain's callback_counts and the coverage rows both come from the mapper's own log. Leading mechanism: rosbag2_player reaching EOF and exiting with its final sample unacknowledged. Leading, not proven — retained evidence cannot separate it from transport loss at that instant.
  • Shutdown: identical. Same two pre-existing imu loop back errors (offsets 0.000505 / 0.000405), mapper exit 0 ending in signal_handler(SIGINT/SIGTERM), camera exit 0, player exit 0 having exited by itself. Only the trigger differs: control torn down after 5 quiet seconds (wall ≈ 278 s), this run after the 120 s deadline (wall ≈ 390 s). No crash, no OOM, no teardown difference.
  • RGB count, attributed rather than excused: the mapper publishes /rgb_img unconditionally once per LIO iteration (publish_img_rgb, LIVMapper.cpp:1342, called at line 508), and [T35_DIAG_CLOUD] from the same call path is 664 in both runs — mapper-side publication is equal. The monitor's 401 vs 606 is a BEST_EFFORT monitor loss, already 18 behind by the first snapshot (wall 10.7 s: rgb 3 vs cloud 21) and growing monotonically to 261. The written criterion is still not met by count; its validity clause is (all three streams invalid = 0).

6. Harness fix: one bounded terminal-message allowance

Authorised by Sherman ("fix the harnass"). Written test-first — the acceptance case, eight rejection cases, the reconciled-rows helper, the supervisor verdict both ways and the closed default without a declared LiDAR topic — with 59 replay tests and 34 recipe tests green locally and the same 59 green on the box, manifest 36/36. It edits replay.py and replay_progress.py only: no config, QoS, tolerance, rate, bag or image byte changed.

A run may now record terminal_message_lost and still pass coverage only when all of these hold:

  1. the LiDAR stream is complete (missing 0, unexpected 0);
  2. exactly one other input topic has a gap, and it is exactly one message;
  3. the missing stamp is that topic's own last expected stamp;
  4. it is strictly later than the last observed LiDAR callback;
  5. every other topic is exact, with the unchanged IMU prestart allowance applied first;
  6. no duplicates on any topic.

An earlier stamp, a second missing message, a lost LiDAR frame, a duplicate, or a gap on a second topic still fails exactly as before. The accepted stamp is recorded, not hidden: the coverage row keeps missing = 1, and result.json gains terminal_message_lost with topic, stamp and the 0.192 s offset. A loss now costs about five seconds of drain instead of about 112 s.
