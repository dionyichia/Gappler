## 1. Routing — how the consumer selects a LiDAR path for this bag

- `lidar_type` selects the subscription type (`LIVMapper.cpp:288–310`): `AVIA` (1) subscribes
  `livox_ros_driver2/msg/CustomMsg` (package chosen by `common.livox_msg_type`, default
  `"livox_ros_driver2"`; `livox_interfaces` is the fallback alternative, `:296–302`); **any other
  value** subscribes `sensor_msgs/msg/PointCloud2` (`:307`). Enums in `common_lib.h`.
- Every `CustomMsg` goes through `avia_handler` regardless of `lidar_type` (`preprocess.cpp:54–58`);
  `mid360_handler` exists only on the PointCloud2 branch.
- The staged pair therefore uses `preprocess.lidar_type: 1`. `lidar_type: 8` (MID360) would subscribe
  PointCloud2 and receive **nothing** from this bag; the checker fails any routing/recorded-type
  mismatch.
- Schema identity: pinned driver `msg/CustomMsg.msg` + `msg/CustomPoint.msg` are byte-identical to
  the recording driver's copy (`diff` empty) — same CDR layout, so replay deserialises our bag
  losslessly. Per point: `offset_time` uint32 ns, x/y/z float32, reflectivity uint8, tag uint8,
  line uint8.
- Subscriptions are depth-200 000 queues (`:300`, `:304`, `:309`, `:310`). The recorded
  `offered_qos_profiles` report `reliability: 1` (RELIABLE) on all four topics — a default reliable
  subscriber is compatible — but `history/depth` read back as `3/0` (not meaningful), which is why
  replay must apply explicit QoS overrides (same pattern as the accepted public run's
  `playback_qos.yaml`).

## 2. Point path (`avia_handler`, feature extraction disabled)

Message-order pipeline, `preprocess.cpp:170–202`:

1. Gate `line < N_SCANS` (`:172`; the tag filter is commented out). `N_SCANS` comes from
   `preprocess.scan_line` (`LIVMapper.cpp:176`). Bag: `line` ∈ [0,3] (20-scan sample, 400,032
   points; strict audit `lines_max=3` full bag) — **`scan_line: 4` is exact**, nothing dropped.
2. `curvature = offset_time / 1e6` → milliseconds (`:180`).
3. First point of the message: |curvature| ≥ 1 ms is zeroed (`:182–183`).
4. Later points: |curv − prev| ≥ 1 ms → curvature := prev + 0.004166667 ms (4.167 µs); `prev` is the
   already-rewritten predecessor, in message order (`:186–189`).
5. Sampling `valid_num % point_filter_num == 0` (`:192`).
6. Range gate `x²+y²+z² ≥ blind_sqr` (`:194`) — **the threshold this gate compares against is
   never set.** The port assigns `blind` (`LIVMapper.cpp:173`, `preprocess.cpp:50`) but never
   `blind_sqr`; upstream computes it immediately after its parameter block
   (`p_pre->blind_sqr = p_pre->blind * p_pre->blind`, `hku-mars/FAST-LIVO2` `LIVMapper.cpp:116`).
   The member is read uninitialised, so the configured `blind` has no reliable effect and the
   zero-range returns counted below **cannot be assumed dropped**. Recorded as F2 in
   [`T3.5_CONFIG_SWEEP_20261019.md`](T3.5_CONFIG_SWEEP_20261019.md); the checker now emits a note
   for it, and the frozen pair's own comment repeating the old claim is superseded (§8). Fixing it
   is a source patch (a new image tag, compared against the accepted image), never a config change —
   the prepared patch, its build mode and the measurement are in
   [`T3.5_F2_BLIND_SQR_PATCH.md`](T3.5_F2_BLIND_SQR_PATCH.md).

Quantified on the bag (20-scan sample, 400,032 points; `clamp_stats.py`, `order_stats.py`, outputs
pinned in the evidence manifest):

- Clamp rewrites: **864 points (0.216%)**, zero first-point rewrites; the rewrites are forward-gap
  compressions (no backward jump ≥ 1 ms exists).
- Order inversions: 2,697 decrease steps (0.67%), **largest 458 µs**, present in all 20 scans.
- Zero-range returns: 7,672,813 / 14,799,936 points (51.84%, full bag) — a driver characteristic for
  no-return samples, not an error. Whether the consumer drops them is **open** (item 6: the gate's
  threshold is unset), so no T3.5 replay so far can be credited with near-range rejection.
- Offsets: 0…106,432,551 ns full bag; `timebase == header` to 0.000 ms.

**Deskew order assumption (residual R4).** The IMU deskew path (`UndistortPcl`) does **not** sort:
its sort is commented out (`IMU_Processing.cpp:289`) and its point-cursor loop (`:498–536`) is
written for time-sorted points; only the no-IMU fallback sorts (`Forward_without_imu:159`). Our
scans are unsorted with ≤ 458 µs inversions. Stationary: inert (zero inter-point motion). Moving
(T3.5d/e): the ≥ 1 ms clamp and sub-millisecond inversions are unmodeled and must be measured on a
motion case before any moving-accuracy claim.

## 3. IMU path

- IMU before the first LiDAR message is dropped (`LIVMapper.cpp:985`); our streams start interleaved
  (first IMU header +14.319 ms vs first LiDAR), so nothing is lost at head. Loop-back drops a
  message and logs an error (`:1001–1007`); a > 0.2 s jump clears the IMU timeline (`:1009–1013`).
- `imu_time_offset` is subtracted from IMU stamps (`:988`); `ros_driver_bug_fix` (whole-second
  rounding, `:991–997`) is off — no such offset was measured (T3.5b).
- Initialisation (`IMU_Processing.cpp:107–152`): average over `imu_int_frame` samples
  (`imu.imu_int_frame` → `set_imu_init_frame_num`, `LIVMapper.cpp:248`); gravity =
  `−mean_acc/|mean_acc| · G_m_s2` (`:147`); `IMU_mean_acc_norm = |mean_acc|` (`:146`). Staged 50 ≈
  0.25 s at the recorded 200.0 Hz.
- Normalisation happens once per IMU pair during propagation:
  `acc_avr · G_m_s2 / |mean_acc|` (`:355`). A g-unit accelerometer (|a| = 0.990 as published) and an
  SI-unit one both land at true gravity; **no rescale is applied to the recording** (matches the
  T3.5b conclusion). Bias covariances are hard-coded 0.0001 (`LIVMapper.cpp:246–247`);
  `imu.b_acc_cov` / `imu.b_gyr_cov` are inert and carried for documentation only (checker notes
  them).
- Sync gate (ONLY_LIO): consumption waits until IMU messages extend past the scan end
  (`sync_packages :1099–1145`; end = scan start + last-point curvature/1000). At bag end this can
  hold back the final scan(s) — a replay-accounting nuance for T3.5c, not a config defect.

## 4. Image path (diagnostic pair: `common.img_en: 0` → ONLY_LIO; visual file: `img_en: 1`)

- With `img_en` false the callback returns immediately (`:1040`), though the subscription still
  exists (`:310`). Images in the bag are ignored; the diagnostic requires nothing of the camera leg.
- The visual file turns the module on with the nominal extrinsic of §7; T3.5c's acceptance is
  sustained visual updates with valid outputs, falling back to the diagnostic if visual fusion
  misbehaves. The visual run proceeds ahead of T5.5 by explicit tree framing; calibration accuracy
  is not claimed.
- The image path as staged (active in the visual file): `getImageFromMsg` uses
  `cv_bridge::toCvCopy(msg, "bgr8")` (`:1030–1035`) — rgb8 input is channel-swapped correctly by
  cv_bridge; grayscale happens via `CV_BGR2GRAY` on 3-channel input (`vio.cpp:1905`) with `Frame`
  requiring `CV_8UC1` (`frame.cpp:45`).
- `img_time_offset` is added to stamps (`:1056`); a < 20 ms spacing guard drops frames
  (`:1071–1077`) — 30 Hz spacing (33 ms) passes; a < 1 ms duplicate filter (`:1057`) and a
  pre-first-LiDAR drop (`:1059`) also apply; `hilti_en` decimation is off.
- Geometry invariant: internal camera size = `cam_width × cam_height × scale`
  (`pinhole_camera.cpp:24–25`) must equal the delivered image size, or `processFrame` resizes by
  `scale` (`vio.cpp:1896–1900`, `vio.cpp:50`). Staged: 640×480 at scale 1.0 == rgb8 640×480 → the
  resize path never triggers (checker enforces).

## 5. Camera parameters and the k3 residual (R3)

- The mapper loads the camera from **another node**: `loadFromRosNs(node, "parameter_blackboard",
  cam)` (`LIVMapper.cpp:212`; `vikit_ros/src/camera_loader.cpp:16–38`). Values arrive via a remote
  `GetParameters` call with a 100 ms service wait, then a slow `ros2 param get` fallback, then
  defaults (`vikit_ros/include/vikit/params_helper.h:104–129`, wait at `:117`). **Start the
  `parameter_blackboard` server and wait for its service before starting the mapper**, or the
  camera silently degrades (`cam_model` default `""` → hard "Camera model not correctly specified"
  failure).
- The `Pinhole` branch reads `cam_model, cam_width, cam_height, scale, cam_fx, cam_fy, cam_cx,
  cam_cy, cam_d0…cam_d3` — **`cam_d4` is never read** (`camera_loader.cpp:26–37`); the fifth
  coefficient defaults to 0.0 (`pinhole_camera.h:40`). CameraInfo `plumb_bob` D = [k1,k2,p1,p2,k3]
  maps d0=k1, d1=k2, d2=p1, d3=p2 (`pinhole_camera.cpp:32,100–102`), so the runtime model is
  4-coefficient. k3 = −0.021481290459632874 is carried in the staged YAML for reference only and
  the checker verifies it. Bounded impact estimate: the dropped r⁶ term is ≈ 0.13 px at half-radius
  and ≈ 4 px in the extreme corner (fx ≈ 385); projection and undistort use the same truncated
  model consistently.
- Staged values equal the bag's first CameraInfo at full precision (checker enforces exact float
  equality): fx 385.0851135253906, fy 384.5696105957031, cx 324.9161376953125, cy 248.54244995117188.

## 7. Extrinsics state (T5.5 owns the real values)

- `extrin_calib.extrinsic_T/R` (LiDAR→IMU; used by LIO in **both** modes): the pinned fork's own
  Mid-360 baseline `[0.011, 0.02329, -0.04412]` has its **sign inverted** for the fork's own code,
  which applies it as `p_imu = extrinsic_R · p_lidar + extrinsic_T` (`IMU_Processing.cpp:85–92`, used
  at `:528`). The Livox Mid-360 manual ("IMU Data", p.15) puts the IMU chip at
  (+11.0, +23.29, −44.12) mm **in the point-cloud coordinates** and documents its axes as parallel to
  that frame; our driver publishes raw sensor-frame points (vendored `MID360_config.json`
  `extrinsic_parameter` all-zero, pushed to the device as its install attitude), so the manual's
  numbers transfer unrotated and the reviewed value is `[-0.011, -0.02329, 0.04412]` with identity
  rotation. Evidence, three-way comparison and residuals: `T3.5_LIDAR_IMU_EXTRINSIC_FINDING.md`
  (2026-10-18). The fork has **no online extrinsic estimation** — `extrinsic_est_en` is absent from
  its source — so a wrong value is never corrected at runtime, and every replay so far carries the
  10.2 cm geometric inconsistency. Both staged pairs keep the pre-correction value byte-unchanged
  (frozen to the old bag and to the collected box evidence: the T3.5a/T3.5c runs really did execute
  that value); the checker notes their known sign rather than failing them, and **a new pair must
  carry the corrected value**. Neither number is measured on our unit: the corrected translation is
  the vendor's document for the sensor class, and the mount rotation is eye-estimated zeros (below).
  Empirical confirmation is the in-place rotation test in T3.5d — a wrong body constant makes the
  reconstructed base position walk a 10.2 cm circle at the rotation frequency.
- `extrin_calib.Rcl/Pcl` (LiDAR→camera; `p_cam = Rcl·p_lidar + Pcl`, `vio.cpp:38–39, 58–59`):
  **two staged states.** The diagnostic file keeps the fork's example as a non-empty placeholder
  (`img_en: 0`, VIO does not run; loaded unconditionally at `LIVMapper.cpp:186–187, 218`).
- The visual file carries the **reviewed nominal composition** (2026-10-17): T_base←livox = M2
  retained mount (0.18, 0, 0.2; eye-estimated zero rotation) composed with the full T5.4
  as-fitted chain to the colour optical frame (screw 0.208/0/0.528 + Intel body
  0.01115/0.0475/0.0145 + colour y −0.059 + optical rpy(−π/2, 0, −π/2)); same camera unit
  (serial 146222253541) and fitted mount as the recording (T5.4; T3.5b capture record). Result:
  `Rcl = [0,−1,0, 0,0,−1, 1,0,0]`, `Pcl = (−0.0115, 0.3425, −0.03915)` m.
  This is a provenance-labelled **working estimate, not a calibration**: mount angles are
  eye-estimated zeros (T5.4: angular uncertainty unknown); translation is tape-level; the T5.4
  live TF read differs sub-mm (factory trim, x 0.21915→0.218885). Rotation is the weak axis
  (≈ 6.7 px/deg at fx 385) — hence the projection pre-check before any fusion claim. The pinned
  code loads Rcl/Pcl once and never refines them online (only the image time-delay estimator
  exists, disabled). T5.5 owns the calibrated replacement; T5.6 verifies by projection.
