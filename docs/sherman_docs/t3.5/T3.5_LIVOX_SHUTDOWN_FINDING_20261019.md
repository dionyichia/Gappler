# T3.5c — Livox shutdown logger ABI collision

## Finding and scope

**The installed Livox SDK and ROS logging have incompatible spdlog symbols in
one process. A logger-only control reproduces a process-exit fault at the same
system-library instruction as the attended driver shutdown. No hardware is
needed to reproduce the mechanism. No production fix has been applied.**

This is an ABI [binary object-layout and calling-convention] collision, not a
bag-integrity failure. The [capture checks](T3.5_CAPTURE_AUDIT_20261019.md)
remain valid: the selected bag finalized before driver shutdown, and its full
79-file freeze was verified unchanged again after the diagnostic runs.

## What actually loads

- The driver executable is the generated ROS component host. It initializes ROS
  and dynamically loads `liblivox_ros_driver2.so`; looking only at the executable's
  dependency list omits the component's SDK dependency.
- In the same sourced nav environment used for capture, the component's SDK
  dependency resolves to `install_nav/livox_sdk2/lib/liblivox_lidar_sdk_shared.so`
  (Build ID `828997c54c0fc0da203837ee588584f4117bac7f`). This is **not** the
  separate `/usr/local/lib` copy, which is also installed.
- ROS brings in `librcl_logging_spdlog.so` and the system `libspdlog.so.1.9.2`.
- Vendored SDK headers declare spdlog **1.3.1** and bundled fmt v5; system ROS
  logging uses spdlog **1.9.2** and fmt v8. The SDK exports its spdlog C++
  templates, logger destructors and shared-pointer disposal functions under the
  same unversioned C++ names. The installed binary's exact build provenance was
  not independently rebuilt here; its exported symbols/disassembly and runtime
  binding are measured directly, rather than inferred solely from source.

## Hardware-free controlled reproduction

The retained `livox_logger_probe.py` loads libraries with `ctypes`, checks that
SDK file logging is disabled, calls only `InitLogger()` and `UninitLogger()`,
then exits. It never calls `LivoxLidarSdkInit`, starts a ROS node, opens a sensor
connection or invokes any driver. GDB catches faults before normal signal
delivery; no driver restart or production rebuild is involved.

| Case | Variable | Observed twice |
|---|---|---|
| Control | SDK logger only | Both calls return; process exits normally |
| Treatment | Load ROS logging globally before loading the same SDK | Both calls return; process-exit logger destruction faults in system spdlog |

Dynamic-loader traces provide the causal link: in the control, the SDK's
`_Sp_counted_ptr_inplace<spdlog::logger,...>::_M_dispose()` binds to the SDK
itself; in the treatment it binds to **system `libspdlog.so.1`**. The logger
is created by the SDK's older implementation but disposed using a different
object layout. The probe backtrace runs from SDK `shared_ptr<spdlog::logger>`
destruction through system `_M_dispose()` during `__run_exit_handlers`.

### Match to the attended shutdown

The original kernel log reports instruction `0x7f540dcd9a20` in the executable
mapping beginning `0x7f540dccf000`. The library ELF executable segment has VMA
`0x31000`; therefore the correct library VMA is:

`0x31000 + (0x7f540dcd9a20 - 0x7f540dccf000) = 0x3ba20`.

This resolves to `_M_dispose()+80`, exactly the treatment probe's fault site.
The original signal is **SIGBUS**, whereas both probes catch **SIGSEGV**;
these are not claimed identical signals or identical original stack traces.
The probes have `rbp=0x80` at a `mov 0x68(%rbp),%rdi` instruction, consistent
with interpreting invalid fields in the mismatched layout.

The SDK's explicit `UninitLogger()` calls `spdlog::drop_all()`, but the global
SDK `shared_ptr<spdlog::logger>` remains until process exit. This explains why
the capture log reaches SDK deinitialization and the Lddc destructor print
before the fault. Relevant source snapshots: `sdk_core/base/logging.cpp:27–59`,
`sdk_core/livox_lidar_sdk.cpp:108–124`, `livox_ros_driver2/src/lddc.cpp:80–107`,
and the generated ROS component host's main function.

The initial control GDB wrapper exited 1 only because it asked for registers
after a normally exited inferior; its process did exit normally. Repeat wrappers
query registers only for a stopped live inferior and exit 0 for both cases.
GDB's own exit 0 for the treatment is **not** an application pass: the captured
signal/backtrace is the expected failing installed-library behavior.

## Remediation boundary — proposed, not implemented

Prepare an isolated SDK build whose private C++ logging symbols cannot collide
with ROS, while preserving the public Livox C API. Verify its export/binding
table and rerun the same logger-only red/green check. Link a separately staged
driver/overlay to that SDK, not to a silently replaced system library.

Do not replace Ubuntu/ROS spdlog, overwrite `/usr/local/lib`, mutate the shared
dirty checkout, hide the crash with `_exit`, or treat a load-order workaround
as a validated production fix. Do not change calibration or bag contents.

Only an attended driver start/stop using the corrected build can establish
clean hardware-driver shutdown. That verification is still owed; it cannot be
substituted by this logger-only test. New bag identity/config preparation and
F2 image selection remain separate pre-replay work. No commit/push/PR/merge.
