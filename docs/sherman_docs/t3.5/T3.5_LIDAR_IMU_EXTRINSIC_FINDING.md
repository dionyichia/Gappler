# T3.5 LiDAR→IMU extrinsic — the pinned fork's Mid-360 profile has the sign inverted

2026-10-18. Read-only static analysis: no mapper execution, no hardware, no bag or config
modification. This document is the record behind the corrected value in
`T3.5_CONSUMER_CONTRACT.md` §7, residual **R2**, and the checker's new LiDAR→IMU assertion.

## Verdict

The pinned consumer (`U-AMC/FAST-LIVO2-ROS2` @ `a09599a288c56b832114d7ad9e898248a4111d9e`) ships
`extrin_calib.extrinsic_T: [0.011, 0.02329, -0.04412]` for Mid-360 in `config/mid360_only.yaml:13`
and `config/mid360_lvi.yaml:13`. Its own code requires the **negation** of that value.

| | Value |
|---|---|
| The fork ships (`extrinsic_T`, Mid-360) | `[0.011, 0.02329, -0.04412]` |
| The fork's code requires | `[-0.011, -0.02329, 0.04412]` |
| `extrinsic_R` | identity — **documented, not assumed** (see below) |

Both staged pairs (`replay/config/t35b_proof3_lio.yaml:35`, `t35b_proof3_visual.yaml:39`) carry the
fork's value, because they inherit the profile. They stay **byte-unchanged**: they are frozen to the
old bag and to the collected box evidence, and the replays they describe really did run that way.

## 1. The rule, read from the pinned source

- `ImuProcess::set_extrinsic(V3D transl, M3D rot)` assigns the translation straight through,
  with no negation: `Lid_offset_to_IMU = transl` (`src/IMU_Processing.cpp:85–86`, same at
  `:91–92`; the `MD(4,4)` overload at `:75–80` takes the same block).
- The deskew path consumes it as
  `P_compensate = extR_Ri * (R_i * (Lid_rot_to_IMU * P_i + Lid_offset_to_IMU) + T_ei) - exrR_extT`
  (`src/IMU_Processing.cpp:528`, with `extR_Ri`/`exrR_extT` formed at `:499–500`), i.e.

  ```
  p_imu = extrinsic_R * p_lidar + extrinsic_T
  ```

  The transformed quantity is an IMU-frame point; the state's origin is the IMU. So `extrinsic_T`
  is the **position of the LiDAR origin expressed in the IMU frame**.
- Therefore, with the IMU chip at position **o** in the LiDAR frame and parallel axes
  (`extrinsic_R = I`): `extrinsic_T = −o`. A point at the LiDAR origin has IMU coordinates `−o`.
  This is the same form the fork uses on its other path (`LIVMapper.cpp`: `p_body_imu(extR *
  p_body_lidar + extT)`).
- **The fork has no online extrinsic estimation.** `extrinsic_est_en`, present upstream in
  FAST-LIO, appears nowhere in this fork's `src/`, `include/` or `config/`. The configured value is
  hard truth; nothing corrects a wrong sign at run time.

## 2. The sensor fact, from the Livox manual

`Livox Mid-360 User Manual` (© 2024), section **IMU Data**:

> "The IMU data contains the 3-axis acceleration and 3-axis angular velocity, **the directions of
> which are the same with that of the point cloud coordinates**. The position of the IMU chip in the
> point cloud coordinates is x=11.0 mm, y=23.29 mm, z=-44.12 mm."

So **o** = (+0.011, +0.02329, −0.04412) m and the axes are parallel — the identity rotation in the
config is documented by the vendor, not an assumption. The manual's "Usage → Coordinates" section
defines `O-XYZ` as the Mid-360 point-cloud coordinates, the frame the position is stated in.

Read from the operator's local copy (`pdftotext -layout`), not from a secondary source.

## 3. Our `livox_frame` *is* that frame

The manual's numbers only transfer if our recorded points are in the sensor's own point-cloud
coordinates. Verified on the vendored driver and SDK:

- Point fields are copied through unchanged, with no remap or sign flip:
  `nav/vendor/livox_ros_driver2/src/lddc.cpp:322–324, 389–391, 447–449`.
- The driver's only transform path is the JSON's `extrinsic_parameter`; ours is all-zero
  (`nav/vendor/livox_ros_driver2/config/MID360_config.json`, the file
  `nav/robot_slam/launch/lidar_only.launch.py:11` loads).
- That zero is pushed to the device as its install attitude (`src/call_back/livox_lidar_callback.cpp:93–101`),
  so the sensor does not rotate points either.
- Livox-SDK2 has no axis remap on the point path (the only `swap` hits are `std::vector` operations).

## 4. Why the fork is the dissenter — the three-way comparison

| Source | Avia | Mid-360 |
|---|---|---|
| Publisher manual, **o** (IMU origin in the point-cloud frame) | (−41.65, −23.26, +28.40) mm | (+11.0, +23.29, −44.12) mm |
| The rule `extrinsic_T = −o` (§1) | (+0.04165, +0.02326, −0.0284) | (−0.011, −0.02329, +0.04412) |
| **Pinned fork** | (+0.04165, +0.02326, −0.0284) ✓ | (+0.011, +0.02329, −0.04412) ✗ |
| FAST-LIO (parent project) `config/avia.yaml`, `config/mid360.yaml` | (+0.04165, +0.02326, −0.0284) ✓ | (−0.011, −0.02329, +0.04412) ✓ |

The Avia manual's wording is the parallel one: "The origin O' of IMU coordinate is defined in the
point cloud coordinates as (-41.65, -23.26, 28.40) (Unit: mm)". The fork's own Avia entry follows the
rule; its Mid-360 entry does not. One file, one code path, two conventions — so one of them is a
slip. The fork's README says Mid-360 support was added later, "alongside the original Avia path", so
the newer entry is the suspect; the fork's git history is two commits (`Initial public release`,
`Update README…`), so there is no provenance trail to read.

*Provenance note: the Avia manual text above is from a published excerpt of the same manual rather
than a local file (the operator's copy is not on hand; a download attempt timed out at 1.1 MB of a
partial PDF). It corroborates; the argument does not depend on it — the Mid-360 manual, the code
rule and FAST-LIO's Mid-360 entry are all primary reads.*

## 5. Impact

1. **Mapper geometry.** The estimator places its IMU body 5.1 cm on the wrong side of the LiDAR, so
   each deskewed point and each residual is geometrically inconsistent by up to 10.2 cm (twice the
   offset). Small, systematic, and not self-correcting — see §1 on `extrinsic_est_en`.
2. **Everything already produced with the staged pair ran that way**: the T3.5a replay records and
   the T3.5c rounds. Their qualitative verdicts (the visibility stage's acceptance; the retained
   own-data FAIL) do not turn on a 5 cm sensor-internal offset, but **no absolute-geometry claim
   rests on those runs**.
3. **The integration bridge** (`T3.5f_INTEGRATION_REVIEW_20261018.html`) needs
   `robot_base_link ← aft_mapped` = mount (0.18, 0, 0.2) composed with the sensor-internal
   LiDAR→IMU offset:

   | | Translation | Magnitude |
   |---|---|---|
   | Corrected (§1 + §2) | (0.191, 0.023, 0.156) m | 0.248 m |
   | Pre-correction value | (0.169, −0.023, 0.244) m | 0.298 m |

   Rotation is identity in both. The two differ by 10.2 cm.
4. **Forward use:** the new checked config pair for the 2026-10-19 recording carries
   `extrin_calib.extrinsic_T: [-0.011, -0.02329, 0.04412]`; `check_replay_configs.py` now asserts it
   in every mode, so a future pair cannot silently inherit the old sign.

## 6. Residuals

- **Proven by reading, not measurement.** Three independent lines (the code rule, the manual, the
  parent project) plus the fork's own internal inconsistency. The single load-bearing phrase is the
  manual's "position of the IMU chip in the point cloud coordinates"; were that the transform rather
  than the origin's position, the sign would invert. The parallel Avia wording and FAST-LIO's
  agreement are what rule that out.
- **Empirical confirmation is owed and is cheap** (T3.5d, attended): with the mapper live, spin the
  robot in place through a known arc, once for each candidate constant. The bridge reconstructs
  `B̂ = I − R(θ)·d_used`, so a wrong `d_used` makes `B̂` walk a circle of radius `|d_true − d_used|`
  = 10.2 cm at the rotation frequency, while the correct one leaves it stationary. A constant
  translation error cancels only when the orientation does not change — which is why a spin, not a
  drive, is the discriminating motion.
- **Our mount rotation** (eye-estimated zero, `shared/global_config.yaml:113`) remains unverified and
  is the dominant angular term: ≈ 1.7 cm per metre per degree. Unchanged by this finding; T5.5 owns
  the measured numbers.
