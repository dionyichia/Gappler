Why

The Livox source bundles spdlog 1.3.1; ROS uses system spdlog 1.9.2. Their C++ logger objects have different binary layouts, but the SDK exports matching symbol names. The dynamic-loader trace proves the SDK's logger-disposal function binds to ROS's system implementation in the failing case, instead of its own implementation in the clean control.

The SDK creates an older-layout object, retains it in a global shared pointer, then the process-exit path disposes it through incompatible system code. Removing the logger from its registry during SDK shutdown does not release that last global reference.

What ties this to the real shutdown

The original kernel address maps to library VMA 0x3ba20, _M_dispose()+80—the exact fault instruction in both reproductions. Original signal: SIGBUS. Logger-only test signal: SIGSEGV. The original driver's core was not retained because Apport ignored the unpackaged executable, so the original complete stack is not available.

Actual SDK: the capture's sourced workspace resolves install_nav/livox_sdk2/lib/liblivox_lidar_sdk_shared.so, not the separate /usr/local/lib copy. Looking only at the generated executable's dependencies misses this dynamically loaded component dependency.
