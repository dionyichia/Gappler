# T3.5 config sweep — numeric parameters in the pinned fork's `config/*.yaml`

2026-10-19. Read-only static analysis: no mapper execution, no hardware, no bag or config
modification, no repository file changed. The sweep hunts for one defect class: **a numeric
parameter written into the wrong convention (sign, axis, unit, frame, sensor class) so the code
consumes it incorrectly** — the class of `T3.5_LIDAR_IMU_EXTRINSIC_FINDING.md`.

## Verdict

Four new defects, all in the LiDAR half of the pinned fork (`U-AMC/FAST-LIVO2-ROS2` @
`a09599a288c56b832114d7ad9e898248a4111d9e`). One of them (`F2`) is live on our own staged
replay path and falsifies a claim in `T3.5_CONSUMER_CONTRACT.md`. The prior extrinsic finding
(`F3`) is re-confirmed and unchanged. The rest of the checked parameters are consistent or have
no ground truth to check.

| # | Defect | Seat | New? |

## 3. Findings

Each entry states the value, why it is wrong, ≥2 independent evidence lines, the impact on the
T3.5 replays and on upcoming live mapping, and the checker assertion that *would* catch it
(**described, not implemented** while the sweep ran; F2's is now implemented as a note — see the
follow-up above).

### F1 — `lio.max_iterations` is read by nothing; the code reads `lio.min_iterations`

**Value.** `lio.max_iterations: 5`, present in every non-camera config (`mid360_only.yaml:66`,
`mid360_lvi.yaml:66`, `avia_only.yaml:46`, `avia_lvi.yaml:46`, `HILTI22.yaml:60`,
`MARS_LVIG.yaml:78`, `NTU_VIRAL.yaml:54`).

**Why it is wrong.** The parameter name does not match the code that consumes it. The fork
declares and reads `lio.min_iterations` and stores it into the struct field `max_iterations_`:

- `src/voxel_map.cpp:50` — `node->declare_parameter<int>("lio.min_iterations", 5);`
- `src/voxel_map.cpp:65` — `node->get_parameter("lio.min_iterations", voxel_config.max_iterations_);`
- consumed as the EKF iteration bound at `voxel_map.cpp:388, 498, 501`.

`grep -rn "lio.max_iterations" src include` returns **0 hits**. In ROS 2 an undeclared override
is silently dropped, so a key spelled `lio.max_iterations` never reaches any variable.

**Independent lines.**

1. **The fork's own code** (above): name mismatch between config and reader.
2. **The parent project**: upstream `fl2up/src/voxel_map.cpp:48` reads `"lio/max_iterations"` into
   the *same* field. The fork's ROS 2 port renamed the key to `min_iterations` in the code but kept
   `max_iterations` in the configs — a port slip, not an intentional rename.

**Impact.** No numeric change today: the config default is `5`, which equals the code default, so
`max_iterations_` is 5 either way. The cost is a **silent tuning trap** — raising
`lio.max_iterations` in a live config changes nothing. Our staged pair already avoids it (it writes
`lio.min_iterations`, `t35b_proof3_lio.yaml`).

**Proposed checker assertion.** For every config: if `lio.max_iterations` is present, report a
warning ("key is never read; the code reads `lio.min_iterations`"); require that any value under
`lio` intended as the iteration bound use the key `lio.min_iterations`.

### F2 — `preprocess.blind` is inert on the CustomMsg/AVIA path

**Value.** `preprocess.blind: 0.1` (mid360 pair), `1.0` (avia pair).

**Why it is wrong.** The AVIA handler applies its range gate against `blind_sqr`, and `blind_sqr`
is **never assigned anywhere in the fork**. It is declared uninitialized, so the gate compares
against an indeterminate value instead of `blind²`:

- `include/preprocess.h:185` — `double blind, blind_sqr;` (no initializer).
- `grep -rn "blind_sqr *=" src include` → **0 hits**. All 18 uses of `blind_sqr` (e.g.
  `preprocess.cpp:194, 227, 269, 319, 795, 814, …`) are reads.
- The constructor init-list sets only `blind` (`preprocess.cpp:18`); `Preprocess::set()`
  (`preprocess.cpp:46–52`) sets `blind = bld` and never `blind_sqr`; and `set()` is **never called**
  in the fork. The only parameter read is
  `get_parameter("preprocess.blind", p_pre->blind)` (`LIVMapper.cpp:173`) with no follow-up squaring.
- `p_pre` is `p_pre.reset(new Preprocess())` (`LIVMapper.cpp:27`); the user-provided default
  constructor leaves `blind_sqr` indeterminate (reading it is undefined behaviour).

**Independent lines.**

1. **The fork's own source and upstream**: upstream assigns the missing line —
   `fl2up/src/LIVMapper.cpp:116` — `p_pre->blind_sqr = p_pre->blind * p_pre->blind;` right after
   the parameter block. The fork dropped exactly this one line in the ROS 2 port. This both proves
   the omission is unintended and fixes the intended contract as `blind²`.
2. **The fork's own consumer documentation**: `T3.5_CONSUMER_CONTRACT.md` §2 item 6 stated the gate as
   `x²+y²+z² ≥ blind²` at `:194` and asserts "zero-range returns are dropped by any positive
   `blind`, never entering the map." That is true only if `blind_sqr = blind²` — which the code
   never establishes.

**Affected path is ours.** Our staged pair uses `preprocess.lidar_type: 1` with
`common.livox_msg_type: "livox_ros_driver2"` → CustomMsg subscription (`LIVMapper.cpp:288–302`) →
`avia_handler` (`preprocess.cpp:54–58, 99–205`) → the broken `:194` gate. The frozen pair's own
comment at `preprocess.blind` repeats the contract's claim ("dropped by the range gate
(`preprocess.cpp:194`), never entering the map") and is therefore **not established by the pinned
binary**.

**Impact.** The bag's no-return samples are `(0,0,0)` (51.84% of points, `T3.5_INPUT_FREEZE_20261017.md:54`);
`x²+y²+z² = 0 ≥ blind_sqr` keeps them for any `blind_sqr ≤ 0` and drops them for any positive
`blind_sqr`. Which happens is at the mercy of an uninitialized double, so the configured 0.1 m
gate cannot be relied on in the T3.5c replays or in live mapping. Magnitude is **deliberately
unquantified** here (read-only sweep); the cheap empirical check is in §3 F2 note below. Note that
the fork's *added* `mid360_handler` (`preprocess.cpp:750`, reached only by `lidar_type: 8`) does the
correct thing — `if (dist_sqr < blind * blind) continue;` (`:769`) — so the defect is confined to
the AVIA/CustomMsg path, which is the one our staged pair uses.

**Proposed checker assertion.** **Implemented at note level (same day):** any config carrying
`preprocess.blind` now prints `check_blind_is_inert`'s note, so the key can no longer be read as an
active gate. A stronger check would be a source check: fail if `blind_sqr` has no `=` assignment in
`src/`, or assert `blind_sqr == blind * blind` is set on the path the config's `lidar_type` selects.
As a config-level stand-in, flag any config pairing `blind > 0` with `lidar_type: 1` — not done, because
it would fail the frozen pair and the note already carries the fact.

**Empirical check — prepared, not yet run (2026-10-19).** The pinned build vs a one-line-patched
build that sets `blind_sqr = blind * blind`, same bag and pair. The observable needs no new
instrumentation: the pinned binary already prints the post-gate point count
(`[ Preprocess ] Output point number:`) once per handled message, so the control is the
already-built accepted image. Expected separation is a factor 1 / 0.4816 = 2.08 of the control
(≈ 22.3 k vs ≈ 10.8 k per scan on the T3.5b bag), with the patched image also printing the
threshold in force. Patch, build mode, prediction and falsification:
[`T3.5_F2_BLIND_SQR_PATCH.md`](T3.5_F2_BLIND_SQR_PATCH.md).

### F4 — `camera_pinhole.yaml` carries the rational model's coefficients in `cam_d0..d3`

**Value.** `camera_pinhole.yaml`:

```
cam_model: Pinhole
cam_fx: 1023.9491577148438   cam_fy: 1023.9491577148438
cam_cx: 654.52294921875      cam_cy: 346.38995361328125
cam_d0: 36.78335189819336    cam_d1: -273.5762939453125
cam_d2: 0.0005355329485610127 cam_d3: -9.484394104219973e-05
```

**Why it is wrong.** Slots `cam_d0..d3` are meant to hold plumb_bob `(k1,k2,p1,p2)`. They instead
hold the *rational* model's `k1,k2` and `p1,p2` verbatim. The same file's `fx,fy,cx,cy` are
byte-identical to `camera_rational.yaml`'s, so this is one camera described by two contradictory
models.

**Independent lines.**

1. **Exact slot identity**: `cam_d0/cam_d1 = 36.78335189819336 / -273.5762939453125 =
   camera_rational.yaml k1/k2`, and `cam_d2/cam_d3 = camera_rational.yaml p1/p2`.
2. **The rational signature inside the same file**: `camera_rational.yaml` carries the paired
   coefficients `k1≈k4` (36.783 vs 36.217), `k2≈k5` (−273.576 vs −270.246), `k3≈k6`
   (711.199 vs 701.993) — numerator/denominator partners that only the rational model pairs. Those
   partners exist only because the source camera was fitted with an 8-parameter rational model;
   no pinhole model has radial partners, so reading the numerator alone as `(k1,k2)` is a
   mis-slotting.
3. **The numbers are geometrically impossible as plumb_bob**: with `k1≈36.8` the radial scale
   `1 + k1 r² + k2 r⁴` is strongly negative and grows in magnitude across the frame, while the same
   coefficients inside the rational ratio evaluate near identity — the exact reason the rational
   form was needed.
4. **The upstream file proves what belongs there**: `fl2up/config/camera_pinhole.yaml` held
   ordinary plumb_bob coefficients (`cam_d0 −0.076160`, `cam_d1 0.123001`) for a *different*
   camera (fx≈1293, cx≈626). The fork replaced working pinhole numbers with rational ones.

**Impact.** Currently **zero** — no launch in the fork loads `camera_pinhole.yaml`
(`grep` across `launch/` = 0 hits; the mid360/avia launches load `camera_rational.yaml`). It is a
dead file whose contents would produce a folded, inverted image if it were ever wired in. No
replay or live-mapping effect today.

**Proposed checker assertion.** Over `config/camera_*.yaml`: if `cam_model: Pinhole`, fail when
`|cam_d0| > 1` or `|cam_d1| > 10` (plumb_bob radial coefficients are O(0.1)); and fail when a
Pinhole file's `cam_d0..d3` equal a RationalPolynomial file's `k1,k2,p1,p2` in the same config set.

### F5 — `common.livox_msg_type` is dead on `lidar_type: 8`, and the mid360 profile's format expectation contradicts the repository

**Value.** `common.livox_msg_type: "livox_ros_driver2"` (mid360 pair), `"livox_interfaces"`
(avia pair). With `preprocess.lidar_type: 8` (mid360) the key never applies.

**Why it is wrong.** `livox_msg_type` is declared and read **only inside the
`if (p_pre->lidar_type == AVIA)` branch**:

- `LIVMapper.cpp:288` — `if (p_pre->lidar_type == AVIA) {...}` … `:292–302` declare/read
  `common.livox_msg_type`.
- The `else` branch (`:310–312`) binds a `sensor_msgs/msg/PointCloud2` subscription with no
  message-type choice at all.

So the mid360 pair (`lidar_type: 8`) always subscribes **PointCloud2**, and its `livox_msg_type`
key is inert. That is fine *only if the driver emits PointCloud2* — but the repository's own
defaults and documentation say the opposite:

1. **The vendored Mid-360 launch ships the custom message**: 
   `nav/vendor/livox_ros_driver2/launch_ROS2/msg_MID360_launch.py:8` —
   `xfer_format = 1  # 0-Pointcloud2(PointXYZRTL), 1-customized pointcloud format`. With the stock
   driver launch, `lidar_type: 8` receives **nothing, silently**.
2. **The fork's README says the repo consumes CustomMsg**: `README.md:219–231` — "Because this repo
   uses `livox_ros_driver2`'s `CustomMsg`, edit the bag's `metadata.yaml` to point at the v2 type"
   (`livox_ros_driver/msg/CustomMsg → livox_ros_driver2/msg/CustomMsg`). The shipped mid360 profile
   contradicts the book the fork tells users to follow.

**Our position.** Our own capture used `xfer_format = 1` (CustomMsg), which is why the bag topic is
`livox_ros_driver2/msg/CustomMsg`; our owned `nav/robot_slam/launch/lidar_only.launch.py:19` forces
`xfer_format: 0` (PointCloud2) and is documented as unsuitable for replaying this bag
(`T3.5_SENSOR_CAPTURE.md:63`). Our staged pair therefore selects `lidar_type: 1` (CustomMsg path)
rather than the fork's `lidar_type: 8`.

**Impact.** Not a numeric-convention error in the value itself, but a load-bearing pairing: the
fork's mid360 profile only works against a driver emitting PointCloud2, while its own driver
default, its own README and our own bag are CustomMsg. Mixing the two yields a zero-point mapper
with no error. Live-mapping consequence: pick the driver format first, then the matching
`lidar_type` — CustomMsg ⇒ `1` (+ `livox_msg_type`), PointCloud2 ⇒ `8` (key inert).

**Proposed checker assertion.** If `preprocess.lidar_type == 8` and the config also sets
`common.livox_msg_type`, report "inert key on this path". Additionally require the bag's
`/livox/lidar` type (`CustomMsg` vs `PointCloud2`) to match the `lidar_type` the pair selects.

## 5. Unverifiable (with reasons)

No ground truth to check, or a ground truth outside the allowed set. Listed so nothing here is
mistaken for a verified pass.

- **`time_offset.img_time_offset: 1200.252661`** (same in all four mid360/avia configs). Consistent
  with an OAK device-clock offset (those configs subscribe `/oak/rgb/image_raw`), and the fork's
  online TD estimator (`td_step_cap 0.5 ms/frame`) exists precisely to reel in a large initial
  value — but the magnitude cannot be checked without the camera, and upstream's `avia.yaml` had
  `0.1`.
- **`rolling_shutter.tr_readout: 0.01101`**. The comment names a RealSense D435/D455 RGB readout,
  but the topic is an OAK camera; no camera datasheet is in the allowed ground-truth set. Its
  *semantics* (total, seconds, top-to-bottom, documented at `LIVMapper.cpp:1162` and
  `vio.cpp:1445–1446, 1590–1591`) are self-consistent.
- **`camera_pinhole.scale 0.5` (640×360) vs `camera_rational.scale 0.5625` (720×405)** for the same
  camera. Both reduce 1280×720; which internal size the loader rounds to is a vikit-internal
  question not answered from the allowed sources. (Compounded by F4.)
- **`extrin_calib.Rcl` / `Pcl` (mid360 pair)** — orthonormal (det +1) but no ground truth; T5.5 owns
  the camera–LiDAR calibration. Our staged pair copies them as a documented placeholder.
- **`lio.voxel_size`, `filter_size_surf`, `point_filter_num`, `acc_cov`/`gyr_cov`,
  `outlier_threshold`, `img_point_cov`, `patch_size`, `patch_pyrimid_level`, `inv_expo_cov`,
  `vio.*` toggles, `lio.*` layer/eigen/error/sigma constants, `pcd_save.*`, `image_save.*`,
  `publish.*`, `evo.*`, `debug.*`** — tuning constants with no external ground truth; correctness
  is a per-dataset question.
- **`imu.b_acc_cov` / `b_gyr_cov`** — not declared or read by the fork; recorded as known-inert
  (already in the checker's `KNOWN_INERT_LIO`). The fork hard-codes `0.0001`
  (`LIVMapper.cpp:246–247`), so the config's `0.001` is unused metadata.
- **`preprocess.blind: 1.0` (avia pair)** and **`lio`/`imu` covariances for HILTI22 / NTU_VIRAL /
  MARS_LVIG** — upstream-identical only; no independent ground truth for those rigs.
- **HILTI22 / NTU_VIRAL extrinsics** — upstream-identical, no independent ground truth.
- **Fork-added time-delay estimator** (`rolling_shutter.td_*`) — the TD update is a textbook
  Gauss-Newton step (`vio.cpp:1777–1792`, `dtd = −(Σ g·res)/(Σ g² + λ)` clamped to `±td_step_cap`),
  but its sign convention is not modelled against the camera here and it is disabled in our staged
  pair, so no sign claim is made.
- **Wrapper absence in `HILTI22.yaml` / `camera_fisheye_HILTI22.yaml`** — upstream-identical (the
  ROS 1 parent has no wrapper), so not a fork defect; whether the fork's ROS 2 launch can load them
  is a launch question outside this sweep.
- **Vestigial republish in the mid360/avia launches** — the `image_transport republish` targets
  `/left_camera/image` while the configs subscribe `/oak/rgb/image_raw`. Structural observation,
  not a numeric parameter.
