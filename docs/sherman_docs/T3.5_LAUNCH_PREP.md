# T3.5 navigation launch preparation

**2026-10-07. Status: PROGRESS, not mapping/localization acceptance.**
Branch `t3.5-launch-prep` is stacked on `t3.4-bringup-evidence` (`3c4038c`).
It depends on the owned LiDAR-only launch from T3.4. No PR or merge implied.

## Changes

- `[code]` Removed the Ethernet-flushing process and returned action from both
  `nav/robot_slam/launch/slam_mapping.launch.py` and `slam_localization.launch.py`.
  Interface addresses must be configured separately by the operator; no network repair is
  attempted by these launches. Existing map autosave is unchanged.
- `[code]` Those two entry points and `nav/robot_navigation/launch/navigation.launch.py`
  now include `robot_slam/launch/lidar_only.launch.py` instead of the vendor custom-message
  launch. The shared owned wrapper selects PointCloud2, 10 Hz and `livox_frame`.
- `[code]` No vendor file, package dependency, scan topic, frame, map path, calibration or
  localization algorithm was changed. `robot_navigation` already depends on `robot_slam`,
  whose CMake file already installs the launch directory.

## Verification

`[observed]` [Evidence and source hashes](../bench-runs/2026-10-07-sherman-t3.5-launch-prep.txt).
The new stdlib tests first failed for five original violations, then passed after the fix.
They check absence of network-mutation strings/actions, owned LiDAR inclusion and that
the LiDAR action is actually returned, not merely constructed. An injected omitted-action
mutation was caught. Mac quick bench passed available levels, with explicit skips.

On the box, static checks, contract extractor/check and launch-construction checks passed.
The latter use temporary **source-backed package shares** (ament index entries pointing to
the candidate source), resolving external packages from the existing installed overlay.
All three descriptions and include paths were constructed, with the returned LiDAR action
verified. The owned wrapper's parameters and installed MID-360 config path were inspected.
No launch service, node action or subprocess action was executed. The temporary index is
removed and its environment override restored after the test.

This is not a build/install/deployment test. The original box checkout and installed overlay
remain unchanged, so the installed full launches still have their previous behavior.
The previous separate-checkout preflight weight gaps remain unresolved. No full-stack or
hardware PASS is claimed. Ethernet addresses and the user-started communications node were
preserved; no base, LiDAR or autonomy driver was launched for these checks.

## Re-run (no hardware actions)

From the candidate checkout root:

```bash
python3 bench/test_navigation_launches.py
source nav/nav_env.sh
python3 bench/test_navigation_launches.py --runtime
```

Use an existing approved nav overlay for external package lookup. Runtime means real ROS
launch-description construction, not running the launch. Never substitute a full `ros2 launch`
command for this check: all three full entry points still include base bring-up and navigation.
