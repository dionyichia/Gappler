# T3.5 minimal manual-control runbook

**2026-10-07, `t3.5-launch-prep`. Status: PROGRESS. UNVALIDATED procedure, no hardware
run has used it.** Candidate source only; not installed/deployed. This is the pending-lab-work
procedure called for in the [attended handoff outline](T3.4_REMOTE_CHECKS.md) (T3.4 "Next
attended session" table) and the [map-prep residuals](T3.5_MAP_PREP.md) ("minimal manual-driving
runbook remain[s] before-visit work"). It prescribes no motor-enable or drive command text:
enabling commands are agreed with the lab operator at the machine, after readiness and the
physical-stop procedure are established.

## Hard rules (read first)

1. **Arm driver off.** Never launch `grasp_state_machine`,
   `launchers/start_camera_arm_sam3_grasp.py`, `launchers/grasp_orchestrator.py` or root
   `main.py` during manual base tests. The state machine homes the arm within seconds,
   unprompted ([ORIENTATION §8.1](../ORIENTATION.md#81--the-arm-moves-within-seconds-of-launch-unprompted-code-reported),
   root `CLAUDE.md` safety rules). T6 verifies no `rm_driver` node or `/rm_driver/*` topic
   exists before every maneuver block.
2. **No Nav2 goals during manual tests.** No publishes to `/goal_pose`, `/manipulation/*`,
   `/manipulator/*` or `/object_centroid_2d` on the lab domain. The Nav2 stack (planner,
   controller, behavior servers) stays down; the only motion source is the keyboard path below.
3. **The software 1.0 s silence-to-zero bound is NOT a physical stopping criterion.** `[code]`
   The tested stack zeroes *messages* within 1.0 s of input loss (0.457-0.603 s observed,
   [T3.4 remote checks](T3.4_REMOTE_CHECKS.md#bounds-and-failure-meaning)); those are
   message-level limits, not braking guarantees. Physical stopping is proven only by the
   dedicated physical-stop exercise with an operator at a verified stop.
4. **No process-kill or network-loss experiments on moving hardware.** Killing teleop was tested
   only in an isolated domain with the smoother still alive; killing the smoother, network
   failure and the chassis watchdog remain unverified ([T3.4 bounds](T3.4_REMOTE_CHECKS.md#bounds-and-failure-meaning)).
   Never reproduce those conditions on a moving base.
5. **Stop advancing on any gate failure.** A failed ownership check, wrong parameter, odometry
   sign mismatch, or missed zero is a halt: record it, resolve it, re-run the gate. Never skip
   forward to the next maneuver.

## Terminals T1-T6

Six labelled terminals, one job each. Open in order; each terminal's gate must pass before the
next terminal starts anything.

| Terminal | Purpose | Runs | Gate before next |
|---|---|---|---|
| T1 | Preflight + LiDAR-only observation | Shell; LiDAR-only launch observation only | No competing camera/LiDAR/bench users; PointCloud2 type, ~10 Hz live data |
| T2 | Comms/status + physical-stop readiness | Shell; chassis status reads | Battery/charging confirmed, operator assigned at verified physical stop, transport posture and clearance confirmed, arm driver confirmed absent |
| T3 | Attended base driver | Base driver launch (explicit operator approval) | Driver up, no autonomy; command-topic ownership verified (see below) |
| T4 | Velocity smoother | `velocity_smoother` with tested bounds | Live parameters match tested bounds; exactly one publisher on the driver's command topic, and it is the smoother |
| T5 | Keyboard teleop (only command source) | `simple_teleop` keyboard node | W/S/A/D observed against physical directions; record sheet entries for every maneuver |
| T6 | Recorder / odometry observer | `ros2 topic` reads + record sheet only; **never publishes** | Independent observation of `/odom`, command topics and timing for every row |

T1 detail `[code]`: follow the T3.4 outline row (no competing users; PointCloud2 at ~10 Hz,
see [T3.4 remote checks](T3.4_REMOTE_CHECKS.md#next-attended-session-unvalidated-acceptance-outline)).
No base, arm, autonomy or RViz process starts here.

T2 detail: establish chassis readiness and physical-stop function; hub heartbeat alone is
insufficient (T3.4 outline). Confirm the correct charger and clear any low-battery flag
(T3.4 remains PROGRESS partly on battery/charging). Confirm nobody else's driver is running:
read-only `ps` check per root `CLAUDE.md`; never stop a process you did not start.

T3 detail `[code]`: the real driver is `xnode_vehicle` (`xpkg_vehicle`), which subscribes
`/cmd_vel` (`nav/vendor/drivers/xpkg_vehicle/src/ROS_INF/ros2_interface.cpp:177`) and
publishes `/odom` with `child_frame_id = robot_base_link` ([ORIENTATION §8.7](../ORIENTATION.md)).
Note `xpkg_power`'s `xnode_power` also publishes `/cmd_vel`
(`nav/vendor/drivers/xpkg_power/src/ROS_INF/ros2_interface.cpp:154`): if it is running, its
publisher is a second command source and T3 does not proceed until ownership is resolved.

T4 detail `[code]`: the tested smoother runs at 20 Hz with max +/-0.05 m/s and +/-0.15 rad/s,
accel 0.1 m/s² and 0.3 rad/s², decel magnitudes 0.2 and 0.6, and 0.25 s stale-input timeout
([T3.4 bounds](T3.4_REMOTE_CHECKS.md#bounds-and-failure-meaning)). **The committed
`nav2_params.yaml` defaults are wider** (max 0.3 m/s and 1.0 rad/s,
`nav/robot_slam/config/nav2_params.yaml:190-203`): T4 must set and then verify the live
parameters match the tested bounds. Keyboard raw input stays separate from final base input;
no keyboard bypass.

T5 detail `[code]`: `nav/simple_teleop/simple_teleop/teleop_node.py` publishes `cmd_vel` at
10 Hz (`teleop_node.py:35-36`), defaults 0.05 m/s and 0.15 rad/s with 0.25 s key timeout
(`teleop_node.py:40-42`). Movement needs repeated W/S/A/D events; 0.25 s silence requests
zero; X requests zero; Q / Ctrl+C / SIGINT exit and restore the terminal
(`teleop_node.py:62-88,106-134`). Unknown keys do not renew movement. Initial key-repeat
delay may cause a pause; this is not a true hold-to-run switch.

T6 detail: T6 is the scribe and the independent check. It subscribes/echoes only. Every record
sheet row needs a T6 witness (requested vs actual direction, odometry sign, timing).

## Single command path and ownership checks

The only permitted motion path:

```
T5 keyboard (simple_teleop, raw cmd_vel @10 Hz)
  -> T4 velocity_smoother (input cmd_vel, output cmd_vel_smoothed @20 Hz, tested bounds)
  -> T3 base driver (xnode_vehicle, consumes smoothed output)
```

`[code]` The tested wiring convention is input `cmd_vel`, output `cmd_vel_smoothed`
(`bench/nodes/test_velocity_smoother.py:85`, remapped to private topics in the bench). At the
machine, verify how the driver's subscription is actually fed (remap or relay) and record the
exact topic names. The invariant, whatever the names: **exactly one publisher on the topic the
driver reads, and it is the smoother; the keyboard never publishes to it directly.**

Run these from T6 (all read-only) after T3/T4/T5 are up and before the first maneuver, and
re-run after any restart:

```bash
ros2 node list
ros2 topic info /cmd_vel -v
ros2 topic info /cmd_vel_smoothed -v
ros2 node info /simple_teleop
ros2 node info /velocity_smoother
ros2 topic hz /odom
ros2 topic echo /odom --once
```

Accept only if ALL hold:

- Publisher list on the keyboard's raw topic contains only the keyboard node; publisher list
  on the driver's command topic contains only the smoother (count 1 each, names recorded).
- `ros2 param get /velocity_smoother max_velocity` (and accel/decel/timeout) match the tested
  bounds above, not the wider file defaults (that committed `velocity_smoother`
 block is not consumed by any launch — verified 2026-10-07 — so T4 always sets
 live parameters explicitly and verifies them).
- `/odom` flows with the expected frame (`robot_base_link` child).
- `ros2 node list` shows no `rm_driver`, state-machine, orchestrator, Nav2 planner/controller,
  or second teleop node; `ros2 topic list | grep -E 'rm_driver|goal_pose|manipulation'` is empty.
- No `xnode_power` `/cmd_vel` publisher unless its test mode is confirmed off and its
  publisher is absent from the graph.

Record the full `ros2 topic info -v` outputs with the record sheet. Any extra publisher,
wrong parameter, or missing topic is a gate failure: halt per hard rule 5.

## Per-maneuver record sheet

Copy one row per maneuver. T5 drives, T6 witnesses and times. Timing method: T6 notes wall
time of the key event (called out by T5) and reads the first changed/stopped message time
from `ros2 topic echo /cmd_vel_smoothed` and `/odom`; short `ros2 topic hz` samples back it up.

| # | Maneuver (key) | Requested (lin.x / ang.z) | Actual physical direction | Odom sign agrees? | Request-to-motion | Release-to-zero-msg (<=1.0 s) | Pass? |
|---|---|---|---|---|---|---|---|
| 1 | Forward (W) | +0.05 / 0 | | | | n/a (held) | |
| 2 | Reverse (S) | -0.05 / 0 | | | | n/a (held) | |
| 3 | Left (A) | 0 / +0.15 | | | | n/a (held) | |
| 4 | Right (D) | 0 / -0.15 | | | | n/a (held) | |
| 5 | Silence (no key, >0.25 s) | 0 / 0 requested by timeout | base must show no new drive intent | | n/a | msg zero time: ___ s | |
| 6 | Stop (X) | 0 / 0 | | n/a | n/a | msg zero time: ___ s | |
| 7 | Exit (Q) | exit + final zero requested, terminal restored | | n/a | n/a | final zero published? Y/N | |
| 8 | Physical stop (hardware) | n/a (independent stop) | base halted by stop device | n/a | operator call-to-halt time | halt time: ___ s | |

Notes for the sheet:

- Rows 1-4: confirm each key's physical direction matches the request (forward means the base
  moves forward, left means it yaws left). Any reversal or wrong axis is a gate failure.
- Rows 5-6 prove *message* zeros only. They say nothing about braking distance; that is row 8.
- Row 7: after Q, T6 confirms the terminal is restored and the graph shows the keyboard node
  gone. Ctrl+C is not a hardware stop.
- Row 8: separate exercise with the assigned operator at the verified physical stop, agreed
  stopping criteria, and operator present (T3.4 outline). Record the criterion used and the
  measured halt, not just "it stopped".

## Stop criteria and gate rules

Advance maneuver-to-maneuver only while every row passes. Halt the session (no further motion)
if any of these occur:

- Any ownership-check invariant fails (extra/missing publisher, wrong smoother parameter,
  unexpected node or goal topic).
- Any row's actual direction disagrees with requested, or odometry sign disagrees.
- Any silence/X zero message arrives later than 1.0 s after input loss.
- Battery warning, new personnel in the cell, clearance lost, or physical-stop operator leaves
  post.
- Anything unplanned moves or publishes (stray node, replayed bag, second teleop).

On a halt: T5 issues X then Q, T4/T3 stay up only if the operator agrees they are still safe,
T6 records what failed with command outputs, and nothing moves again until the cause is found
and the full ownership check re-passes. A halted session resumes at T6 re-verification, never
mid-sheet.

## Shutdown and custody checklist

1. T5: press X, then Q; T6 confirms final zero published and the keyboard node left the graph.
2. T4: stop the smoother; T6 confirms the driver's command topic has no publishers.
3. T3: stop the base driver using the verified hardware-stop/power procedure agreed with the
   operator (this runbook does not define that procedure; it must come from the attended
   session's readiness work).
4. T6: `ros2 node list` and `ros2 topic list` show none of your nodes/topics; read-only `ps`
   check shows none of your processes. Only stop processes your group started (own process
   group; root `CLAUDE.md` shared-box rule).
5. T2/T1: record battery/charger state and who holds custody of the machine and charger.
6. File the completed record sheet (this doc's table, filled) plus the saved `topic info -v`
   outputs as session evidence; link from `WORK_LOG.md`.
