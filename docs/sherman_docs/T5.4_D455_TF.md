## Objective

Determine the transform chain from `robot_base_link` to the D455 optical frames
and make fixed mounting geometry single-sourced. At the opening CAD-only session,
physical placement was unknown and no live TF publisher was created. After T5.3
fit and the 2026-10-06 measurements, the branch added an opt-in camera TF chain
and camera-referenced navigation. CAD-only numbers were not deployed as mounts.

The vendor model's `rw_Joint` / `lw_Joint` origins are
`(0, ±0.13379, 0.065) m` relative to `robot_base_link`
(`nav/vendor/urdf/xpkg_urdf_echo_plus/urdf/model.urdf:90-94,143-147`). With the
reported axle height 65 mm and axle aligned to the measured chassis midpoint,
the model origin is at floor height: `65 − 65 = 0 mm`.

Therefore the **provisional parent-to-bottom-screw transform** is:

```text
robot_base_link → D455 bottom mounting-screw frame
x = 195 + 13 = 208 mm
y = 0 mm
z = 558 − 30 − (65 − 65) = 528 mm
xyz = (0.208, 0, 0.528) m
rpy = (0, 0, 0) rad  [visual estimate only]
```

This is not `camera_link` or an optical-frame transform. Apply the package's
socket-to-sensor chain separately, after confirming the installed package and
frame naming. The measurement-recording step alone changed no runtime TF;
the later integration below now publishes this provisional mount when explicitly
launched. Geometry accuracy and alignment are not calibrated; T5.5 camera–LiDAR
calibration remains separate.

## Package facts `[code]` (`realsense2_description/urdf/_d455.urdf.xacro`, IntelRealSense/realsense-ros)

- Origin = bottom screw mount: user `<origin>` attaches parent → `bottom_screw_frame`.
  **Correction verified against the installed package 2026-10-06:**
  `camera_link` offset is (+0.01115, +0.0475, +0.0145) m, not +0.0158 on x.
  The model's x expression subtracts glass/depth-plane offsets:
  `0.0158 − 0.0001 − 0.00455 = 0.01115 m`. The installed xacro is used directly.
- Body 0.124 × 0.029 × 0.026 m; nominal sensor offsets off `camera_link`:
  depth +0, right-IR y −0.095 (95 mm baseline), color y −0.059; IMU at
  (−0.01602, −0.03022, +0.0074).
- Optical frames hang off each sensor via fixed `rpy(−π/2, 0, −π/2)` (axis
  convention flip, never measured).
- Header comment: values approximate; the driver overwrites fine extrinsics live
  from factory calibration. Depth start plane: datasheet Rev 009, Fig 4-4
  (`zero_depth_to_glass` 4.55 mm).
- Responsibility split: user tapes mount→socket; Intel owns socket→sensors;
  driver owns live fine extrinsics.

## D455 sensor-frame integration, 2026-10-06

`nav/robot_slam/launch/base_camera.launch.py` starts only the D455 and a mount
`robot_state_publisher`. It uses the serial in shared config (146222253541),
derives camera name `base_d455` from the configured screw-frame name, and expands
`nav/robot_slam/urdf/base_d455.urdf.xacro` using the measured xyz/rpy.

The xacro includes the installed Intel `_d455.urdf.xacro` with
`use_nominal_extrinsics=false`. Ownership is:

```text
robot_base_link
  → base_d455_bottom_screw_frame   mount publisher, measured config
  → base_d455_link                 mount publisher, Intel body geometry
  → base_d455_depth/color_frame    RealSense driver, factory extrinsics
  → base_d455_*_optical_frame      RealSense driver, optical-axis rotation
```

Topics are `/base_camera/base_d455/color/image_raw` and
`/base_camera/base_d455/depth/image_rect_raw`. These names differ from the earlier
temporary preview's `/base_camera/d455/...` topics. Namespacing alone does not
prefix TF frames; `camera_name=base_d455` is what gives this driver distinct names.

## Navigation-reference decision and implementation, 2026-10-06

Sherman explicitly confirmed **both object approach and return-to-user reference
the new base-mounted D455**. The chosen reference is its depth optical-frame
origin, derived from the configured camera-frame prefix by
`gappler_common.camera_reference_frame()`. This is a position reference, not a
copy of the old 180 mm scalar. Arm and LiDAR geometry remain unchanged.

Object approach looks up both map-to-camera and base-to-camera transforms.
Return-to-user looks up base-to-camera. Neither falls back to 180 mm if TF is
missing. Approach emits no goal/start when its camera TF is missing; return
refuses the goal without setting its returning flag, allowing retry when TF
becomes available. The obsolete legacy config scalars are removed.

Distances remain **horizontal planar clearances**: approach 0.6 m, return 0.5 m.
They are not 3D Euclidean distances, collision envelopes or robot-front gaps.
The shared, stdlib-only `nav_geometry.camera_goal_xy` accounts for both forward
and lateral camera position. For target `t`, desired robot heading `yaw`, and
base-frame camera origin `(cx, cy)`, it computes:

```text
base_goal = target − R(yaw) × (cx + clearance, cy)
camera_at_goal = base_goal + R(yaw) × (cx, cy)
              = target − clearance × (cos(yaw), sin(yaw))
```

Thus camera-to-target planar distance is exactly the requested clearance,
including Intel's lateral sensor offset; the robot base need not lie on the
camera-to-target line. Approach selects heading from the current camera toward
the object. Return preserves the opposing-to-user heading, compensating camera
offsets in that orientation. Optical-frame rotation is not used as a base yaw.

Pure tests cover approach/return distances, rotated headings, lateral offsets
and refusal of nonfinite/invalid geometry. Mock-nav fixtures deliberately use
camera offsets different from the measured values, proving nodes consume TF
rather than another copied scalar. Known F1/F2/E1 defects remain separate.
Arrival also requires both base-to-camera and map-to-camera TF before emitting
`/manipulation/start`; a pure regression checks map TF loss after a valid goal.
This is a geometry/readiness gate, not certification of grasp safety.

### Availability is not freshness or sensing readiness

The lookups request the latest available transform (`Time()`), without a
timestamp-age limit. TF can retain a cached dynamic transform or a static camera
mount after its publisher stops. Lookup success therefore proves a usable frame
chain, not a currently running camera, fresh images or fresh localisation.
Missing-TF tests exercise lookup refusal; they do not prove detection of a dead
publisher whose transforms remain cached.

Arrival still trusts the navigation success message rather than independently
checking final camera clearance. Existing glasses-pose frame handling and Nav2
failure-recovery defects (E1/F1/F2) remain outside this geometry change. These
limits must be retained in the PR; no physical navigation/grasp safety claim is
supported by the new guards.
