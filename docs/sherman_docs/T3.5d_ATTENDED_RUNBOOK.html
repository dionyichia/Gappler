4. Acceptance — stationary first, then hand-operated mapping

Two ordered stages. The first is a precondition for the second, and a stationary pass never stands in for the moving one.

4.1 Stationary initialisation (must succeed before any motion)

4.2 Hand-operated mapping (no autonomous motion)

Offline or stationary success does not prove moving-map quality. A replay PASS, a stationary initialisation, and a quiet map while nothing moves are all compatible with a bad moving run — the deskew path is inert when stationary and its assumptions are unproven in motion. The only evidence for moving-map quality is the hand-driven run itself, and even then no absolute-geometry claim rests on it: every run carrying the sensor-internal intrinsic inconsistency is bounded against absolute accuracy until T5.5 measures the real numbers. T3.5d accepts a coherent recorded map and trajectory, not accuracy.

5. The in-place spin test — the empirical discriminator for the LiDAR→IMU sign

Purpose. The pinned fork's Mid-360 extrin_calib.extrinsic_T is the Livox manual's IMU-position numbers unnegated, while the fork's own code applies them verbatim (p_imu = R · p_lidar + T) where their negation is required, and it never estimates the extrinsic online. The correction [-0.011, -0.02329, 0.04412]/identity rests on the vendor manual, the code rule and the parent project — documented, not measured on our unit. A translation error along the sensor's own axes cancels while the orientation never changes, so only a rotation exposes it: a spin, not a drive, is the discriminating motion. This test is the acceptance test for the correction.

How to read it. The bridge reconstructs the base position from the composed transform. With a wrong body constant the reconstructed base position walks a ~10.2 cm circle at the rotation frequency (the error is twice the 5.1 cm sensor offset, swept by the rotation); with the correct constant it holds still through the spin.

OutcomeMeaning
Corrected-value pass holds still; pre-correction pass walks the circleThe sign correction is confirmed empirically on our unit. The corrected value stands as the session's working constant; the mount rotation residual in §8 is unchanged and still unverified.
Pre-correction pass holds still; corrected pass walksThe finding is contradicted for our unit — stop and investigate. Do not "fix" it by editing the constant to force a pass (§7): preserve both runs and escalate to the measurement owner.
Both walk, or both hold stillThe test is inconclusive (wrong motion, unlogged arc, stale odometry, two map → odom publishers). Stop and investigate; do not tune to make it discriminate.

6. Pose-rate adequacy — the ~10 Hz measurement

The mapper publishes /aft_mapped_to_init once per LiDAR frame, so its rate is nominally ≈10 Hz. The integration boundary for Nav2 is decision 4 of the wiring review: measure on the box before touching transform_tolerance; a repeat-timer or interpolation is the fallback, not the default. No measured live rate exists yet — that is what this section records.

7. Stop conditions — stop and investigate, never tune

Any trigger below ends the stage. Preserve the evidence, stop the processes, and investigate off the robot. Never adjust an extrinsic, a threshold, a scene or a config to turn a failing run into a passing one — a changed input means a new run, recorded as such.

Stop ifAction
Initialisation fails — the mapper never converges, or the parameter_blackboard camera load fails.Stop the stage; keep logs; check the parameter server ordering and the overlay sourcing (§2). Do not retry blindly.
Invalid outputs — any invalid odometry, malformed or point-less registered clouds in a visual run (empty clouds in a diagnostic run are the source-observed heartbeat and are never a stop on their own), wrong frame names, non-zero invalid-output count.Stop; preserve the topic snapshot and mapper log; investigate.
Stalls — LiDAR, IMU, image or odometry stops advancing, or the mapper falls behind its inputs.Stop; capture the stall window; investigate the source of the hold-up.
Absent visual updates — a visual run produces no sustained visual updates / empty corrected visual map.Stop and investigate. Do not swap to the diagnostic config and call it a pass — a LiDAR-inertial-only run is a different claim.
Shutdown crashes — a mapper teardown crash or non-zero exit at stop (the pinned fork's destructor crash is a known open item).Stop; record the exact teardown backtrace and exit codes; investigate. A crashed teardown is not a clean shutdown.
Two publishers of one TF edge — the bridge and SLAM Toolbox, or two map → odom writers, are ever live together.Stop immediately; kill this session's own groups; investigate the launch overlap.

8. The bridge body constant and the residual term

The bridge's robot_base_link ← aft_mapped constant is the mount robot_base_link → livox_frame (0.18, 0, 0.2) composed with the sensor-internal LiDAR→IMU offset:

TranslationMagnitudeRotation
Used this session (corrected)(0.191, 0.023, 0.156) m≈ 0.248 midentity
Pre-correction (spin-test contrast only)(0.169, -0.023, 0.244) m≈ 0.298 midentity

Residual, unverified. The composition uses our own mount translation (0.18, 0, 0.2) with a mount rotation that is currently eye-estimated zeros. That rotation is the dominant angular term (≈ 1.7 cm per metre per degree) and is not measured here — T5.5 owns the real numbers. The spin test in §5 discriminates the translation sign only; it does not measure the mount rotation. The identity in the sensor-internal offset is a vendor-documented fact, not our measurement.
