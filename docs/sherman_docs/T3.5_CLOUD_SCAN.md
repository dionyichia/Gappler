# T3.5 synthetic point-cloud to scan check

**2026-10-07. Scope:** isolated software geometry, not live sensor or navigation acceptance.
Branch `t3.5-launch-prep`, stacked on T3.4. No production navigation code changed for this check.

`[observed]` [Reviewed box evidence](../bench-runs/2026-10-07-sherman-t3.5-cloud-scan.txt):
all 12 cases passed with 10/10 distinct scan frames; final private domain empty.
Five stdlib checks and the Mac quick bench passed available checks, with explicit skips.

## What it exercises

`bench/cloud_scan.sh` starts only the owned QoS relay and the installed
`pointcloud_to_laserscan_node`, plus the test publisher/recorders. Fixed domain 127,
localhost-only and the existing fail-closed empty-graph guard separate this from hardware.
All data topics are under `/t35_scan/`. Cleanup targets owned process groups only.

Converter parameters and routes are read from candidate launch source, not copied into fixtures.
The check also requires the converter and any selected relay to be returned launch actions:

| Profile | Tested route | Height / range limits |
|---|---|---|
| `slam_mapping` | Synthetic cloud → relay → converter | Existing mapping launch parameters |
| `slam_localization` | Synthetic cloud → relay → converter | Existing localization launch parameters |
| `navigation` | Synthetic cloud → converter directly | Existing AMCL entry-point parameters |

The direct route is intentional: that is how the current AMCL launch connects its converter.
The relay remains separately observed in that case. No route/configuration was changed.

## Cases and assertions

- **Known geometry:** front/left/right/angled points, including near/far points in one beam.
  The nearest valid horizontal range must occupy the expected angular bin.
- **Bounds:** points just inside/outside the configured height and range limits.
- **Invalid-only:** NaN XYZ components, infinite X, and out-of-height points.
- **Empty:** a valid cloud schema with no points; no finite scan obstacles expected.

Fixtures use the existing bench's 26-byte little-endian Livox-like layout with XYZ and
extra fields. The geometric oracle uses the actual float32-encoded XYZ, not unrounded input.
Checks cover relay RELIABLE input/BEST_EFFORT output, full message preservation, scan frame/timestamps,
angle/range metadata, expected bin count, nearest ranges and positive infinity for empty bins.
Ten small frames per case are sent at approximately 0.1-second intervals; at least nine
distinct matching cloud/scan frames must arrive; duplicates are rejected. This is a small-fixture
delivery check, not a load test. Runtime endpoints expose reliability/durability, but this box's
DDS discovery reports history/depth as UNKNOWN/0. KEEP_LAST/depth 10 are therefore checked
in the source declarations and their constructor use, not claimed as runtime-observed.

## Re-run remotely

From an approved candidate checkout root, with no other bench/CI job running:

```bash
python3 bench/test_cloud_scan.py
bash bench/cloud_scan.sh
```

The shell runner sources ROS and the candidate helper; no new build or sensor overlay is
needed. Do not run concurrently with the keyboard/smoother bench: both reserve domain 127.
Exit 0 is PASS, 1 is failure/refusal, 3 is dependency SKIPPED. Logs are `log/t35-relay.log`
and `log/t35-<profile>.log`; capture runner output for the per-case delivery counts.
Timeout allows 30 s shutdown grace for escalation of the two owned child process groups.

## Limits of proof

Input and target frames both equal `livox_frame`, so no physical TF alignment is tested.
The cloud layout is synthetic, not a captured or independently verified live driver frame.
This does not prove sensor calibration, full LiDAR-rate throughput, scan freshness after
sensor failure, map quality, obstacle avoidance, navigation or physical stopping.
Original checkout, installed overlay and hardware-facing processes are unchanged.
T3.4 and T3.5 remain PROGRESS; see [launch preparation](T3.5_LAUNCH_PREP.md).
