Connecting FAST-LIVO2 to the current robot

What this is: the wiring review requested while T3.5c waits for the 19 October recording. What it is not: an implementation, a claim that FAST-LIVO2 can drive Nav2, or a task-tree change. T3.5f still sits behind T3.5c → T3.5d → T3.5e. Two facts are new and were previously unrecorded: the mapper's real frame names (read from the pinned source, §2), and the one Nav2 input FAST-LIVO2 cannot supply at all (§6). Revision (2026-10-18): the body constant this review first took from the fork's Mid-360 profile was wrong by a sign — the corrected value is (0.191, 0.023, 0.156) m, rotation identity. §4, decision 5, the file-change table and the ledger row below carry the correction; the evidence is T3.5_LIDAR_IMU_EXTRINSIC_FINDING.md. Everything else is unchanged.

1. Verdict in four lines

  1. Do not touch the TF tree. The mapper's world frame is camera_init and its body frame is aft_mapped — not map and not body. One small new node translates; every existing consumer keeps the frame names it already hardcodes (map, odom, robot_base_link).
  2. The bridge should own map → odom, the edge SLAM Toolbox owns today — and only one of them may ever run. The base driver keeps odom → robot_base_link; the local costmap stays in odom and keeps eating /scan from the raw cloud, unchanged.
  3. Nav2 needs a 2D occupancy grid (/map) that FAST-LIVO2 does not produce. It saves a 3D point cloud. That is the one genuine hole in this integration (§6).
  4. The mapper also has no map load, so T3.5e's restart-localisation premise is real: the pinned fork only saves a pcd (pcd_save.pcd_save_en); nothing reads one back. [code]

4. Proposed wiring

Why map → odom and not the alternatives:

OptionWhat changesVerdict
Bridge owns map → odomone new node, one launch argument, CHANNEL_CONTRACT rowrecommended — Nav2 params, costmap frames, goal frames and every consumer are untouched
Bridge owns odom → robot_base_link, mapper owns map → odomdriver pub_tf:=false, Nav2 local costmap moved to map, /odom disagrees with TFrejected — the local costmap would jump whenever the correction updates, and two topics would carry different poses
Make camera_init the map frame by renaming consumersobject_approach, goto_glasses, pose_publisher, Nav2 params, contracts baselinerejected — churn with no gain; the rename is done once, inside the bridge
Keep SLAM Toolbox for pose, mapper only for the cloudnothingthat is today; it does not test FAST-LIVO2 pose at all

One offset the bridge needs — corrected 2026-10-18. The mapper's pose is the IMU body pose, so aft_mapped ≈ livox_frame plus the sensor's internal LiDAR→IMU offset: the robot_base_link → livox_frame mount (0.18, 0, 0.2) composed with the mapper's LiDAR→IMU extrinsic. The pin's Mid-360 value [0.011, 0.02329, −0.04412] is the Livox manual's IMU-position numbers unnegated, and the fork's own code needs the negation — so the bridge constant is (0.191, 0.023, 0.156) m, rotation identity, |·| ≈ 0.248 m, not the earlier (0.169, −0.023, 0.244) m. The sensor's axes are documented as parallel to its point-cloud frame, so identity rotation is a vendor fact rather than an assumption; the fork has no online extrinsic estimation, so a wrong sign is never corrected at runtime. Full evidence, and the in-place spin test that decides the sign empirically: T3.5_LIDAR_IMU_EXTRINSIC_FINDING.md. Recommendation unchanged: add one geometry entry (a static livox_frame → aft_mapped) so the number is single-sourced, and check it with the same overlay that gates the T3.5c recording.

6. The input Nav2 needs and FAST-LIVO2 does not have

[code] nav/robot_slam/config/nav2_params.yaml:121–124 gives global_costmap a static_layer that subscribes to /map (nav_msgs/OccupancyGrid, transient-local). FAST-LIVO2 publishes 3D point clouds and saves a .pcd; it never produces a 2D occupancy grid. So the global plan has no map to plan on unless something makes one.

OptionHowCost / risk
(a) Offline 2D map build, reused liveduring T3.5d, or on the recorded bag, run SLAM Toolbox mapping offline (it already autosaves every 30 s, slam_mapping.launch.py:26–35) and feed the resulting .pgm/.yaml to nav2_map_server livelowest risk — no new runtime node, one offline step, map is a frozen artifact
(b) Cloud → grid projection nodenew node: project /cloud_registered into 2D and publish /mapmedium — new runtime code, occupancy semantics (free/unknown) are ours to get wrong
(c) Voxel/STVL plugin over the registered cloudswap static_layer for a 3D-layer pluginreplaces the global planner's world model; far beyond T3.5f

Obstacles, in contrast, need nothing. The local costmap keeps /scan from the raw Livox cloud via qos_relay → pointcloud_to_laserscan (nav2_params.yaml:94–104), all in livox_frame. That is correct here: the local costmap lives in odom, and /cloud_registered is in camera_init, so feeding the registered cloud in would mix a corrected world frame into a local frame — a real bug, avoided by leaving it alone.

7. What the bench will say

  • Breaks if we restructure instead of parameterise: bench/test_slam_maps.py:110–136 asserts the localisation launch's first statement is require_serialized_map, that the pose/manifest gates are called, and that there is exactly one map_start_pose. A launch argument keeps all three; a rewritten file does not.
  • Will flag new wiring: L1 bench/contracts.py errors ORPHAN ADDED on any half-wired topic — so the bridge must really subscribe to /aft_mapped_to_init and really publish the TF, not describe it in config.
  • L0 launch-packages/launch-executables (bench/static.py): any package or executable named in a launch must exist in-repo or be in KNOWN_EXTERNAL. If the mapper runs from a container, the launch names no mapper package — one less line to edit.
  • Must be added for T3.5f to be covered at all: an L4-style case that stands up a mapper-shaped TF (camera_init → aft_mapped at 10 Hz) and asserts the bridge produces map → robot_base_link within tolerance, and that it refuses to publish when odometry goes stale. The template is the existing robot pose case, bench/nodes/test_nav_nodes.py:512–526.
