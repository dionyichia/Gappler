# T6.3 walkthrough: from one photo to objects in the room

**What this is.** A plain-language guide to what the T6.3 code does, step by step, with one real
example (the chair in frame 700 of the lab recording). Each step points at the code that does it,
so you can open the file and read along. Written 2026-10-21, on branch `t6.3-end-to-end-photo`.
Owner: Zongzhe.

Read this before [`quizzes/T6.3_QUIZ.md`](quizzes/T6.3_QUIZ.md). The quiz asks about corner cases
of these steps.

## The goal

The robot drives around the lab with a camera and a LiDAR. We want a list of the objects it saw,
with where each one is: "a chair here, a sofa there". That list is the robot's memory of the room.

T6.3 is the first time the whole chain ran on a real lab recording, start to finish.

## The recording

A bag file from the lab, recorded 2026-10-20 with FAST-LIVO (a program that tracks where the
sensors are while they move). It holds:

- colour photos, 640 x 480 pixels,
- LiDAR scans: millions of 3D points, already placed in the room's coordinates,
- the camera's position and direction for each moment.

It has **no depth image**: no photo where each pixel says how far away it is. Step 1 makes one.
The facts about the bag are in [`NOTE_fastlivo_bag_facts.md`](NOTE_fastlivo_bag_facts.md).

## The steps, one photo at a time

The code numbers the steps S0 to S11, following HiCo-Nav. They are given here in brackets.

### Step 1. Get a photo with depth (S0)

**What happens.** The loader takes the LiDAR points around the moment the photo was taken and
works out which pixel of the photo each point lands on, and how far it is from the camera. The
result is a depth image: a photo where some pixels, about 13 percent, also know their distance.
Where two points land on the same pixel, the nearer one wins.

**Where.** `FastLivoBag.observation` ([`replay_loader.py:393`](../../memory_graph/replay_loader.py))
calls `project_cloud_to_depth` ([`geometry.py:54`](../../memory_graph/geometry.py)).

**Out.** An `Observation`: the photo, the depth image, the camera's lens numbers (`K`) and the
camera's position in the room (`T_world_cam`).

### Step 1b. Remove hidden points (new in T6.3)

**The problem.** LiDAR points are spread thin, with gaps between them. Through the gaps between
the chair's own points, points from the wall and floor behind the chair also landed inside the
chair's area of the photo. The camera cannot see them, the chair is in the way, but the depth
image had them anyway.

**What happens.** If a pixel has a much nearer pixel right next to it (within 3 pixels, more than
10 percent nearer), it is probably hidden behind something. It is deleted.

**Where.** `drop_occluded` ([`geometry.py:93`](../../memory_graph/geometry.py)), called right after
step 1 ([`replay_loader.py:409`](../../memory_graph/replay_loader.py)).

**Why in the loader.** Only LiDAR depth has this problem. A depth camera (like the D455) gives a
full depth image where each pixel already shows the nearest surface. Fixing it where the LiDAR
depth is made keeps every later step the same for both kinds of depth.

### Step 2. Find the objects in the photo (S1)

**What happens.** SAM 3, an AI model, gets the photo and a list of 30 words ("chair", "sofa",
"shelf", ...). For each word it finds every match and draws its outline. An outline is called a
**mask**: the set of pixels that belong to that object. Each match also gets a box around it and a
confidence score from 0 to 1.

All 30 words are asked in one go, so the photo is only read once. That takes about 1.3 seconds on
the lab GPU.

**Where.** `detect` ([`sam3_adapter.py:99`](../../memory_graph/sam3_adapter.py)). SAM 3 itself is
loaded by `build_sam3` ([`run_photo.py:224`](../../memory_graph/run_photo.py)).

**Example.** Frame 700: 151 matches. Many are weak or repeated.

### Step 3. Clean the list and the outlines (S2 and S5)

**What happens, in order.**

1. Drop weak matches (score under 0.3), background words (wall, floor, ceiling) and tiny boxes
   (`filter_detections`, [`detection_filter.py:25`](../../memory_graph/detection_filter.py)). The
   rest are sorted, most confident first.
2. Shrink every outline by one pixel. Edge pixels often sit on the boundary between the object and
   what is behind it (`erode_one_pixel`, [`masks.py:20`](../../memory_graph/masks.py)).
3. Drop tiny outlines, and drop an outline that is almost a copy of a more confident one
   (`kept_mask_indices`, [`masks.py:45`](../../memory_graph/masks.py)).
4. If one object sits inside another (a cup on a table), cut the inner one out of the outer one
   (`subtract_contained`, [`masks.py:82`](../../memory_graph/masks.py)).
5. **New in T6.3:** a pixel may belong to one object only. If two outlines still share a pixel,
   the more confident one keeps it (`one_owner_per_pixel`,
   [`masks.py:114`](../../memory_graph/masks.py)).

**Why step 5 was added.** SAM 3 sometimes found one desk twice, as "desk" and as "table". Rules 3
and 4 did not catch it, because the two outlines were not quite copies and neither box was inside
the other. Without step 5 the same desk pixels would feed two objects.

**Where all of it is called.** `clean_masks` ([`masks.py:135`](../../memory_graph/masks.py)).

**Example.** Frame 700: 151 matches become 60.

### Step 4. Describe how each object looks (S6)

**What happens.** Each object's box is cut out of the photo, with a little margin. CLIP, another AI
model, turns each cut-out into a list of 512 numbers. Two pictures of the same chair give similar
numbers (they score 0.93 out of 1). A chair against a sofa scores about 0.56.

**Where.** `image_features` ([`image_feature.py:55`](../../memory_graph/image_feature.py)), with the
encoder in `clip_encoder.py`.

**Why.** Later, when the robot sees an object again, the numbers help decide whether it is the same
object or a different one.

### Step 5. Lift each object into the room (S7, S8, S9)

**What happens, for each object.**

1. Take the pixels inside its outline that have a distance. Turn each one into a 3D point in the
   room (`back_project`, [`geometry.py:113`](../../memory_graph/geometry.py)). If fewer than 16
   pixels have a distance, the object is skipped.
2. Keep the biggest clump of points and throw away stray ones (`clean_cloud`,
   [`geometry.py:227`](../../memory_graph/geometry.py)).
3. Put a box around the clump (`fit_box`, [`geometry.py:201`](../../memory_graph/geometry.py)).
4. Skip objects more than 6 m from the camera (`within_range`,
   [`geometry.py:238`](../../memory_graph/geometry.py)).

**Where all of it is called.** `build_candidates` ([`geometry.py:249`](../../memory_graph/geometry.py)).
Each result is a **candidate**: one object seen in one photo, with its points, box, word and CLIP
numbers.

**Example, before step 1b existed.** The chair's pixels had distances from 1.08 m (the chair) to
2.08 m (the floor behind it). The biggest clump was the floor, so the chair's box sat on the floor,
at height -0.02 m. After step 1b, the chair's box is at seat height, 0.58 m.

### Step 6. Add it to the memory (S10 and S11)

**What happens.** Each candidate is compared with the objects already stored. If one is stored at
the same place (their points come within 2.5 cm of each other) and looks alike, the new sighting
merges into it. Otherwise it becomes a new object.

**Where.** `ObjectStore.integrate` ([`object_store.py:159`](../../memory_graph/object_store.py)).

**Example.** Frame 2200 sees the same chair from 1.17 m away. Its candidate lands 7 cm from frame
700's, so the two merge into one object. Before step 1b, frame 700's "chair" was a floor patch,
half a metre from the seat, so it never merged.

## The runner: `run_photo.py`

[`memory_graph/run_photo.py`](../../memory_graph/run_photo.py) is the script that runs all six
steps on chosen frames of the bag. It runs on the lab box, which has the GPU.

| Function | What it does |
|---|---|
| `run_photo` (line 76) | Step 2, then hands over to `stages_after_detection` |
| `stages_after_detection` (line 58) | Steps 3, 4 and 5 |
| `main` (line 241) | Reads the bag, runs each frame, then step 6, prints one line per object |
| `log_rerun` (line 160) | Writes a 3D view you can open in the Rerun viewer: the room, the camera, the photo with outlines, each object's points and box |
| `save_photo`, `load_photo` (lines 110, 135) | Save a photo with what SAM 3 and CLIP said about it, and load it back |

The command used on the lab box:

```bash
.venv/bin/python -m memory_graph.run_photo --bag <handdriven1_0.db3> --frames 700 1400 1500 2200 --rrd out.rrd --save-fixture out_fixture/
```

## The test: `test_run_photo.py`

SAM 3 and CLIP need the lab GPU. So three photos were saved together with what SAM 3 and CLIP said
about them, in `memory_graph/tests/fixtures/fastlivo_photo/`. The test loads them and runs steps 3
to 6 again, on any computer, with no GPU.

[`memory_graph/tests/test_run_photo.py`](../../memory_graph/tests/test_run_photo.py) checks that:

- the same objects come out, in the same order, within 5 cm of where they were on the GPU
  (line 69),
- no pixel belongs to two outlines (line 78),
- every object is in front of the camera and within range (line 84),
- every object goes into the memory (line 99).

What it cannot check: whether SAM 3, CLIP or the loader still behave the same. Their output is
frozen in the saved files.

## Words used here

| Word | Meaning |
|---|---|
| depth image | A photo where each pixel holds a distance instead of a colour. 0 means no distance known |
| mask, outline | The set of pixels that belong to one object in one photo |
| confidence | SAM 3's score from 0 to 1 for how sure it is of a match |
| candidate | One object seen in one photo, lifted into 3D. Not yet known to be new or already stored |
| object | One thing in the room, built up from every photo that saw it |
| fixture | Saved data that a test loads, so the test does not need the original source |
