**Session 2026-09-15. Branch `t0.3-fresh-clone-paths`, rebased onto main 2026-09-19.**

## The short answer

Eleven of the thirteen hardcoded file addresses are gone. Two were left on purpose. The bench check
that watches for this moved from "cannot tell" to "pass". Nothing was executed, so none of this
proves the robot works, only that the code now looks in the right places.

## What the problem was

`[code]` Thirteen lines across eight files contained a full file address typed out by hand, all
pointing inside `/home/iot22/GitHub/Renaissance-Capstone-Project/`. That is a username on the lab
machine plus the project's old name. The project has since been renamed to Gappler and copied to
other machines, so none of those addresses pointed at anything real on any current computer.

The effect was that `main.py`, `ros2_robot_ws/src/orchestrator.py`, `ros2_robot_ws/src/main.py` and
`sam3_ros_node.py` each stopped on their first attempt to open a file. Only the lab machine could run
anything, so only one person could do real work at a time.

Full survey of the original state is [`../NEXT_STEPS.md`](../NEXT_STEPS.md)
section 2.5. See the "For Dion" section at the bottom, because that section is now out of date.

## The two kinds of fix

The addresses split into two groups that want opposite treatment, and getting this distinction right
is most of the task.

**Inside the project, calculate. Never configure.** Most of the addresses pointed at files that live
inside the repository. For those, the code should not be told an address at all, because making them
configurable is just a way to get them wrong later. A Python file can ask where it is on disk and
count folders from there. `main.py:15` and `src/config/base.py:19-20` already did this correctly
before this session, so the work was extending an existing mechanism rather than inventing one.

**Outside the project, configure.** A few genuinely live outside the repository and differ per
machine. The code cannot work those out, so somebody has to say. Those became an environment
variable, which is a named setting that lives in your terminal rather than in the code.

Two of these deserve more than a renumbering.

**`sam3_ros_node.py` was not just a wrong address, it was a duplicate.** `src/config/models.py:11`
already defined that exact file's location correctly, as `ModelPaths.SAM3_PATH`. The same fact was
written down three times in this repository and only one copy was right. The node now imports the
correct one, and the third copy went with the deleted demo block. Writing one fact in three places is
what produced this bug in the first place, so fixing the addresses without removing the duplication
would have left the trap set.

**`install.sh` was the one with teeth.** `install.sh:16` and `:26` run `rm -rf` against these two
variables. Today `set -e` stopped the script first, because the folder was simply absent. On a
machine that still held an old copy of the project it would have found that one instead and deleted
inside it. Nothing bad happened, but the fuse was lit.

### Group B, one environment variable

`[code]` Commit `8d86d04`. `GAPPLER_MAP_DIR`, defaulting to `~/maps`.

| File and line | Change |
|---|---|
| `slam_mapping.launch.py:38` | autosave writes `$GAPPLER_MAP_DIR/current_map` |
| `slam_localization.launch.py:147-150` | `map_file_name` overridden after the params file |
| `slam_toolbox_localization.yaml:14-17` | now a plain relative default plus a comment saying the launch file decides |

Two things worth recording here.

**A ROS parameters file cannot read an environment variable.** It only holds fixed values. So the
change could not be made in `slam_toolbox_localization.yaml` where the bad address lived. It had to
go in the launch file that loads it, `slam_localization.launch.py:147`, which passes the file and then
an override after it. ROS applies the later entry over the file. The value in the YAML survives as a
written-down default that no longer decides anything.

**`[code]` This turned up a real bug nobody had flagged.** Mapping wrote to `~/maps/current_map`,
meaning the running user's home folder. Localisation read from `/home/iot22/maps/completed_map`,
meaning one specific other person's home folder, under a different filename. Different user *and*
different name, so a map saved by the mapping launch could never have been loaded by the localisation
launch, on any machine, by anyone. Both now read one setting, which fixes it as a side effect.

This is worth knowing before M3 mapping starts. If anyone has been assuming those two launch files
talk to each other, they have not been.

**Known duplication, deliberate.** The `~/maps` default appears in both launch files. `robot_slam` is
a CMake package, so sharing one constant between two launch files needs more machinery than the
duplication is worth. Recorded rather than solved.

## What was deliberately left

**The three OpenVINS lines**, `src/main.py:309`, `:310` and `:337`. `[code]` They point at an external
OpenVINS workspace at `~/Ros2Workspaces/OpenVINS/` that is not in this repository, while the
repository carries 398 MB of OpenVINS source at `Navigation_Module/OpenVINS/` that has never been
built (no `install/` anywhere in the tree). Which one is authoritative is an open question and
touching the paths before answering it would bake in the wrong answer.

`src/main.py:312` **was** fixed despite sitting in the same block, because it points at one of our own
files, `estimator_config.yaml`, and was broken on every machine regardless of how the OpenVINS
question is settled.

`[unverified]` I could not check whether the external workspace still exists. The lab box was
unreachable over tailscale on 2026-09-15. Worth ten seconds at the next lab session:

```bash
ls -d ~/Ros2Workspaces/OpenVINS/install 2>&1
```

**AnyGrasp still launches through conda.** `ros2_robot_ws/src/main.py:30` and `:122-131`. Same class
of assumption, but it is not a path and changing it changes how the program runs. It also needs
somebody to settle which checkpoint file is real, which is finding 3 in
[`../NEXT_STEPS.md`](../NEXT_STEPS.md) section 2.6. The path work leaves a clean
seam: now that `ANYGRASP_DIR` is derived, swapping the launcher is a two-line follow-up.

**The bench's own blind spot on `~/` paths.** `bench/preflight.py:811` matches `/home/<user>/` only,
and its file list at `:814` excludes `.md`, `.rviz`, `.txt` and `.cpp`. So the check that polices this
cannot see a `~/` address at all. `bench/contracts.py:416` does catch them, so the inventory is
complete and it is only the failing check that has the hole. Left as a separate piece of work.
