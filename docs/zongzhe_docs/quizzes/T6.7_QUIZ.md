## Walkthrough: what T6.7 does, with "find the couch"

T6.7 is the reasoning layer working as a whole. A person gives an instruction. The layer turns it
into class names the detector (SAM 3) can look for. Three parts built earlier do the work:

| Part | File | What it does |
|---|---|---|
| T6.7a | `task.py` | Turns the instruction into a CLIP text vector, and holds the target and related classes |
| T6.7b | `reasoning.py` | Asks Qwen which classes the instruction means. Falls back to CLIP if the reply is unusable |
| T6.7c | `vocabulary.py` | The detector's class list. New classes go on the end, so a class id never changes |

Follow "find the couch" through it, with the 30-class base list (sofa is in it, couch is not):

1. `TaskContext.from_text` turns the sentence into a CLIP vector (T6.7a).
2. `ClassExpander.expand` builds the prompt: the rules, two examples, the 30 classes and the
   instruction (`reasoning.py:60-78`). It asks Qwen with a 10 s limit.
3. Qwen 1.5B replies `{"targets": ["couch"], "related": []}`. That was the reply in the first
   check run.
4. `parse_reply` reads it. Since step 5, `couch` goes through `canonical()`, which looks it up in
   the synonym table from config and turns it into `sofa` (`reasoning.py:149-158`).
5. `extend_for_task` adds any target not yet in the list to its end (T6.7c). `sofa` is already
   there, so nothing is added and SAM 3 keeps 30 prompts.
6. The result is an `Expansion`: the task with its classes filled in, where they came from
   (model or fall-back), the raw reply, what was added, and `ranked`, the targets best first.

The check script runs that for 22 written instructions, once with each model and once with the
CLIP fall-back alone, and writes a table for a person to mark. The first run and the hand check
led to five fixes (step 5):

| Fix | What changed | Where |
|---|---|---|
| 5a | A synonym table maps couch to sofa, bin to trash can, and so on | `config.py:173-183`, `reasoning.py:150-155` |
| 5b | `_` and a space count as the same when reading a reply | `vocabulary.py:49-53` |
| 5c | The prompt asks for 2 to 5 related classes | `reasoning.py:64-65` |
| 5d | The CLIP fall-back makes only its best class a target | `reasoning.py:282-288` |
| 5e | Qwen 1.5B is the default model | `config.py:159` |

## Round 1: the check script

### Q1. `check_reasoning.py`, `run_one`

**Question.** What does the check do with one instruction, and what decides whether its row
passes?

**Model answer.** It turns the instruction into a task (`TaskContext.from_text`), runs
`expander.expand` on it, and writes one row: where the classes came from, the targets in order,
the related classes, any new classes, the time and the raw reply (`check_reasoning.py:66-85`).
The row passes if the **first** target is in the instruction's `accept` list
(`check_reasoning.py:82`). Related classes are reported but not scored: a person judges them.

**My answer.** Not answered yet.

### Q2. `check_reasoning.py`, `run_set` and `round_trip`

**Question.** `run_set` gives every instruction a fresh copy of the base list. `round_trip` runs
all of them on one shared list. Why both?

**Model answer.** They test different things.

- `run_set` (`check_reasoning.py:88-91`): each row should depend only on its own instruction. If
  the list were shared, a class added by an earlier row ("plant") would already be in the list for
  later rows, and the same instruction could give a different answer depending on what ran
  before it.
- `round_trip` (`check_reasoning.py:94-117`): a long run does see instructions one after another
  on one growing list. This checks the T6.7c promise over the whole set: no class id ever moves,
  the list still starts with the base list, and a save then a load gives the same list back.

**My answer.** Not answered yet.

### Q3. `reasoning.py`, `Expansion.ranked`

**Question.** Why does `Expansion` need a `ranked` field when the task already holds the targets?

**Model answer.** The task holds its targets as a set (`task.py:49`), and a set has no order.
`extend_for_task` also sorts them alphabetically (`vocabulary.py:188`). So after `expand`, nothing
says which target the model put first. The check judges the first target, so `expand` keeps them
in the order given, model order or fall-back order, in `ranked` (`reasoning.py:226`, `:290`).

**My answer.** Not answered yet.

### Q4. `check_reasoning.py`, `check`

**Question.** `check` takes a function that builds each expander, not the expanders themselves.
Why?

**Model answer.** So only one model is in GPU memory at a time. Each expander is built when its
turn comes, used for both passes, then dropped, and the GPU cache is emptied
(`check_reasoning.py:145-156`). Building 0.5B and 1.5B up front would load both, about 4 GB
together, on a GPU other people share.

**My answer.** Not answered yet.

### Q5. `eval/instructions_t6_7.json`

**Question.** Why was the instruction set frozen before the first run? And why does step 5f need
a second, held-out set?

**Model answer.** Frozen first: the `accept` lists say what counts as right. Written after seeing
the replies, they would drift towards whatever the model happened to say, and the check would
pass by construction. Held-out set: the step 5 fixes were designed from these 22 instructions, the
synonym table especially. Passing them again shows the fixes do what they were built for, not that
they work on instructions nobody has seen. New instructions, written before the rerun, test that.

**My answer.** Not answered yet.

## Round 2: reading the model's reply

### Q6. `reasoning.py`, `canonical` inside `parse_reply`

**Question.** Walk the reply name `"Couch"` through `canonical()`, line by line. What comes out?

**Model answer.** `reasoning.py:152-155`, with sofa in the list and `("couch", "sofa")` in
the synonym table:

| Line | Does | Value |
|---|---|---|
| `_names` (before it) | trims and lower-cases | `couch` |
| `key = name_key(name)` | also reads `_` as a space | `couch` |
| `renamed.get(key, key)` | the synonym table | `sofa` |
| `spelling.get(key, key)` | the list's own spelling of that key | `sofa` |

So the target is `sofa`, a class already in the list, and nothing new is added.

**My answer.** Not answered yet.

### Q7. `vocabulary.py`, `name_key`

**Question.** What does `name_key` do? Why not just rename `tv_monitor` to `tv monitor` in the
list instead?

**Model answer.** It does what `normalise` does (trim, lower case, single spaces) and also turns
`_` into a space (`vocabulary.py:49-53`). It is only for **comparing** a name with the list.
Renaming the list itself would change the phrase that class id 27 stands for. Saved vocabulary
files and the T6.4e ground truth (which uses `tv_monitor`) would no longer match. It would also
change the prompt SAM 3 gets, and so its detections. That is T6.12's question, measured on its
own. `parse_reply` builds `spelling` from `name_key` to the list's spelling
(`reasoning.py:149`), so a reply of "tv monitor" still comes out as `tv_monitor`.

**My answer.** Not answered yet.

### Q8. `parse_reply`, a new name with an underscore

**Question.** The model replies `fire_extinguisher`, which is not in the list. What becomes the
target, and why does the spelling matter?

**Model answer.** `name_key` gives `fire extinguisher`. It is not a synonym and not in
`spelling`, so `canonical` returns the key as it is, with a space (`reasoning.py:155`). It passes
`_is_name` (two plain words) and becomes a new class. The spelling matters because a new class
is the exact text SAM 3 is prompted with on every photo from then on. "fire extinguisher" is how
a person writes it. The underscore was the model copying `tv_monitor`'s style from the list.

**My answer.** Not answered yet.

### Q9. `config.py`, `class_synonyms`

**Question.** Why a hand-written synonym table rather than CLIP text similarity to find a list
class that means the same thing?

**Model answer.** Both were on the table in the step 5 draft. The table was chosen because:

- It is predictable: a name in the table always maps, a name not in it never does. A test can
  check every entry.
- CLIP would need a similarity threshold. Pairs that are not synonyms, like printer and computer
  tower or phone and laptop, may sit close in CLIP's space, so a threshold that catches couch to
  sofa could also merge those.
- A threshold tuned on the 22 instructions would fit them, not new ones.

The cost: the table only covers what is written in it (`config.py:177-183`).

**My answer.** Not answered yet.

### Q10. `config.py`, `__post_init__` checks on `class_synonyms`

**Question.** Which synonym settings does the config refuse, and why must a config that changes
the base list also set `class_synonyms`?

**Model answer.** Refused (`config.py:225-235`):

1. an empty name, or the same name twice (compared with `name_key`, so "Couch" and "couch" are
   the same),
2. a synonym whose class is not in the base list, such as `("couch", "settee")`. A typo in a
   class name is an error, not a silent new class and a new SAM 3 prompt,
3. a name that is already a class in the base list, such as `("chair", "sofa")`. That would make
   a real class impossible to name.

Rule 2 is why a config that swaps in its own base list must set `class_synonyms` to match, or to
`()` for none: the default table points at sofa, trash can, tv_monitor and computer tower, and
those may not be in the new list. The error message says so. Rule 2 was dropped for a while during
step 5 and brought back after this quiz found the typo hole (issue 1).

**My answer.** Not answered yet.

## Round 3: the fall-back, the prompt and the model

### Q11. `reasoning.py`, the fall-back in `expand`

**Question.** No model reply. Trace "take me to the door" through the fall-back before and after
step 5d. How does it differ from upstream?

**Model answer.** `fallback_targets` keeps the list classes whose CLIP text similarity to the
instruction is within 95 % of the best, best first, at most 5 (`reasoning.py:181-207`). For this
instruction that gave `door, window`.

- Before 5d, and upstream (`map/map.py:193`): both become targets, so the robot would search for
  windows too.
- After 5d (`reasoning.py:282-288`): the best, `door`, is the only target. `window` becomes
  related, cut to `reasoning_max_related`.

Under Zongzhe's marking rule, a second target that is not the object asked for makes the row
wrong. 5d fixes that for door and window, and for keyboard and tv_monitor.

**My answer.** Not answered yet.

### Q12. `reasoning.py`, `PROMPT`

**Question.** What two changes did 5a and 5c make to the prompt, and why? "2 to 5 related" could
push the model to invent classes. What stops that from doing harm?

**Model answer.** 5a: a second example, "find the couch" answered with `sofa` when sofa is in the
list (`reasoning.py:72-73`). The rule "use the list's name" was already there and 1.5B ignored
it twice. An example usually works better than a rule on a small model. 5c: "2 to 5 objects from
the list" replaced "Leave it empty if none are" (`reasoning.py:64-65`), which 1.5B took for 21 of
22 instructions.

What limits the harm: `parse_reply` keeps a related name only if it is already in the list, drops
repeats and background classes, and keeps at most `reasoning_max_related` (5)
(`reasoning.py:160-177`). A related class can never add a SAM 3 prompt. Whether the lists make
sense is checked by hand on the 5f rerun.

**My answer.** Not answered yet.

### Q13. `config.py`, `reasoning_model`

**Question.** What does Qwen 1.5B cost compared with 0.5B, and why is that acceptable?

**Model answer.** About 3 GB of GPU memory in float16 against about 1 GB, and about 0.3 s per
reply against 0.1 to 0.35 s (`config.py:154-159`, run record 2026-10-23). Acceptable because the
call happens **once per task**, at the start, not on every photo. In return it was right on 20 of
22 instructions by hand, against 12 of 22 scored for 0.5B. The voice path still loads 0.5B in its
own process, so the two do not share a model.

**My answer.** Not answered yet.

### Q14. `reasoning.py`, `_ask`

**Question.** The model hangs. What does `expand` return, and what happens to the next task?

**Model answer.** `_ask` runs the model in a daemon thread and waits `reasoning_timeout_s`
(10 s) (`reasoning.py:259-265`). If the thread is still running, `_ask` returns "no reply within
10 s", and `expand` uses the CLIP fall-back. The task goes on. The thread keeps running, since
Python cannot kill it, but as a daemon it does not stop the program from exiting. While it is still
running, the next task does not call the model at all. It goes straight to the fall-back with "the
previous model call is still running" (`reasoning.py:248-249`), because the model is not safe to
call from two threads at once.
