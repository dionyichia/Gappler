## Round 1: the runner, the fixture, the two new rules

### Q1. `run_photo.py`, `stages_after_detection` and `run_photo`

**Question.** What does each take and return? Why does `stages_after_detection` take a
`features_for` function and not an encoder? Why does the fixture store CLIP vectors for the
cleaned detections, not for SAM 3's raw output, and what has to stay the same for them to line up?

**Model answer.**

| Function | Takes | Does | Returns |
|---|---|---|---|
| `run_photo` (`run_photo.py:76`) | an `Observation`, SAM 3, the CLIP encoder, the vocabulary | S1 (`detect`), then hands over | a `PhotoResult` |
| `stages_after_detection` (`run_photo.py:58`) | an `Observation`, SAM 3's raw `Detections`, `features_for` | S2, S5, S6, S7 to S9 | a `PhotoResult`: raw, cleaned detections, vectors, candidates |

Neither writes to the graph. `main` does that afterwards with `ObjectStore.integrate`
(`run_photo.py:278`).

`features_for` is a function so the same code runs two ways. On the lab box it calls the CLIP
encoder on the cleaned boxes (`run_photo.py:88`). In the test and in `--photo` mode it returns the
vectors saved in the fixture (`test_run_photo.py:28`, `run_photo.py:273`). That is how the replay
needs no CLIP model and no GPU. The vectors are not reused from the graph.

The vectors are stored for the cleaned detections because S6 runs after S5: they are exactly the
vectors the GPU run used, one per cleaned detection, in order. Raw output had 151 detections on
frame 700 against 60 after cleanup, so storing raw vectors would waste space and need a map from
cleaned back to raw. **What must stay the same:** S2 and S5, their code and their config
(confidence threshold, background classes, mask rules, one owner per pixel). They must give the
same detections in the same order, or vector i no longer belongs to detection i.

**My answer.** I said `stages_after_detection` turns detections into vectors stored in the graph,
and that `features_for` reuses vectors already in the graph. Both wrong: it runs S2 to S9 and
returns candidates, the graph comes later in `main`, and `features_for` is either the live encoder
or the fixture's saved vectors. I got the purpose (replay without a GPU). I missed why the
vectors are stored after cleanup and what must stay fixed for them to line up.

### Q2. `save_photo` and `load_photo`

**Question.** What goes into the `.npz`, in what form? Why can colour be lossy while depth is
exact? Why bit-packed masks, and what is `mask_width` for?

**Model answer.** (`run_photo.py:110`)

| Key | Form |
|---|---|
| `rgb_jpeg` | the colour image as JPEG bytes, quality 90 |
| `depth_mm` | depth as uint16 whole millimetres, 0 = no reading |
| `K`, `T_world_cam`, `frame_id`, `timestamp` | as in the `Observation` |
| `xyxy`, `conf`, `class_id`, `label` | SAM 3's raw boxes, scores, ids, phrases |
| `masks`, `mask_width` | raw masks, 8 pixels per byte along each row |
| `features` | one CLIP vector per cleaned detection, float32 |

Colour can be lossy because nothing measured reads it on replay. S6 is stored, so CLIP never
looks at the colours again. They only colour the points. Depth feeds back-projection, so an error
there moves objects. Millimetres are exact enough: rounding moves a point by at most 0.5 mm.

`np.packbits` pads each row up to a multiple of 8 bits. `mask_width` tells `np.unpackbits` the
real width, so the padding is cut off (`count=`, `run_photo.py:144`). At 640 px it changes
nothing, but an image whose width is not a multiple of 8 would come back too wide without it. It
is not a size or resolution setting.

**My answer.** I named the JPEG, SAM 3's output and the vectors, but missed depth, `K` and the
pose. "Small file, keep what matters" is right in spirit. The reason colour may be lossy is more
precise: replay never reads it except to colour points. I got `mask_width` wrong: it undoes the
row padding, it does not trade size against resolution.

### Q3. `geometry.drop_occluded`

**Question.** The rule in one sentence. Why does LiDAR depth need it and D455 depth not? What does
a 10 percent margin mean at 1 m and at 6 m? What does it cost?

**Model answer.** A depth pixel is cleared if some valid pixel in its 7 x 7 block is more than 10
percent nearer: `depth > nearest * (1 + margin)` (`geometry.py:110`).

LiDAR depth is a sparse cloud projected into the image (12 to 14 percent of pixels). The z-buffer
only decides between points that land on the same pixel. So the wall behind a chair fills the
pixels between the chair's own points, and the chair's mask collects both. A D455 depth image is
dense, and each pixel already holds the nearest surface, so nothing shows through.

The margin scales with distance. At 1 m a pixel is cleared if a neighbour is more than 10 cm
nearer. At 6 m it takes 60 cm. A fixed metre threshold would be too strict far away, where LiDAR
noise and surface slope give bigger depth steps between neighbours.

Costs: coverage drops (13.8 to 12.3 percent on frame 700). A thin thing within 10 percent of what
is behind it (paper on a wall) keeps its background. True far pixels right next to a near
object's edge are cleared too.

**My answer.** "Tighter boxes" is a result, not the rule. I did not say why LiDAR needs it and the
D455 does not (sparse projection, the z-buffer only works per pixel). My point that a nearer point
drops neighbours over smaller depth differences is roughly the 1 m against 6 m answer. Coverage
loss is right. I missed the thin-object and edge costs.

### Q4. `masks.one_owner_per_pixel`

**Question.** What does it do to two overlapping masks, and why does the order matter? Why does it
run after the duplicate and containment rules, not instead of them? In the desk and table test,
what happens to the table, and where does it finally disappear?

**Model answer.** It walks the masks in order. Each mask keeps only the pixels no earlier mask
took (`masks.py:127`). S2 sorted the detections by confidence, so the first, most confident mask
wins every shared pixel. Unsorted input would hand pixels to the wrong mask.

It runs last (`masks.py:149`) because the earlier rules decide by different evidence:

- The duplicate rule (`kept_mask_indices`, `masks.py:45`) drops a whole near-copy (IoU above 0.9).
- The containment rule (`subtract_contained`, `masks.py:82`) cuts a small object out of the box
  that holds it, whatever the scores. A cup keeps its pixels even if the table scored higher.

If one owner per pixel replaced containment, a more confident table would take the cup's pixels
and the cup would be lost. So it is a backstop for the overlap the two upstream rules miss.

The table in the test lies entirely inside the more confident desk, so its mask comes back empty.
It is not removed in `kept_mask_indices`: that runs before this step (`masks.py:147` against
`:149`). The table survives S5 as a detection with an empty mask, still gets a CLIP vector in S6,
and disappears in S7: `back_project` returns None for a mask with fewer than `min_points` valid
depth pixels (`geometry.py:127`), and `build_candidates` skips it.

**My answer.** "The most confident mask gets the pixel" is right. I did not explain why order
matters (S2's sort). My reason for running it last was vague, and I missed the key point that
containment works whatever the scores and one owner per pixel does not. I got the table wrong: it
is not dropped in `kept_mask_indices`, which runs earlier. It lives on with an empty mask until S7.

### Q5. `test_run_photo.py`, `LabPhotoTest`

**Question.** What does `test_same_objects_as_the_recorded_run` prove, and what can it never
catch? When must `expected.json` be remade?

**Model answer.** No GPU runs in the test. It loads SAM 3's saved output and the saved vectors and
runs S2 to S9 again (`test_run_photo.py:26`). It proves our code after SAM 3 still gives the same
labels in the same order, with box centres within 5 cm of the GPU run (`test_run_photo.py:76`).
It is a regression test of our stages.

What it cannot catch:

- Changes in SAM 3, CLIP or the vocabulary. Their output is frozen in the fixture.
- Changes in the loader. The fixture holds depth already rendered and filtered.
- Wrong answers that were already wrong on 2026-10-21. `expected.json` is what the code gave, not
  ground truth.

Remake it whenever SAM 3, the vocabulary, CLIP or the loader changes, so the fixture matches what
the pipeline now sees. Also remake `expected.json` when S2 to S9 change on purpose, for example a
retune in T6.4. T6.4 is one likely time, not the rule.

**My answer.** I said it proves the GPU run reproduces the labels. It replays the GPU run's saved
output without a GPU, so it tests the stages after SAM 3, not the GPU run. "It does not prove the
graph is replicated" is fair. I did not list what it cannot catch. "Remake at T6.4" is one case,
the rule is: whenever something upstream of the saved data, or the stages themselves, change.

### Code issues found in round 1 (none changed)

1. **Saved vectors can silently misalign.** `stages_after_detection` only checks that the number
   of vectors matches the number of detections (`run_photo.py:70`). If S2 or S5 changes and still
   yields the same count but a different set or order, each object gets another object's vector
   and nothing fails. Fix: save each cleaned detection's index into the raw output (what
   `clean_masks` returns, plus S2's order) and check it on replay. `[inferred]`, not triggered.
2. **Emptied masks are still encoded.** One owner per pixel can empty a mask (the table). S6 runs
   CLIP on its box anyway, and S7 drops it later. Wasted work, small.
3. **Boxes are not updated after masks are cut.** `subtract_contained` and `one_owner_per_pixel`
   change masks but keep the old box, which S6 crops from. Upstream does the same. Small.
4. **`build_sam3` switches bfloat16 on for the whole thread and never off** (`run_photo.py:235`),
   copying the segmentation service. CLIP overrides it with float16 (D-MG7). Anything else run
   later in that thread would be in bfloat16. Note only.
