Method (probe.py)
  Wait for color, aligned depth and camera_info. Count frames received for 10 s with no calls.
  Then 20 calls to /segmentation/segment, prompt "light", each on the newest frame.
  inference = the service's own inference_ms, round trip = the probe's call to answer.
  Modes run in the order A1, B1, A2, C1, B2, so CPU heat hits both sizes.

Modes
  A  rgb_camera.color_profile:=640x480x15 depth_module.depth_profile:=640x480x15  (3b settings)
  B  pointcloud.enable:=true, nothing else  (what ./quickstart_terminals.sh grasp starts)
     Driver defaults: color 1280x720x30, depth 848x480x30. Aligned depth comes out 1280x720.
  C  driver defaults, no point cloud

  SAM 3 found the light in every call of every mode (1 detection each time).

What it shows
  1. 1280x720 costs about 40 % more per call: 360-410 ms against 260-270 ms. SAM 3 resizes
     every image to the same input size itself [inferred], so the extra time is in the bigger
     request (3x the bytes) and the work on full-size images around the model: conversion,
     resize, mask upsampling, depth lookup [inferred, not profiled].
  2. Best case for the grasp client, calling back to back: about 2.6 calls a second at
     1280x720, 3.6 at 640x480. Both clear the 2.0 s stale-centroid limit (T1.24).
  3. The point cloud does not change SAM 3's time (C1 vs B2) but takes the camera node from
     66 % to 88 % of a thread. The grasp path does not use it [unverified: check before
     dropping it from quickstart].
  4. The driver defaults now deliver frames. On 2026-10-07 they sent none. Today 25-30 fps.
     B1 logged one "Frames didn't arrive within 5 seconds" warning, about 23 s after start,
     B2 and C1 none [unverified whether it was during the probe or during shutdown].
  5. The CPU stayed at 89-93 C the whole run, clock 800-1500 MHz (intel_powerclamp, as on
     2026-10-12). All numbers above are on a throttled CPU. A1's one 534 ms call is the first.

Not measured
  The full loop through grasp_segmentation_client.py (its own centroid rate at each size).
  Depth quality at short range. A RealSense's closest usable depth depends on the depth
  resolution [unverified for this camera], which matters for 3b's "distance where z stops".

Decision (Dion, 2026-10-13): pin the grasp layout's wrist camera to 640x480x15, for now.
  quickstart_terminals.sh grasp now starts it with rgb_camera.color_profile:=640x480x15
  depth_module.depth_profile:=640x480x15 and no point cloud. Checked on the box with --print:
  the pane command matches mode A above, which ran clean twice.
