Section 1Can we split the work three ways

Dion's question was whether there is any obvious way to divide this between three people right now. The answer is worth stating before anything else on this page.

Partly. Not this week, and cleanly from week 3.

Three separate streams exist and they touch each other at only three message channels and one measurement. What hides them is that two removable obstacles sit in front of all three, so from where we stand today everything looks like a single queue. Removing both is the whole of milestone M0 and costs about two weeks.

The two obstacles

Nothing in this repository runs from a fresh clone. Every absolute path points at a user and a repository name that no longer exist Only the one machine that already holds working state can run anything, so only one person can do real work at a time 12 h Zongzhe

Why the split is real once those are gone

  • ROS 2 couples subsystems by channel name and message type and by nothing else. No subsystem here imports another. That is exactly the property that lets three people build against an agreed interface and find out at integration time whether they agreed.
  • The bench already supplies stand-ins for the hardware. A simulated arm, a fake navigation server that can be told to fail, synthetic camera publishers, and a private message channel so two people on the same workstation cannot see each other's traffic.
  • About two thirds of the open work needs no hardware at all. Path portability, the configuration work, most of the 51 audit findings, the memory graph built from recordings, and the goal-ordering work which is LiDAR only.
  • Mechanical work does not contend with code at all. The mount, the switch, the physical measurements that four places currently disagree about, the trial fixture.

The one rule that keeps this working

ROS matches channel and frame names as plain text at run time. A rename applied to four of five places compiles, launches and quietly does nothing. That has already produced two defects in this repository. Run ./bench/run.sh before and after any change that moves code.

Section 5What each person owns

What you are accountable for, what you get out of it, why the work suits you, and what is open enough to be worth digging into. Task-level ownership is in the tree above.

Dion

Perception, the arm, and the research claim

Owns everything between a camera frame and the arm closing on an object, plus the contribution itself. Arm bring-up through to a working grasp, one segmentation service instead of two competing ones, the glasses stream reaching the arm, the calibration of the base camera and what its accuracy costs, and the gaze-conditioned query that M8 measures.

Takeaway. An end-to-end perception system on real hardware, from raw frames to an executed motion, and a measured result with an ablation table behind it. Production ROS 2 in both Python and C++, since T7.1 is written with rclcpp against a working Python reference.

Why it fits. The most vision-heavy and the most systems-heavy stream in the project. Most of it is repair rather than authorship, and the skill it rewards is reading an unfamiliar system accurately enough to find the five lines that matter.

Worth exploring. Image embeddings. Nothing in this repository computes one today, so the feature extractor is genuinely new code, and both the memory graph and the gaze crop consume it. Owning it makes the interface between perception and the graph a deliverable rather than a conversation.

Zongzhe

The memory graph and the reasoning layer

Updated 20 September. Navigation bring-up moved to Sherman. What stays here is the software half: the two bridge nodes, the node that emits drive goals, and everything above the goal.

Owns the one part of this project that does not already exist in some form: object entries built from images, depth and camera pose; the merge rule that stops one physical object being registered twice; the sentence query that returns a place to drive to; and, if the schedule allows, the frontier scoring and visit ordering in M9.

Takeaway. A published method taken from the paper to working, evaluated code, with the design decisions owned rather than inherited. The most paper-shaped work on the board, and the part a reader of the write-up will ask about first.

Why it fits. Well-posed problems with a right answer, most of them geometric or statistical, and the core of it runs on a laptop against recorded data. Progress does not depend on the robot being free, the lab being open, or anyone else finishing first.

Worth exploring. The merge rule itself, which is 3D overlap combined with embedding similarity and a threshold nobody has tuned for this room. It is the decision the graph's correctness turns on and it is directly measurable. The reasoning layer is the other one, and it carries the only real research risk in the project, because no model here has ever been given an image.

Sherman

The platform, and where its poses come from

Updated 20 September. This now includes navigation bring-up outright, tasks T3.3 to T3.6, the Nav2 and SLAM settings, the static transforms, and the FAST-LIVO2 escalation in T5.9. Sherman also owns the lab session itself: the agenda, the setup, the recording and running the trials, whoever else is in the room.

Owns the robot as a working machine: it powers on, it drives, it maps, it localises, it answers on the network, and a runbook exists that says how. Owns the physical build the rest depends on, meaning the forward camera mount, the calibration rig and target, and the trial fixture that makes M8's runs repeatable. Owns the open question of which pose source the memory graph needs, and the measurement that answers it.

Takeaway. SLAM and localisation on real hardware, ending in a comparison with a number attached rather than a preference. Plus a mechanical design that is genuinely on the critical path rather than a bracket bolted on at the end.

Why it fits. Bring-up rewards resourcefulness with unfamiliar tooling far more than it rewards knowing the internals first, and most of what stands between this repository and a running robot is retrieval and assembly rather than development. The mount is a real design problem, because the arm is mounted facing backward and its swept volume constrains where a forward camera can sit.

Worth exploring. The pose-source question is open and nobody has the answer. Start with the 2D localisation already running, because it is free, and escalate only if the measurement says to. Two findings make it more interesting than it looks: the LiDAR's own inertial sensor is already publishing on livox/imu with nothing subscribing, and the vendored OpenVINS copy is calibrated for the glasses rather than for a base camera. Neither obvious shortcut is quite the shortcut it appears to be.

Working agreements

  1. Hardware sessions are booked and have a written agenda. Travel is twenty minutes each way, so a session with no agenda costs an hour before anything starts. Write it in your own docs folder the day before.
  2. Run the bench before and after any change that moves code. It takes a second and it catches the failure mode this project has already suffered twice.
  3. Two people can use the lab workstation at once as long as each uses a different private message channel. The bench scripts refuse to start if the channel is not empty, which is the check that stops you reaching real hardware by accident.
  4. The defect log is one shared file, one line per bug, from the first powered session onward. It is the raw material for the paper's discussion and it costs nothing to keep.
  5. Nobody edits anybody else's docs folder. Corrections go in your own folder with a citation, and you tell the owner.
  6. Every change goes on a branch and through a PR into dev. Since 21 September dev is the default branch and both dev and main are protected: a PR must pass the bench before it merges. dev is promoted to main by PR.

Two rules that keep this working

One publisher per channel, one owner per channel. Three channels have two publishers today and each one is a known defect. If you need a second source, that is a conversation, not a commit.

Run ./bench/run.sh before and after any change that touches a name. Names are matched as plain text when the robot runs, so a rename applied to four places out of five starts cleanly and quietly does nothing.
