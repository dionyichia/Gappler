Gappler Code Audit

A line‑by‑line read of every file this project owns, traced publisher to subscriber. The first three findings interlock, and together they mean the grasp path cannot work as written. Seven findings have since been reproduced on the bench, which is what the badges below mark.

Mostly unverified

This began as a static read — no hardware, no ROS, nothing executed. That is still true of most of it, so treat an unmarked entry as something to check, not something to fix. The exception is the seven entries marked observed, which the bench has since reproduced on the lab machine against real running nodes: B2a, B4, C7 (2026‑09‑11) and E1, F1, F2, F4 (2026‑09‑14). Each matched the mechanism predicted here, which is the best evidence available that the reasoning in the rest is sound. One entry was tested and not reproduced: B2's message loss, see its note.

Filter
Scope

This page carries 59 of the 62 findings in docs/dion_docs/CODE_AUDIT.md. Three live only in the document because they are inventory rather than defects: B7, the kill‑word fallback firing on ordinary sentences, and K1/K2, which count how much of the channel and constant surface is declared outside the shared config. Counts in the filter bar are computed from this page, so they cannot drift out of step with it again.

A

The grasp path cannot work

One defect in three parts, spread across two languages and two Python environments. Read this section first.

A1Blocks

The AnyGrasp gate is inverted

anygrasp_detection_node.py:182

def synced_callback(self, rgb_msg, depth_msg):
    if not self.intrinsics_received:
        return
    if self.pipeline_state != "IDLE":   # runs ONLY when IDLE
        return

Its own docstring three lines above the function, the file header at :6, and ORIENTATION.md §5 all say it runs when pipeline state is EXECUTING. The condition does the opposite.

A2Blocks

The state machine accepts candidates only in EXECUTING

grasp_state_machine.cpp:171

if (state_ != State::EXECUTING || msg->grasps.empty())
  return;

Mutually exclusive with A1.

A3Blocks

USE_SIMPLE_EXECUTE = true hides both

grasp_state_machine.cpp:41

With this flag set, the entire candidate‑consuming path — executingStep(), checkStability(), slerpQuat(), approachAngleDeg(), the candidate queue — is unreachable. What runs instead is: snapshot the centroid, one Cartesian step, then executingSimple(), which does nothing but close the gripper.

AnyGrasp's output is not used at all today. The arm closes at a position derived purely from the SAM 3 centroid. The 3.4 GB model, the machine‑locked licence and the whole /grasp_candidates contract are, at runtime, decorative.

Why this matters more than any single bug here: the moment anyone flips this flag to turn "real" grasping on, it fails 100 % of the time with EXECUTING: no candidates received after a 3‑second timeout — and the cause is in a different file, a different language and a different conda environment.
B

Safety‑relevant

The arm homes unprompted within seconds of launch, and has never been commanded to move at all.

B1Safety

The root launcher promises an emergency stop that does not exist

main.py:5 (docstring) · main.py:67 (printed at runtime) — both say "press 'q' for emergency stop"

while True:
    time.sleep(1000)

There is no keyboard handling anywhere in the file. No getch, no termios, no thread reading stdin. Pressing q does nothing; only Ctrl+C works, via the SIGINT handler at :50.

This is the top‑level entry point for a system that moves a robot arm, and it tells the operator they have a stop key they do not have.

B2Safety

The e‑stop may not deliver its own message on Ctrl+C

estop.py:72‑76

except KeyboardInterrupt:
    node.emergency_stop()   # publishes
finally:
    node.destroy_node()     # immediately
    rclpy.shutdown()

publish() hands the message to DDS asynchronously. Tearing the participant down on the next two lines can beat delivery.

The author knew this: orchestrator.py:121 does time.sleep(1.5) with the comment "allow topic to deliver before exit" for the identical pattern. The e‑stop — where it matters most — does not.

Tested 2026‑09‑11, not reproduced. bench/estop_delivery.sh sent the stop all five times and it arrived every time, so the race is real in principle but did not bite on this machine. The program still crashes on exit. What the same run did find is worse, and it is B2a below.
B2aSafetyobserved

Ctrl+C in the e‑stop terminal does nothing at all

estop.py:48‑55

getch() puts the terminal in raw mode while it waits for a key, which is nearly all the time. In raw mode Ctrl+C arrives as the character 0x03, not as a signal, so it matches none of e/r/s/q and is silently ignored. No stop is sent and the script keeps running.

So the except KeyboardInterrupt path that B2 worries about is only ever reached by a signal from outside, such as kill -INT. Closing the terminal window sends SIGHUP, which is not handled either.

An operator whose reflex is Ctrl+C gets nothing. This is the emergency stop, and the key almost everyone would reach for first is the one key it ignores. Only e works.
Reproduced 2026‑09‑11 — bench/estop_delivery.sh on the lab machine.
B3Safety

The voice kill word cannot stop the arm

subscribers of /aria/audio/prompt: goto_glasses.py:59, object_approach_node.py:80 — both in Navigation_Module

The LLM maps "stop", "end", "kill", "terminate", "quit", "cancel" to "end", and goto_glasses.py:94 cancels the Nav2 goal. Nothing in rm_mtc subscribes to that topic at all.

So "stop the robot" stops the base and leaves the arm running. The only arm stop is estop.py, in its own terminal, with the window focused — see B2.

B5Runtime

The orchestrator orphans the arm driver and state machine on exit

orchestrator.py:85‑97 — the handler that terminated the children is commented out

main()'s finally calls destroy_node() and prints "Terminated" without touching processes. When the orchestrator exits, background.launch.py and main.py keep running — the state machine is still live and will still move the arm on the next centroid.

B6Runtime

No in‑position interlock inside the state machine

grasp_state_machine.cpp:604‑612

IDLE→SELECTING waits on has_centroid_ alone. The state machine never subscribes to /manipulation/start; the orchestrator only gates launching it. Once running, any centroid starts the approach whether or not navigation says the base is in position.

C

Concurrency in grasp_state_machine.cpp

Two of these are undefined behaviour, not style — symptoms that come and go with timing and optimisation level.

C1Blocks

One condition variable, two mutexes

:607 waits with centroid_mutex_ · :464 waits with queue_mutex_ — same queue_cv_

std::condition_variable requires that all concurrent waiters use the same mutex. Using two is undefined behaviour. Expect lost wakeups and intermittent hangs.

C2Blocks

The centroid is read without its lock, in the loop that decides to close in

grasp_state_machine.cpp:633‑641

double object_depth;
{
  // auto age = this->now() - latest_centroid_.header.stamp;
  // if (age > rclcpp::Duration::from_seconds(1.0)) { ... }
  object_depth = latest_centroid_.point.z;   // no lock
}

The braces are left over from the lock_guard that was removed along with the commented‑out staleness guard. latest_centroid_ is a 40‑byte struct written by the callback under centroid_mutex_. This is a data race on the single value that decides SELECTING → EXECUTING — whether the arm closes on the object.

ORIENTATION.md §8.8 records the missing staleness guard. It does not record that removing it also removed the lock.
C6Blocks

Reference cycle — neither destructor ever runs

grasp_state_machine.cpp:759 holds shared_ptr<MtcPlanner> · mtc_planner.hpp:37 holds Node::SharedPtr to the same node

A shared_ptr cycle. The refcount never reaches zero, so ~GraspStateMachine never runs (shutdown_ never set, worker thread never joined) and ~MtcPlanner never runs (mtc_executor_->cancel() never called, spin thread never joined). main() returns from rclcpp::spin() with two threads still live.

node_ is only used for logging — a WeakPtr, or just the logger, breaks the cycle.

C7Blocksobserved

Unbounded queue growth after a successful grasp

grasp_state_machine.cpp:704‑716 returns out of workerLoop without reaching publishState(IDLE) at :721

state_ stays EXECUTING forever, so graspCallback keeps pushing into candidate_queue_, which nothing drains any more. The node also handles exactly one object per launch, despite the while (true) structure.

Reproduced 2026‑09‑11 — bench/state_machine_sim.sh ran a full grasp on the simulated arm: home, approach, grip, carry. It then stayed in EXECUTING and never announced IDLE again, exactly as predicted.

E

Frames and coordinates

E1Blocksobserved

goto_glasses treats a robot‑relative pose as a map coordinate

goto_glasses.py:170‑184 and :198‑217

Both read glasses_pose.pose.position.x/y directly and stamp the result frame_id = "map". There is no TF lookup, and msg.header.frame_id is never read.

/aria/fused_pose is stamped "robot_base_link". So a position expressed relative to the moving base is used as an absolute map coordinate — and the error changes every time the base moves.

ORIENTATION.md §6.4 flags the frame mismatch. What it does not say is that the consumer never looks at the frame at all, so nothing would ever catch it.
Reproduced 2026‑09‑14 — bench/nav_nodes.sh. Fed a robot_base_link‑stamped fused pose, the node produced a goal at (1.00, 0.60) in map. The wearer's actual map position was (2.40, 2.00). The robot would drive 2.0 m to the wrong place, and the error changes with every base movement.
E5Blocks

Two nodes race for Nav2 on the same spoken word

goto_glasses.py:59‑61, 67, 88‑100 · launched unconditionally by slam_localization.launch.py:156‑159

goto_glasses.py is not the return‑leg‑only node its name suggests. Its own docstring says it handles "all user‑directed navigation", and it has two paths that both send goals through the single navigate_to_pose action client created at :67:

PathTriggerFrame handling
Outbound/aria/audio/prompt, or /goto_glasses/triggerthe E1 defect, stamps "map" at :174 with no TF lookup
Return/manipulator/return_to_userthe E1 defect, stamps "map" at :204

object_approach_node.py runs the forward leg and is structurally independent — no topic of one feeds the other. The coupling is the shared action server, not a topic. Both nodes react to /aria/audio/prompt, so one spoken object name can make goto_glasses fire an E1‑corrupted goal at the moment the forward leg needs Nav2 for its approach.

This changes a scoping decision. PROJECT_PLAN.md §4.2 puts the return leg out of scope, which was taken to make E1 droppable. It does not: E1's outbound half is on the path we do use, and the launch file for normal operation starts this node every time. F2 below is genuinely return‑leg only.

Checked repo‑wide in the same pass: the E1 pattern, stamping frame_id = "map" on values that never went through a TF lookup, exists in exactly two places, both in this file. object_approach_node.py:232 looks identical but is correct, because its values come from a real lookup_transform first.

G1Runtime

The SAM mask has no timestamp relationship to the frame it masks

anygrasp_detection_node.py:74‑75, 125‑126, 195

# Latest mask cache — decoupled from RGB/depth sync
def mask_callback(self, msg):
    self.latest_mask = msg        # no timestamp check, ever
...
combined_mask = depth_mask & sam_mask

RGB and depth are synchronised to within 50 ms. The mask is then combined from whatever arrived most recently — arbitrarily stale, from a camera on a moving wrist. The comment presents this as a design choice; the effect is masking the current frame with an older frame's segmentation. There is also no shape check before &.

L

The feature exists but the wiring stops short

Not a broken line of code. A connection that was never made, so a whole capability is inert.

L1Runtime

Voice cannot change what the arm looks for — the target word is fixed in the source

sam3_ros_node.py:40 — TEXT_PROMPT = "box" · the file has exactly one create_subscription, at :52, and it is for CameraInfo

The segmentation node the arm actually uses never subscribes to /aria/audio/prompt. RGB and depth reach it through two message_filters subscribers feeding a synchroniser, so that one CameraInfo subscription really is the only one. The target word is a module‑level constant handed straight to process_text_prompt at :114, and the file's own docstring says so: "Runs SAM3 inference with a fixed text prompt".

The topic itself is live and correctly wired everywhere else. It is published by the Aria audio pipeline, named in shared/config.yaml:14, and subscribed by the object‑recognition pipeline and both navigation nodes. The one consumer that feeds the arm is the one that does not listen.

Ask for a bottle and the base will drive to it, while the arm keeps hunting for a box — and nothing reports that the request was dropped. The whole voice chain, microphone through transcription through the LLM object extractor, ends at the navigation nodes and at a segmentation call site that is commented out.

It compounds with A3: with USE_SIMPLE_EXECUTE = true, even a live prompt would only steer the visual servo. It would not select a grasp. B3 is this same missing subscription seen from the safety side, where it means the spoken kill word cannot reach the arm.

The two ways to fix this, and the open decision between them, are NEXT_STEPS.md §2.2 and PROJECT_PLAN.md T2.0. Read ORIENTATION.md §6.5 first: simply uncommenting the pipeline's call site while this node runs leaves two publishers racing on the same three topics.

?

Open questions

These are decisions, not fixes. Several of them change what the right fix is.

  1. A3 — was USE_SIMPLE_EXECUTE = true a deliberate bring‑up shortcut, or did someone forget to flip it back? It changes what "the grasp pipeline" even means right now.
  2. B4 — who changed HOME_JOINTS, and against what? If nobody knows, the first hardware run should use the realman_manip values, since those are the ones the safety doc describes.
  3. A1 — is the inverted gate a typo, or was there a reason to run detection during IDLE (pre‑computing candidates before the approach)? If the latter, A2 is the bug instead.
  4. D1 — what was meant to publish /manipulator/release? Voice — the LLM returns the word, not a Bool — a button, or the visualiser? The orchestrator has no other way to finish.
  5. I1 — which launcher owns background.launch.py? Removing it from one of the two is a two‑line fix, but only once the ownership is decided.
  6. E1/E2 — should /aria/fused_pose be in map or robot_base_link? The publisher's variable names say map, its stamp says robot_base_link, and its only consumer assumes map. Two of those three have to change.
