## What this session settles about the stop

`[observed]` **There is no dedicated emergency stop button, and no separate controller box.** The
only physical control is a power button at the rear of the arm. Checked by Dion and Sherman at the
robot on 2026-09-23.

`[observed]` **There is no teach pendant.** Checked the same day.

This answers T1.4's D3 row, and it changes T1.7:

- **The stop is cutting power**, by the rear button or by the plug. It does not depend on ROS, the
  network, the driver, or which terminal has focus, which is why it stays the primary stop.
- `arm/estop/estop.py` remains the software stop and runs in its own terminal, but it is a second
  line, not the first. It only works if the driver is running, the network is up and the terminal
  has focus. Its own confirmation proves the message was delivered, not that the arm stopped.
- **Without a pendant, T1.7 cannot hand-jog the arm.** The first commanded motion has to go through
  `/rm_driver/movej_cmd` at a low speed value, with a hand on the power button for the whole move.
  That path bypasses MoveIt, so it does no planning and no collision checking. The pose must be
  correct before it is sent. This makes T1.3's screening a precondition, not a convenience.
- Repository `CLAUDE.md` forbids publishing to `/rm_driver/*_cmd` on the real domain. T1.7 is the
  one sanctioned exception, with two people present.

## Step 5: network and controller `[observed]` PASS

`ip -4 addr show enp2s0`: link `UP,LOWER_UP`, carrying `192.168.1.100/24` as primary plus
`192.168.1.10/24` and `192.168.1.5/24` as secondaries. All three addresses present as T0.2 left them.

**The arm was unreachable on the first attempt, then reachable about a minute later.** The first
`ping -I 192.168.1.10 192.168.1.18` returned `Destination Host Unreachable` from `192.168.1.100`,
which is the local machine reporting that ARP never resolved. Nothing was answering at `.18` yet.

`ip neigh show dev enp2s0` then showed the arm had appeared:

```
192.168.1.18 lladdr 00:00:3e:9e:9f:a0 REACHABLE
```

`[observed]` **The arm's MAC address is `00:00:3e:9e:9f:a0`.** Recorded here for the first time. It
pins which physical device this evidence refers to.

`[inferred]` The arm was still booting during the first attempt. This is consistent with the
archived guide's note that port 8080 can take about 60 seconds after power-on
(`../archive/RCP_NEW_USER_STARTUP_GUIDE.md` §3.3). **Practical consequence: a failed ping in the
first minute after power-on is not a fault.** Wait and retry before investigating.

On retry, both checks passed:

```
3 packets transmitted, 3 received, 0% packet loss
rtt min/avg/max/mdev = 0.403/0.407/0.411/0.003 ms
Connection to 192.168.1.18 8080 port [tcp/http-alt] succeeded!
```

Round trip 0.4 ms with no loss and no jitter to speak of. The control port accepted a connection.

## Step 6: driver handshake

Launched alone, in its own terminal:

```
ros2 launch rm_driver rm_65_driver.launch.py
```

`[observed]` PASS. The driver came up and completed its handshake:

```
[rm_driver] RM_65_driver is running
[rm_driver] product_version = RM65-BI
[rm_driver] controller version : 3
[rm_driver] UDP_Configuration is cycle:5ms,port:8089,force_coordinate:0,
            ip:192.168.1.10,hand:0,rm_plus_base:0,rm_plus_state:0,speed:1
```

Three things this settles:

- **`product_version = RM65-BI` is now `[observed]`.** It was `[reported]` from the 2026-08-25
  guide until this session. The arm is the model the code assumes.
- **Controller version 3**, recorded here for the first time.
- **The UDP configuration matches the config file exactly**: cycle 5 ms, port 8089, reporting to
  `192.168.1.10` (`arm/vendor/rm_driver/config/rm_65_config.yaml:10-12`). The driver is talking to
  the address the workstation actually holds, which is the thing most likely to be wrong and is not.

`[observed]` The software stop was up first and reported every key, including the `S` that
Sherman's runbook omits:

```
[estop]: E-stop ready.  E=emergency  R=resume  S=soft stop  Q=quit  Ctrl+C=emergency and quit
```

This is the straight-up posture, every joint within about 1 degree of zero. It is the first direct
reading taken by the task owner rather than reported secondhand.

**It corroborates Sherman's T1.3 rest readings.** His figures from 2026-09-22 were
`[0.0143, 0.0006, 0.0107, 0.0014, 0.0014, 0.0016]`. Largest disagreement is joint1 at 0.0025 rad,

arm between the two sessions, and both readings describe the same physical posture.

**Why this matters for T1.3.** The tightest joint-limit margin in this posture is joint5 at 2.232
rad, which is 127.9 degrees of room. Compare the two candidate home rows: Row A leaves 37.9 degrees
at its tightest, and the realman_manip row leaves 1.6 degrees at joint4, which is what broke the
grasp approach. The resting posture is therefore a legitimate third candidate on margin grounds,
and the only open question against it is containment, which needs Sherman's T1.4 numbers.

### One finding to carry forward

only. Nothing in the current grasp path is known to read them, so this is recorded rather than
raised, but anything added later that expects joint velocity or torque from `/joint_states` will
get nothing.

## Feedback for Sherman's runbook

Reviewed against the code on 2026-09-23. Everything factual in it checked out: the driver-only
launch, the `.18:8080` and `.10:8089` addresses, the six joint names, what `arm_env.sh` does, and
the warning that `arm_bringup.launch.py` also starts control and MoveIt. Three points for him:

1. **It requires two people and never defines the physical stop.** Both are correct requirements.
   This session answers the second: there is no button, the stop is cutting power.
2. **The stop program has a key the runbook omits.** `S` sends a soft stop, current motion only
   (`../../arm/estop/estop.py:109`). The runbook lists `E`, `R`, `Q` and `Ctrl+C`. For the one
   document whose subject is the stop, list every key.
3. **Add the boot wait as a step, not a footnote.** A failed ping in the first minute after
   power-on is normal, and this session would have been misdiagnosed without knowing that.
