## What this session settles about the stop

`[observed]` **There is no dedicated emergency stop button, and no separate controller box.** The
only physical control is a power button at the rear of the arm. Checked by Dion and Sherman at the
robot on 2026-09-23.

`[observed]` **There is no teach pendant.** Checked the same day.

This answers T1.4's D3 row, and it changes T1.7:

- **The stop is cutting power**, by the rear button or by the plug. It does not depend on ROS, the
  network, the driver, or which terminal has focus, which is why it stays the primary stop.
- `arm/estop/estop.py` remains the software stop and runs in its own terminal, but it is a second
  line, not the first. It only works if the driver is running, the network is up and the terminal
  has focus. Its own confirmation proves the message was delivered, not that the arm stopped.
- **Without a pendant, T1.7 cannot hand-jog the arm.** The first commanded motion has to go through
  `/rm_driver/movej_cmd` at a low speed value, with a hand on the power button for the whole move.
  That path bypasses MoveIt, so it does no planning and no collision checking. The pose must be
  correct before it is sent. This makes T1.3's screening a precondition, not a convenience.
- Repository `CLAUDE.md` forbids publishing to `/rm_driver/*_cmd` on the real domain. T1.7 is the
  one sanctioned exception, with two people present.

## Step 5: network and controller `[observed]` PASS

`ip -4 addr show enp2s0`: link `UP,LOWER_UP`, carrying `192.168.1.100/24` as primary plus
`192.168.1.10/24` and `192.168.1.5/24` as secondaries. All three addresses present as T0.2 left them.

**The arm was unreachable on the first attempt, then reachable about a minute later.** The first
`ping -I 192.168.1.10 192.168.1.18` returned `Destination Host Unreachable` from `192.168.1.100`,
which is the local machine reporting that ARP never resolved. Nothing was answering at `.18` yet.

`ip neigh show dev enp2s0` then showed the arm had appeared:

```
192.168.1.18 lladdr 00:00:3e:9e:9f:a0 REACHABLE
```

`[observed]` **The arm's MAC address is `00:00:3e:9e:9f:a0`.** Recorded here for the first time. It
pins which physical device this evidence refers to.

`[inferred]` The arm was still booting during the first attempt. This is consistent with the
archived guide's note that port 8080 can take about 60 seconds after power-on
(`../archive/RCP_NEW_USER_STARTUP_GUIDE.md` §3.3). **Practical consequence: a failed ping in the
first minute after power-on is not a fault.** Wait and retry before investigating.

On retry, both checks passed:

```
3 packets transmitted, 3 received, 0% packet loss
rtt min/avg/max/mdev = 0.403/0.407/0.411/0.003 ms
Connection to 192.168.1.18 8080 port [tcp/http-alt] succeeded!
```

Round trip 0.4 ms with no loss and no jitter to speak of. The control port accepted a connection.

## Cold start: the validated procedure

Follow this from nothing. Every expected output below was observed on 2026-09-23, so a deviation is
a real difference, not an unknown. Two people. Nothing here moves the arm.

### Before power

1. **Hardware free?** Read-only, changes nothing:
   ```bash
   ps -eo pid,user,etime,args | grep -iE 'rm_driver|arm_bringup|grasp_state_machine|start_grasp_pipeline|grasp_orchestrator|Runner.Worker|bench/run.sh'
   ```
   Expect only your own `grep`. If somebody else owns a process, stop and ask them. Never kill it.

2. **Stop agreed.** The stop is the power button at the rear of the arm. There is no e-stop button
   and no controller box. Name who holds it. They stay within reach for the whole session.

### Power on and wait

3. Power on the arm. **Wait a minute before judging anything.** The arm is unreachable for roughly
   the first minute while it boots. A failed ping in that window is normal.

### Environment, in every terminal

```bash
source ~/rcp-Gappler/arm/arm_env.sh
export ROS_DOMAIN_ID=91
export ROS_LOCALHOST_ONLY=1
```

Domain 91 because the bench defaults to 77, so the two cannot collide. If `arm_env.sh` says there
is no `install/`, run `./build.sh` first. `ros2 node list` should show nothing before you start.

### Terminal 1: the stop, first, then leave it alone

```bash
python3 ~/rcp-Gappler/arm/estop/estop.py
```

Expect exactly:
```
[estop]: E-stop ready.  E=emergency  R=resume  S=soft stop  Q=quit  Ctrl+C=emergency and quit
```

Nobody types in this terminal unless something is wrong. **`Q` quits without stopping.** The power
button is still the primary stop, because this program only works if the driver is running, the
network is up and this terminal has focus.

### Check the network

```bash
ip -4 addr show enp2s0                    # expect .100, .10 and .5, link UP
ping -I 192.168.1.10 -c 3 192.168.1.18    # expect 0% loss, about 0.4 ms
nc -zv -w 3 192.168.1.18 8080             # expect "succeeded!"
```

If ping says `Destination Host Unreachable` **from your own address**, ARP has not resolved and
nothing is answering at `.18`. Check `ip neigh show dev enp2s0` for
`192.168.1.18 lladdr 00:00:3e:9e:9f:a0`. If it is absent, the arm is off, unplugged, or still
booting. That MAC is this specific arm.

### Terminal 2: the driver, alone

```bash
ros2 launch rm_driver rm_65_driver.launch.py
```

**Not `arm_bringup.launch.py`. Not any launcher.** Those start the state machine, which homes the
arm within seconds without asking.

Expect:
```
[rm_driver] RM_65_driver is running
[rm_driver] product_version = RM65-BI
[rm_driver] controller version : 3
[rm_driver] UDP_Configuration is cycle:5ms,port:8089,...,ip:192.168.1.10,...
```

A different `product_version`, or a UDP ip that is not `192.168.1.10`, means stop and work out why.

### Terminal 3: confirm feedback

```bash
ros2 topic echo /joint_states --once
ros2 topic hz -w 10 /joint_states
```

Expect `joint1` to `joint6` with six finite positions, and about **200 Hz with min equal to max at
0.005 s**. That is the driver's declared 5 ms cycle. A rate well off 200, or visible jitter, means
the feedback loop is degraded even though the handshake succeeded.

At rest the arm reads every joint within about 1 degree of zero. `Ctrl+C` in **this** terminal ends
the rate display.

### Shut down, in this order

1. `Ctrl+C` in the **driver** terminal. Confirm with `pgrep -af rm_driver`, expect nothing.
2. Agree the arm's power state with the person at the robot.
3. Close the **stop terminal last**.

Never `pkill`. Never stop a process you did not start. `Ctrl+C` in the driver terminal is driver
teardown, not an arm stop.

## Next session: running the simulator

**The driver must be fully shut down first.** `bench/sim_moveit.sh:33-34` refuses to start if any
`rm_driver` process exists anywhere on the machine, regardless of ROS domain. That is deliberate: a
simulated arm and a live driver on one machine is how a command reaches real hardware by accident.

```bash
pgrep -af rm_driver      # must return nothing
./bench/sim_moveit.sh
```

It plans and executes three poses on a mock arm whose joints exist only in memory: the home row in
the code, the realman_manip row, and `zero`, which is effectively the resting posture measured in
this session (`../../bench/nodes/test_sim_moveit.py:24-26`).

**Known limitation, and the reason this cannot close T1.3 yet.** The script reports whether each
pose is reachable and collision-free *in the model*. It does not report where the arm ends up, and
the model contains no mast, no table and no lab. Reachable is not tucked. Judging containment needs
two things that do not exist yet: a position readout added to the sim, and Sherman's T1.4 footprint
numbers to compare against.
