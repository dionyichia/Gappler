# T1.7: first commanded motion

**Purpose:** move the real arm for the first time, to the HOME pose decided in T1.3, and record
the joint values it actually reaches. Dion and Sherman at the robot, 2026-09-23.

**Scope for this session:** HOME only. RETURN is not sent (Dion, 2026-09-23). It stays open under
T1.7 for a later session.

**Builds on:** [`T1.6_FIRST_POWERED_SESSION.md`](T1.6_FIRST_POWERED_SESSION.md) for the stop,
the boot wait, the environment and the shutdown order.

---

## Decisions for this session

- **One joint at a time.** HOME differs from the straight-up rest posture in three joints: j3, j5
  and j6. Each step moves one of them. A wrong sign or wrong unit then shows as one small, obvious
  move, not three joints at once.
- **Speed 1**, the lowest value the driver accepts. `speed` goes straight to the arm SDK as a
  percentage `[code]` `arm/vendor/rm_driver/src/rm_driver.cpp:151`. At 1% a 90 degree move should
  take tens of seconds `[inferred]`, slow but visible. If the arm looks stalled, stop, then retry
  at 2.
- **`block: false`.** With `block: true` the driver sits inside `rm_movej` until the motion ends
  `[code]` `rm_driver.cpp:155`. If the driver handles one message at a time, the software stop
  would wait behind the move `[inferred]`. `false` keeps the driver free to take the stop.
- **Joint values are radians.** The driver converts to degrees itself `[code]` `rm_driver.cpp:145`.
- **Every step starts only if the arm reads where the previous step left it.** Each command sends
  all six joints, so any joint that is not where we assume will move too.

## Attempts

### Attempt 0, 2026-09-23: nothing sent

The full HOME pose was published at speed 5 from a shell on the box. `ros2 topic pub` printed
`Waiting for at least 1 matching subscription(s)...` until Ctrl+C. No driver was listening on that
shell's ROS channel, so the message never left and the arm did not move `[observed]`. Most likely
cause: the driver was not running, or the shell had not set `ROS_DOMAIN_ID=91` `[inferred]`. The
procedure now checks for the driver before any command.

### Attempt 1, 2026-09-23: stopped before any command, driver unhealthy

Nothing was sent. Two faults, both before step 0 `[observed]`:

1. **The driver did not set up joint feedback.** After `product_version = RM65-BI` and
   `controller version : 3`, it printed `set_realtime_push revice error` and
   `The set_realtime_push error code is -2`, where T1.6 printed the `UDP_Configuration is ...` line.
   That call tells the arm to stream joint states to the workstation
   (`arm/vendor/rm_driver/src/rm_driver.cpp:807`). It failed, so no `/joint_states` is expected.
   -2 means the arm did not answer the request `[inferred]` from the SDK's "receive error" text.
2. **Terminal 3 saw no driver topics.** `Unknown topic '/rm_driver/movej_cmd'` and no
   `/joint_states`. The `source` line in that terminal also had a typo (`arm_env.shsh`) `[observed]`.
   Either the driver was on another ROS channel or it had exited `[inferred]`.

Rule added: no command is sent unless the driver printed the `UDP_Configuration` line and
`/joint_states` runs at about 200 Hz, as in T1.6.

### Attempt 2, 2026-09-23: HOME reached, PASS

**Result:** the real arm reaches the T1.3 HOME pose. Every joint landed within 0.0004 rad (0.02°) of
its commanded value, each move was slow and smooth, and the driver accepted all three commands
`[observed]`. The joint readings are committed in
[`../bench-runs/2026-09-23-labbox-t1.7-home-joint-states.txt`](../bench-runs/2026-09-23-labbox-t1.7-home-joint-states.txt).
The original files stay on the box in `~/rcp-Gappler/docs/dion_docs/t1.7_logs/`.

The results logger in Terminal 3 exited on its own before the final `kill %1` (exit 15). The last
`data: true` was still read from its file, so nothing was lost.

## What this settles

- **HOME stays as it is in `mtc_planner.hpp`.** The reached values differ from the commanded ones
  by at most 0.0004 rad, which is settling noise, not a pose error. Copying them in would change
  nothing physical and would break the bench tests that compare against the same row
  (`bench/nodes/test_state_machine_sim.py:41`, `bench/nodes/test_sim_moveit.py:33`). The header
  now carries a comment saying the row is validated on the real arm.
- **HOME extends slightly outside the base.** T1.3 placed the tool 0.43 m in front of the arm's
  base (`docs/sherman_docs/T1.3_HOME_POSE.md`). At the robot the tool extends slightly past the
  base footprint. Dion judged this acceptable for HOME, because HOME is the pose the arm takes when
  navigation has arrived and it looks at the table, not a pose for driving.
- **Correction for Sherman's T1.4 doc.** `sherman_docs/T1.4_PHYSICAL_SETUP.md` ("Parked vs working
  envelopes") says home should be a tucked posture inside the footprint. The HOME row does not meet
  that `[observed]`. The tucked pose is now its own task, T1.18, a `navigation_rest_pose` inside the
  base. Not edited there, since it is Sherman's folder.
- **Follow-up tasks added to the task tree:** T1.18 (find `navigation_rest_pose` inside the base)
  and T1.19 (rename HOME to a name that says what it is).
- **Still open under T1.7:** the RETURN pose on the real arm. Camera view angle at HOME not
  recorded this session.
