Section 1The short version

If you read nothing else on this page, read this.

The goal is a robot you can talk to: you wear smart glasses, look at an object, say "grab that box", and a mobile robot drives over, picks it up and brings it back to you.

Most of the individual pieces work. What is missing is the wiring between them. Right now the system behaves like two separate machines that happen to sit in the same room:

Machine A — listening Hears youThe glasses' microphones, speech recognition and a small language model all work. Your spoken words come out the other end correctly.
Machine B — grasping Grabs thingsThe camera, the segmentation model, the grasp planner and the arm all work, and the arm can pick something up.
The problem They don't talkMachine B never receives the word Machine A heard. It looks for a fixed, hardcoded object instead: the word "box".

So today the robot can hear you well enough to drive somewhere, but not well enough to know what to pick up. There are five specific places where the wiring is cut or crossed — Section 6 walks through each one with the exact line of code responsible.

These are not bugs anyone forgot about

Four of the five are lines someone deliberately commented out, most likely so the arm could be tested on its own without depending on the glasses. That was a sensible thing to do. But it means you cannot just uncomment them and expect it to work — and break 5 explains a case where doing exactly that makes things worse.

Section 2What the system is meant to do

The full intended sequence, in order, in plain terms.

#StepHow it is done
1You speak. "Grab that yellow box." Seven microphones in the glasses record continuously.
2Speech becomes text. Whisper, a speech-recognition model, transcribes it.
3Text becomes one object name. → "box" Qwen2.5, a small language model, pulls the object out of the sentence. It also recognises "stop" and friends as a kill word.
4Both cameras look for a "box". SAM 3, a segmentation model, outlines every matching object it can see — once in the glasses' camera, once in the camera on the arm.
5Your eyes settle the ambiguity. If three boxes are visible, the eye tracker says which one you were looking at.
6The two cameras confirm they agree. LightGlue matches visual features between the two views, checking that both cameras are looking at the same physical object and not two similar ones.
7The outline becomes a position in space. The depth camera turns the 2D outline into a 3D point the robot can drive toward.
8The base drives within reach. Nav2 (the standard robot navigation stack) plans a path using a laser map and stops 0.6 m from the object.
9The arm approaches and grasps. The arm creeps toward the object in 4 cm steps until it is 18 cm away, then AnyGrasp proposes where to put the fingers, and the gripper closes.
10The robot returns to you. It finds the glasses' position and drives back.
11You say "release". The gripper opens.

Steps 1–3 work. Step 4 works but uses the wrong word. Steps 5, 6 and 10 are disconnected. Steps 8 and 9 work in isolation but have never been run as one sequence. Step 11 has a listener, but nothing in the repo sends the "release" message code. The One grasp, start to finish tab walks through all of this step by step.

Section 3How the parts talk to each other

One idea, and it explains the whole structure of this codebase.

Everything here is built on ROS 2. ROS 2 is not a program you run — it is a message system. Picture a set of named radio channels. Any program can broadcast on a channel, and any other program can tune in.

TermWhat it means
TopicA named channel, like /aria/audio/prompt. Data flows one way. Any number of programs can broadcast or listen.
NodeAny running program that broadcasts or listens. One Python script can contain several.
Message typeThe shape of the data on a channel — a string, an image, a position.
TFA always-running service that tracks where every physical part is relative to every other part. "Where is the camera lens relative to the robot's base?" is a TF question. It is how a pixel in an image becomes a place the arm can reach.
Launch fileA recipe that starts several nodes at once with the right settings. Files ending .launch.py.

Why this matters for reading the code: the five parts of this system are connected only by channel name. No part imports code from another part. That has two consequences you will feel immediately:

  • Good: you can replace one part entirely — say, swapping in a different navigation system — without touching the others, as long as it broadcasts and listens on the same channels.
  • Awkward: half the system can be broken while the other half runs perfectly, and nothing reports an error. A channel with nobody broadcasting on it is not a crash. It is just silence. That is exactly the situation today.
One setting worth knowing early: BEST_EFFORT vs RELIABLE

Each channel declares how hard it should try to deliver. RELIABLE means retry until it arrives. BEST_EFFORT means drop it rather than wait. Video uses BEST_EFFORT, because an old frame is worse than no frame.

Get this wrong and the two sides simply never connect — with no error message. This repo contains an entire node whose only job is to bridge that mismatch, because the laser scanner broadcasts RELIABLE and the thing consuming it demands BEST_EFFORT. qos_relay.py

Why part B lives in its own separate environment

The grasp planner (AnyGrasp) ships as a pre-compiled binary built against an old version of PyTorch. That version cannot coexist with the one the segmentation model needs. So B runs in a completely separate Python environment and talks to everything else only over ROS channels.

Practical rule: never make part B import code from the rest of the project. It will break. This is also why some channels carry Python "pickle" data that only part A can read — those are for visual debugging, and B must never subscribe to them.

Roughly 95% of the files are not yours

Three folders are third-party code copied into the repo wholesale, and you should treat them as sealed boxes: Navigation_Module/OpenVINS/ (about 3.4 million lines of motion-tracking code), grasp_module/, and deps_ws/. Add every rm_* folder except rm_mtc — those are the arm manufacturer's. What is genuinely ours: src/, rm_mtc/, robot_slam/, and four loose scripts.

Section 4b · project conventionName things descriptively

Five subsystems here each have a "base", a "camera", a "pose" and a "main". Unqualified names are not just untidy in this project — they cause real bugs.

The rule for all new code, channels, frames, files and documentation

A name must say which subsystem it belongs to, without the reader needing context.

The cautionary example is a real one in this repo code — two nearly identical names for two different physical objects about half a metre apart:

Name in the codeWhat it actually refers toWould be clearer as
base_linkthe arm's root — the point the arm measures all its own movements fromarm_base_link
robot_base_linkthe wheelbase's root — the point navigation measures frommobile_base_link

Anyone reading "base" has to already know which subsystem they are in. And the connection between the two is published in only one of the two navigation launch files (Section 8), so getting them confused produces a calculation that fails silently rather than erroring.

The same problem in other forms

  • Three files named main.py, plus orchestrator.py — four entry points, and no name tells you which is which. Section 4
  • "camera" could mean the glasses' main camera, their eye-tracking camera, their two navigation cameras, or the one on the arm's wrist. The channel prefixes are what disambiguate: /aria/… is the glasses, /camera/… is the wrist camera.
  • /object_centroid vs /object_centroid_2d — differ by a suffix, and the _2d one is not even an ordinary point (its third value is a distance in metres, not a coordinate).

Every collision we found, ranked by risk code

#Names that collideWhat each actually is
1base_link / robot_base_link arm root / wheelbase root
2camera_link, camera_color_optical_frame, camera_rgb The wrist camera's mount, the wrist camera's lens, and the glasses' camera — three unrelated things all called "camera"
3/manipulation/… vs /manipulator/… The same arm↔navigation contract, split across two prefixes that differ by one character. Three channels use one, two use the other, with no rule telling you which

8rm_65_config / rm_65_w_gripper_config Arm without / with the gripper. Ours all use the gripper version, but the manufacturer's launch files use the plain one — so copying a launch snippet gives you an arm with no gripper
Two of these have already caused real defects

A test tool broadcasting into the void. The same constant name is defined in five files. Four say the real channel; one says an old placeholder name dummy_mask_publisher.py:14. That file's own comment tells you to "match these to the placeholders" in another file — but that file's value is not a placeholder, it is the real one. So the tool for testing the arm without the glasses sends its messages nowhere.

A comment describing the wrong machine. One file documents a measurement as being taken "from base_link centre" goto_glasses.py:35 — the arm's reference point, used to describe the wheelbase's own geometry, inside the navigation code. Another file describes the identical measurement correctly object_approach_node.py:51. One of the two is simply wrong, and the near-identical names are why.

One more, found by the same audit

The glasses' marker-sighting messages are stamped with a reference frame called camera_rgb image_streaming_pipeline.py:60. That name appears exactly once in the whole repository — nothing defines it and nothing publishes it. Any position calculation against it fails. It is hidden right now only because break 1 means those messages are never sent at all.

Applying it

Prefix channels with the subsystem. Name reference frames after the physical thing and its subsystem. Never name a file, program or constant something a reader could reasonably attribute to a different part of the system. Write "the wheelbase's root frame" in prose, not "the base frame".

When renaming something that already exists

Grep for every occurrence of the string first. Channel and frame names are matched as plain text at runtime, not checked when the code is compiled — so a rename that misses one place fails silently while the robot is running, which is the worst time to find out.

Section 5Before you run anything

Two things that will cost you a broken arm or a wasted day.

⚠ The arm moves on its own, seconds after launch, with no command

The state machine calls its "go to home position" routine before it waits for any input at all — within a couple of seconds of starting. grasp_state_machine.cpp:594-595 code And the retry loop keeps trying forever until it succeeds. :342

As of 25 August 2026 the arm had never been commanded to move at all. Nothing about arm motion in this repo has been tested on hardware. reported

Rules: clear the space around the arm first; run the emergency-stop script estop.py in its own terminal before anything else; and never start grasp_state_machine or ros2_robot_ws/src/main.py unless somebody is physically standing next to the robot.

⚠ Worse: the arm can start moving because a message arrived

The coordinator itself is safe at startup — it only launches the arm driver and the motion planner, which plan but do not move. orchestrator.py:78

But it then sits waiting on the channel /manipulation/start. The moment any message appears there, it launches the robot side, which starts the state machine, which moves the arm.

So a stray test command, a leftover navigation node, or a replayed recording can set the arm in motion. There is no point in that sequence where a human confirms anything. Treat a running coordinator as a loaded arm.

The navigation module depends on a package that is not in this repo

Both navigation launch files try to include a launch file from a package called xpkg_demo. That package is nowhere in this repository, though it is listed as a dependency. robot_slam/package.xml:12 code

Because of how ROS classifies that dependency, compiling will probably succeed and launching will fail. inferred it is the wheelbase's own startup code. Find out where it came from before booking time with the robot.

Section 6 · the important oneWhere the system is disconnected

Five specific places. Each one below gives the plain-English problem, the exact code responsible so you can check it, and what it means in practice.

First, the picture

The five breaks

Break 1 code

The glasses barely broadcast anything

Six things should start up when the glasses app runs. Four of them are commented out. Only the audio path survives.

Evidence

src/main.py:106-112

Effect

No camera images, no eye tracking, no motion sensors, no marker detection, and no debug window. Only the spoken-word channel works.

This knocks out more than it looks. The glasses' position is worked out from a printed marker they see through the camera — no camera images means no position, which means the robot can never find you to come back.

Clue

Line 110 fetches the camera calibration data from a queue, but the only two things that use it are among the commented-out lines. It is fetched and thrown away — which suggests these lines were switched off quickly, not designed out.

Break 2 code · the headline problem

The object you asked for never reaches the robot

One line of code would send the chosen object's outline and position to the arm. It is commented out. A second, simpler program does that job instead — using a fixed word typed into the source.

Evidence

The good version, switched off object_recognition_pipeline.py:384

# self._publish_mask_and_centroid(inference_state, depth, header, ros_image)

The stand-in that runs instead sam3_ros_node.py:40

TEXT_PROMPT = "box"   # no voice input, no eye tracking
Effect

The arm grasps whatever matches the literal word "box". Everything upstream — speech recognition, the language model, eye tracking, the two-camera cross-check — is computed correctly and then discarded.

The method that is not being called is complete and looks correct. It is simply never invoked.

Fixing it

Do not just uncomment line 384. Read break 5 first — that creates a second, subtler problem which will make your fix look broken for reasons that have nothing to do with this break.

Break 3 code

The "bring it back to me" sequence is not wired up

The coordinator's own comments describe a six-step sequence. Steps 3 and 4 — the ones that handle the return trip — are commented out.

Evidence

orchestrator.py:57-62, and the handlers at :69-102

3. Wait for goal_reached          4. Launch rm_bringup   ← both off

What remains: start the arm driver, wait for a go signal, launch the robot side, wait to hear "release", open the gripper. The navigate-back-to-the-user leg is absent.

Small to restore — two subscriptions — but it depends on break 1 and break 4, since the robot needs to know where you are.

Break 4 code · a different kind of problem

One component's documentation describes something the code does not do

There is a file that is supposed to combine two sources of position data into one accurate estimate of where you are standing. Its README describes that clearly. The code does roughly half of it, and reports its answer in the wrong coordinate frame.

Break 5 code · nothing is switched off here

Two programs claim the same three channels

This one is different: no code is commented out. Two separate programs are each set up to broadcast on the same three channels. Only one does today — because the other one's line is the very line from break 2.

Uncomment line 384 while the stand-in is still running and you get two programs broadcasting on the same channels at once. The state machine will act on whichever message happens to arrive last — so behaviour becomes a race, changing run to run for no visible reason.

Section 8The handover points

Seven channels carry the whole conversation between seeing, driving and grasping. If you are replacing a part, this is the contract you must honour.

Everything else in Section 7 is internal to one part. These seven are the seams between them — marked ★ in that table. The full sequence, in order:

#WhoSays what
1Perception → Navigation"The object is at this position" /manipulation/goal_pose
2Navigation (internal)Works out where to stop, drives there /goal_pose → /goal_reached
3Navigation → Coordinator"In position, go ahead" /manipulation/start
4Coordinator → ArmStarts the grasp sequence
5Arm → Navigation"Got it, take me back" /manipulator/return_to_user
6Navigation → Coordinator"We're back" /return_to_user/goal_reached
7You → Coordinator"Release" /manipulator/release
Two similarly named reference frames, and mixing them up is a classic bug

base_link is the arm's base. robot_base_link is the wheelbase's. Everything the arm plans happens in the first; everything navigation plans happens relative to the room map.

The connection between them is published in only one of the two navigation launch files slam_localization.launch.py:98-103 code — the arm sits 0.18 m forward, 0.48 m up, and rotated 180°, facing backwards. The map-building launch file does not publish it at all, so during map-building the arm is not connected to the position tree and any calculation involving it fails silently.

Section 9HiCo-Nav integration

The planned next phase: replacing the navigation system with the one from the HiCo-Nav paper.

⚠ Open blocker: the required camera does not exist on this robot

HiCo-Nav's memory graph needs a continuous forward-facing colour-plus-depth camera. This robot has exactly one camera and it is bolted to the arm's wrist — it points wherever the arm points, and it moves during a grasp. The navigation system is laser-only; there are no camera channels in it anywhere. code

Three ways forward, none free: buy a base-mounted camera (about $400, plus university ordering time); park the arm in a fixed observation pose and accept the compromise; or substitute the laser scan and adapt the method. This is the decision that costs weeks if it turns out wrong — settle it first.

The first question to answer from the paper

Does HiCo-Nav produce destinations or wheel speeds? The answer decides how big this job is:

  • Destinations — it sits alongside the existing code and Nav2 stays as it is. Small change.
  • Wheel speeds — it replaces the component that steers the robot, and inherits all the map and reference-frame plumbing. Much larger change.

What a replacement would displace

RoleCurrently
Route plannerNavfnPlanner, 0.5 m tolerance, unknown space treated as passable
Steering controllerRegulatedPurePursuitController — 0.2 m/s, 0.6 m look-ahead, reversing disabled
Obstacle map (local)3D voxel layer plus a safety margin, relative to wheel odometry
Obstacle map (global)Saved map plus safety margin, relative to the room
Robot shapeA circle of radius 0.2 m — no detailed outline is configured

Nothing in the segmentation, grasp-planning or arm channels should be touched by a navigation change. That separation is what makes it possible to integrate navigation while the grasping half is still half-working.

Scope this before building anything

HiCo-Nav records every object it sees into a memory graph. If that graph becomes the answer to "where is the thing I was asked for", then three things change at once: where the camera image comes from, when segmentation is triggered, and possibly whether perception produces the object's position at all — or whether it is read out of the graph.

That could take over three of the seven handover channels. Read the paper against Section 8 and decide which ones, before investing in the segmentation work in Section 11.

Section 10Traps

Things that are true, non-obvious, and will waste your time if you meet them unprepared.

Hidden assumptions

AssumptionWhy it matters
Eye tracking assumes everything is 1.5 m away eye_tracking.py:150 code The eye tracker gives a direction, never a distance. To turn that into a point on the screen the code projects it onto an imaginary wall at a fixed 1.5 m. For anything nearer or further, the reported gaze point drifts off target — and that point is what decides which object you meant.
The wrist camera's reference frames are not defined in this repo code They come from a third-party package that is not included here. Every grasp calculation depends on them, so if that package is missing or the camera driver is not running, grasp attempts are skipped silently rather than erroring.
The arm does not check whether its target is stale grasp_state_machine.cpp:637-641 code The freshness check is commented out, so the arm will keep creeping toward a target position that stopped updating.
The clever grasp planning is compiled but not used grasp_state_machine.cpp:40 code A simplification flag is switched on, so the arm does a blind 10 cm push toward the object and closes the gripper. AnyGrasp's suggestions are received and ignored in this mode. Worth knowing before anyone spends a day debugging AnyGrasp's output.
Startup timing is handled by guessing ros2_robot_ws/src/main.py code Components are started with fixed waits — 2 s, 3 s, 5 s — because the state machine needs the motion planner to be ready. On a slower machine the guess is wrong and you get confusing failures.
Three programs can send driving commands code The wheelbase driver is the real one. The docking system also sends a slow creep when a test mode is on. And a third, unfinished driver exists whose speed conversion is an explicit placeholder — it is not started by anything, and must not be run alongside the real one.

Traps that cost a previous session real time reported

  • Never set PYTHONNOUSERSITE=1. There are two versions of PyTorch installed. The one that works with the graphics card is in the user folder; the one in the grasp planner's environment has no graphics support at all. That setting forces the broken one. Do not "tidy up" the user folder either — the system depends on it winning.
  • A depth filter silently emptied the point cloud. The grasp planner was set to ignore anything beyond 0.5 m while the workbench sat at 1.45 m — so every point was discarded and the program crashed rather than complaining. It looked like a successful start followed by an instant crash.
  • Launch every terminal with the environment script. The grasp planner is started in a way that inherits its search paths from the terminal. Start it from an unprepared terminal and that one component dies on startup while everything else looks fine.
  • Child programs dying is reported as a warning, not an error. The launcher keeps running. A dead grasp planner presents as "nothing ever happens". Read the terminal output.
  • The arm's controller takes about 60 seconds after power-on before it accepts connections. "Connection refused" immediately after switching on is normal.
  • The workstation's network address is not arbitrary. The arm is told to send its status to one specific address. Set it wrong and everything connects but no data arrives — which presents as a hang, not an error.

Dead code that will mislead you

Not bugs, but each one looks meaningful and is not: a feature-matching program that is wired up but never actually started (the class inside it is used, directly); a calibration-logging function that is never called and writes to a stray file; several leftover print("Success")-style debug lines; an on-screen menu that lists five of six available views; and a test tool for the arm that broadcasts on an old channel name nothing listens to any more, so it no longer works as a stand-in.

Do not build the two-stage version yet

If HiCo-Nav's memory graph already tracks every object it has seen, that graph is probably the right trigger and a purpose-built cheap model would be wasted work. Settle the scoping question in Section 9 first.

Then: make segmentation one service

Resolve break 5 by deciding which program owns the model. The target: one service that holds the model, accepts a word and a camera to look through, and is the only broadcaster of the outline and position channels. Both current programs become users of it. Because the code is already shared, this is a reorganisation rather than a rewrite.

Sequence it after the two decisions above — both change what this service's interface should look like, and doing it twice is wasted effort.

One grasp, start to finish

The ideal run, from top to bottom: you ask for a cup, and the robot fetches it. Each step shows what happens in the room, which program runs, what method it uses, what message it sends, and whether that step works today.

The short answer: what feeds what in the grasp

The grasp controller is the part that decides. It sits before MoveIt, not after it. MoveIt only plans the path for each move the controller asks for.

Always running in the background

These streams run continuously once the programs are up. The steps below use them. The other messages are one-off: sent once, when a step happens.

    Uses

    Sends

    Method
