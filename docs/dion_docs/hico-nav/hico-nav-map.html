Section 1The short version

Six sentences, then the detail.

HiCo-Nav lets you talk to a robot in ordinary language and have it go find the thing you meant, in a building it has never seen. You say "I want to host a dinner party on a summer evening, where should I set the table?" and it works out that it is looking for a table, explores until it finds one, and drives there. It does this with no training on that building and no training at all — it is zero-shot, built out of off-the-shelf models wired together well.

The interesting engineering is in how it is wired. Thinking hard is slow; driving without hitting things has to be fast. Most systems make the fast part stop and wait while the slow part thinks. HiCo-Nav refuses to do that: it runs three loops at three different speeds at the same time, and they talk to each other only by reading and writing a shared memory — a growing collection of camera snapshots and the objects visible in them. Nothing ever waits for anything.

The four things you should take away

Answer 2 · goals or speedsSpeeds — but take goals The paper drives the wheels directly. We should take only the layer above that. Section 7
Answer 3 · how much it swallowsLess than feared Its memory can tell us which table. It cannot replace close-range grasp perception. Section 7

Bonus answer · registrationA cascade, not every frame Cheap detection on all 10 fps; expensive segmentation on ~1 frame per 1–2 s. Answers our own §2.1. Section 5
One genuine piece of luck

The paper's real robot uses a Livox MID-360 LiDAR and a RealSense camera. code This robot already has a MID-360, mounted rigidly on the base. Half the sensor suite already matches. What is missing is a camera in the right place — not a camera of an unusual kind.

Section 2What it actually does

The task, start to finish, in plain terms.

Two words worth learning

Zero-shot means no training. Point it at a building it has never entered, give it a phrase it has never been shown, and it works. Nothing here needs a dataset, an annotation budget, or a fine-tuning run. paper

Frontier means the edge of what the robot has mapped so far — the boundary between "I have seen this" and "I have not". Exploring means repeatedly choosing which frontier to go stand at next. Most of Section 6 is about choosing well.

Section 3The three layers

Three loops at three speeds, never waiting on each other.

The problem the paper is solving: a robot has to react to a chair leg in milliseconds, but understanding "where should I set the table" takes a large model a second or more. Bolt those together and you get a bad choice — think often and drive badly, or drive well and miss the target.

HiCo-Nav's answer is to stop connecting them directly. Each layer runs on its own thread at its own rate, and the only thing they share is the memory graph. The reasoning layer deposits conclusions there whenever it reaches them; the driving layer reads them whenever it next needs to decide. Neither ever blocks.

Why "proactive" is the important word

In competing systems, the fast module decides when to wake the slow one, then sits and waits for an answer. HiCo-Nav's reasoning layer is never woken and never asked. It walks the memory on its own schedule, continuously, and leaves its findings behind. paper

Section 5Memory, and how objects get into it

The most portable idea in the paper, the one that needs the camera — and the cascade that decides when the expensive model runs.

Most comparable systems build a scene graph — a tidy symbolic structure that says "chair is near table, table is in kitchen". HiCo-Nav argues that is the wrong substrate, for a blunt reason: a vision-language model reads pictures, not symbol tables. Every conversion into symbols throws away information the model could have used.

So the memory is built out of the photographs themselves. It has exactly two kinds of thing in it, and one kind of link:

So how are objects registered — does it run segmentation on every frame?

No, and this is the part most worth copying. The obvious guess — run the expensive segmentation model on every frame, or every other frame — is not what happens. The pipeline is a cascade: a cheap detector looks at everything, and the expensive segmenter only ever sees the frames a free test has already judged worth keeping.

StageWhat runsOn whatRate
1 · PoseFAST-LIVO2, mapped into the camera frameevery framesensor rate
2 · DetectYOLO-World — open-vocabulary boxesevery frame10 fps
3 · DecideThe keyframe test — two thresholds, no model at allevery frame10 fps
4 · RegisterMobileSAM mask → depth to 3D → CLIP feature → mergekeyframes only~1 per 1–2 s

Only at stage 4 does an object actually enter the memory. The mask is cut, depth and the camera pose lift it into a 3D shape, a CLIP feature records what it looks like, and then the merge test decides whether this is a new object or the fourth time the robot has seen the same chair.

The merge test — "have I seen this before?"

Two independent measures have to agree before a sighting is folded into an existing object: do the 3D shapes overlap, and do they look like the same kind of thing. Both are needed, because each fails alone — overlap alone merges a book with the table it rests on, and appearance alone merges the four identical chairs around that table into one. Fail the combined test and a new object node is created instead.

This is where the camera requirement becomes unavoidable

Every stage from 2 onward needs the camera, and stage 4's output is the memory. There is no version of this that runs on LiDAR alone: with no images there are no snapshots, with no snapshots there is nothing for the language model to read, and Layer 3 has no input at all. The camera is not a quality improvement — it is the substrate.

This answers an open question in our own work register

NEXT_STEPS.md §2.1 asks when SAM 3 should run — it currently runs on every synchronised RGB+depth pair, against a hardcoded prompt. That item lists a "two-stage" option but marks it inferred, noting it would need "a second model and an 'interesting' criterion". The paper is that design, and it supplies the criterion: escalate when a new object class appears, or when the robot has moved or turned enough since last time.

Two things make the case stronger here than in the paper. inferred First, the paper escalates to MobileSAM — a deliberately lightweight model — whereas we would be escalating to SAM 3 at 3.4 GB, so we save proportionally more. Second, §2.1's "graph-driven" and "event-driven" options turn out to be the same option: the keyframe test is the event. There is one policy to build, not two.

It is also the cheapest item in this entire document to try — a distance threshold, a rotation threshold, and a set-difference on class names. It needs no camera purchase and does not wait on anything else.

One caution that comes with it

A cascade lowers the update rate by design. ORIENTATION.md §8.8 records that the consumer-side staleness guard in grasp_state_machine.cpp:637-641 is commented out — so the state machine will happily drive toward a target position that stopped updating. That missing guard becomes more dangerous under a cascade, not less. Restore it alongside, not afterwards.

How the model reads it

The whole graph will not fit in a language model's context window, so it is cut into chunks and streamed. The order is not arbitrary. At the very start of the task, the model is asked once to expand the instruction into two lists:

"where should I set the table?"
  → targets  = { table }              seeing one of these completes the task
  → related  = { chair, plate, dining room }  these hint where the target is

Chunks containing targets go first, then chunks containing related objects, then everything else ordered by how well its contents match the instruction. That single up-front call is then reused for the entire run — including by the exploration scorer in the next section, which is how the system gets language-model-quality judgement into a loop that runs hundreds of times a second without paying for it.

Section 6Choosing where to go

Scoring the doorways, then putting them in the right order. This is the part with the largest measured effect.

Step one — score each frontier

Two independent sources of evidence, added together. Most published systems use only one of them; the paper's own ablation shows they are complementary rather than redundant.

Step two — put them in order, not just pick the best

Here is the paper's sharpest observation. Almost every comparable system is greedy: score the frontiers, go to the highest one, rescore, repeat. That produces the oscillating, doubling-back behaviour anyone who has watched an exploring robot will recognise.

But a full tour of every frontier is wrong too, because the robot stops the moment it finds the thing. Visiting all of them is never required. So the quantity to minimise is not distance travelled — it is how long you expect to wait before you find it.

Two refinements worth noting

  • Cost is measured in seconds, not metres. A candidate directly behind the robot is expensive because turning takes time. The cost model uses the robot's actual maximum linear and angular speeds. paper
  • Small enclosed pockets get priority. A little unexplored alcove is cheap to resolve now and a recurring nuisance if left — the robot will keep coming back to it. The paper raycasts to detect that case and pulls those candidates forward.
This ordering is the single biggest contributor in the paper's ablation

Replacing it with greedy selection costs 2.4 points of success rate — more than either camera-derived scoring signal. It is also the only major component that needs no camera at all, which makes it the obvious thing to build while a camera is on order. Section 10

Section 7What it would replace here

The paper is a whole navigation stack. We already have one. These are separable — that is the useful insight.

The temptation is to treat this as all-or-nothing: either adopt HiCo-Nav or do not. But its contributions sit at four different heights in the stack, and they can be taken independently. Three of the four are additive — they occupy space that is currently empty.

Does the memory graph swallow our object-finding?

inferred Partly, and the boundary is clear enough to state. The memory graph knows every object it has ever seen, where it roughly is, and what it looks like. That is exactly what is needed to answer "drive me to the thing I asked for". It is not enough to grasp it — its object shapes come from a fast segmentation at navigation distance, and the grasp planner needs a clean close-range mask.

the likely division of labour

  memory graph  ─────►  "the mug is on that table over there"   coarse, from memory
                          │
                          ▼  drive there, arrive
                          │
  live SAM 3 + AnyGrasp ─►  "grip it here, at this angle"       fine, from live frames

This is close to the split already described in ORIENTATION.md §5. The graph changes where the goal pose comes from; it does not touch the grasp pipeline. That is a smaller change than NEXT_STEPS.md §1.3 was braced for.

One thing we already have that the paper needed to build

code HiCo-Nav's real-world experiments were voice commanded. The Aria glasses on this project already run Whisper and publish /aria/audio/prompt, and the navigation code already listens to it. Tier B's input side is essentially free.

Section 8Blockers, and the one purchase to raise now

Ordered by lead time, longest first. This section is the reason the document exists.

Blocker 1🔴 weeks · procurement

A forward-facing colour-plus-depth camera. Confirmed, and load-bearing.

The existing documentation guessed this and marked it as needing confirmation. It is confirmed, and the requirement is stronger than assumed: the camera images are not input to the memory, they are the memory.

Three uses

1 · The snapshots the language model reads. 2 · Depth, which gives every object a 3D position. 3 · Seeing past the edge of the map, worth 1.3 points of success rate on its own.

What we have

code One RealSense D435i, bolted to the arm's wrist. The navigation workspace has no image topic in it at all.

Option 1 · buy

Recommended. Buy a D455, not another D435i — the D455 is what the paper deployed, and its wider field of view and longer depth range suit looking at doorways, where the D435i's roughly 2 m usable range is marginal. Mount it rigidly, forward-facing, on the base.

Option 2 · park the arm

Worse than the docs assumed. The paper's own small-object success rate falls to 65 % because of vibration blur — and that is with a rigidly mounted camera. A camera at the end of a 6-DoF arm will be worse. It also ties every snapshot's position to joint-state timing, and it makes the arm unavailable for grasping while exploring. Usable as a stopgap during the wait; not the answer.

Option 3 · LiDAR only

Gives up Tier B entirely. No image means no snapshot, no snapshot means nothing for the language model to read. What survives is a geometry-only explorer, which discards the entire reason to adopt this paper.

Also start now

inferred The mount design. It has to clear the arm's swept volume and not stare at the robot's own shell. The arm is mounted yawed 180°, which complicates this. Weeks of lead time, and it can run in parallel with the purchase.

Blocker 2🔴 days–weeks · not in the existing docs

Where do camera poses come from?

The paper uses FAST-LIVO2, a LiDAR-inertial-visual odometry system. We use 2D slam_toolbox. Every position in the memory graph inherits this choice.

Why it matters

If poses drift, the same table seen twice becomes two objects, and the graph degrades steadily over a run. The failure is gradual and easy to misdiagnose.

Three paths

Adopt FAST-LIVO2 — closest to the paper, but needs time-synchronised LiDAR + camera + IMU. open Whether the MID-360's built-in IMU is even published in this workspace is unchecked.

Derive poses from slam_toolbox + the transform tree — cheapest. 2D SLAM gives no reliable pitch or roll, so snapshots inherit that error. inferred Probably fine on a wheeled base on a flat lab floor.

Use OpenVINS — already vendored in this repository, but visual-inertial without the LiDAR term, so it does not solve camera–LiDAR registration for free.

Recommendation

Start cheap, then measure. Pose quality is directly observable as duplicate object nodes in the graph, so this is a decision that can be made from evidence rather than in advance.

Blocker 3🟠 days · only after the camera arrives

Calibrating the camera against the LiDAR

The paper names calibrated LiDAR–camera extrinsics as a prerequisite. There is no such calibration here, because there has never been a base-mounted camera to calibrate.

Plainly

The two sensors have to agree on where things are. Without that, an object detected in the image lands in the wrong place on the map — and every downstream position is wrong by the same amount.

Effort

A well-understood but fiddly workshop task. Budget days, not hours. It sits directly behind Blocker 1 on the critical path, which is another reason the purchase is the urgent item.

Blocker 4🟠 days + a policy check

Where does the vision-language model run?

The paper's robot called a cloud API (Qwen3-Omni). It also reports an offline variant (Qwen3-VL-8B) running locally.

Cloud

Needs reliable network from a moving robot, an API key, and a per-call budget. It also sends lab imagery off-site — worth checking against department policy before it becomes the default by accident.

Local

inferred Roughly 8–16 GB of VRAM depending on quantisation, on a 16 GB card that already hosts SAM 3 (3.4 GB), YOLO-World, MobileSAM and CLIP. This is a real contention problem, not a rounding error. Quantisation or a smaller model is likely required.

Read the speed table carefully

The paper's timing numbers come from an RTX 5090. The only embedded-hardware claim is qualitative. Nothing in the paper predicts throughput on our card, and the local-model path in particular should be expected to be slower here. The asynchronous design makes that survivable — a slower reasoning layer degrades decision quality rather than stalling the robot — but it is worth stating rather than discovering.

Blocker 5🟡 hours–days · check before writing Tier A

Two solvers, one of which has a licence worth reading

Graph pruning needs an integer-programming solver; the frontier ordering needs a travelling-salesman solver.

The ILP

Open options exist (CBC, HiGHS, OR-Tools). Low risk — but this project already carries one machine-locked commercial licence in AnyGrasp, and a second would be unwelcome.

The tour solver

The paper names LKH. LKH is free for academic use but is not open source and not redistributable. inferred OR-Tools' routing solver should substitute fine at the problem sizes involved. Worth settling before Tier A is written, because Tier A is this solver.

Section 9How well it works

The published numbers, and how much of them to believe for our case.

Two measures are used throughout. SR (success rate) is the share of tasks completed. SPL weights each success by how close the route was to the shortest possible one — it penalises wandering. Both are percentages, higher is better.

BenchmarkInstruction difficultyHiCo-Nav SR / SPLBest rivalMargin
ObjectNav · MP3Da bare category name48.5 / 21.545.4 / 17.2+3.1
ObjectNav · HM3Da bare category name61.0 / 31.859.6 / 33.0+1.4 SR, −1.2 SPL
Open-vocabulary · HM3D-OVONarbitrary object names52.4 / 20.740.8 / 12.1+11.6
Text-instance · TextNava paragraph describing one specific object27.8 / 12.920.2 / 11.4+7.6

Read the shape, not the absolute numbers. The margin is small when the instruction is one word and large when it is a sentence. That is the signature of a system whose advantage comes from understanding rather than from searching faster — which is exactly the advantage this project needs, since our instructions come from a person speaking naturally.

The comparison that matters is against SG-Nav and UniGoal. They achieve the same reasoning quality by calling a large model at every single step — and pay 10 to 25 times over in task time. The asynchronous design is what buys deep reasoning at shallow-system speed.

These numbers are from an RTX 5090

Not from the Jetson the real robot carried, and not from our card. The paper's only embedded-platform claim is qualitative, with two concrete figures: detection at 10 frames per second, and one memory snapshot kept every 1–2 seconds. No honest throughput estimate for our hardware can be derived from the table above.

The real-world number we should pay most attention to

On an actual quadruped, over 40 voice-commanded trials: 95 % success on large objects, 65 % on small ones. The gap is attributed to the robot's motion blurring the images. Our targets — mugs, boxes, tabletop items — are firmly in the small-object regime, and our base is wheeled and therefore smoother than a walking quadruped. But this is the number that should set expectations, not the 61 % simulator figure.

Testing it in a simulator

upstream The public HiCo-Nav code is the Habitat simulator setup that produced the paper's benchmark numbers: Python 3.9, one script per benchmark, and no ROS. inferred That matters because our test bench checks nodes with fake inputs, which works for message bugs but not for a search. Where HiCo-Nav goes next depends on what it has already seen, so testing it needs a world that changes as the robot moves.

Two simulators answer two questions. Habitat, with upstream's own scripts, checks that our port still scores like the paper. A robot simulator (Gazebo or Isaac Sim) checks the whole chain through Nav2 on our base. code The base already has a Gazebo model that drives on /cmd_vel, but it has no LiDAR or camera. Details, costs and a suggested code split in PAPER_REPORT.md §5.6.

No integration plan. No node decomposition, no topic names, no launch structure, no decision about which of the existing contract topics the memory graph takes over.
