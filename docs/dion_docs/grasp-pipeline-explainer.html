How the Arm Grasps

What happens between the wrist camera seeing a box and the gripper closing on it, which parts are broken, and which choices are still open. Written to learn from, not to look up.

In one line: the wrist camera finds the box, the arm creeps toward it 4 cm at a time until it is 18 cm away, then makes one last move and closes the gripper. A smarter grasp planner, AnyGrasp, is wired in but switched off.

The picture

Six programs pass messages to each other. Solid lines are what runs today. Dashed lines are wired but ignored while the simple path is switched on.

SAM 3 also sends AnyGrasp the box's outline (the mask). The messages are ROS 2 topics. Their exact names are in docs/CHANNEL_CONTRACT.md §3, rows H5 to H8.

The six programs

All are started by one launcher, launchers/start_grasp_pipeline.py, in this order. Never run it on the real arm. It homes the arm within seconds.

One grasp, step by step

The state machine is a loop with three named states. It announces its state on a topic so other programs know what it is doing.

IDLE→ SELECTING→ EXECUTING→ IDLE
  1. start-up

    Wait 2 seconds, add virtual walls so MoveIt will not plan through them, then move to the home pose, a fixed set of six joint angles.

    grasp_state_machine.cpp:593-596, pose in mtc_planner.hpp:46

  2. IDLE

    Wait until SAM 3 reports a box. Then go home again, so every attempt starts from the same place.

    :613-623

  3. SELECTING

    Look at where the box sits in the image. Work out which way to move so it ends up in the right spot, and move the gripper 4 cm that way. The target spot is 55 pixels right of the image centre, most likely because the camera sits beside the gripper, not in it.

    Repeat until the box is closer than 18 cm. Give up after 50 steps.

    :627-653, one step is selectingStep() at :367

  4. EXECUTING

    Open the gripper. Then finish the grasp. There are two ways to do this, and a switch in the code picks one. See the next section.

    :664-671, the switch is USE_SIMPLE_EXECUTE at :41

  5. after the grasp

    Move to a return pose holding the object, and announce it. On the simple path the loop then stops for good. One grasp per start-up.

    :711-719

The fork: two ways to finish

This is the part behind the open question. The switch USE_SIMPLE_EXECUTE is set to true, so today the arm takes the left path.

Simple path on today

One more straight move of 10 cm toward the box, keeping the gripper at the same height and the same angle. Then close.

  • Needs only the camera and SAM 3
  • Few moving parts, easy to watch and debug
  • The gripper never turns. It only suits objects that can be held from the angle the home pose leaves it at, like a box
  • Does not use AnyGrasp at all

Code: :671-719

AnyGrasp path off

Wait for AnyGrasp's grip proposals. Keep the best one until it stays put for 5 frames in a row (within 15 mm and 10°). Then move the gripper to exactly that position and angle, and close.

  • Can grip awkward shapes, because the gripper turns to suit the object
  • About 150 lines that have never run
  • Blocked by three bugs, below
  • Needs the AnyGrasp program, its licence and a working Python setup

Code: executingStep() at :459

Why the AnyGrasp path cannot work yet

Three bugs block it, and each one hides the next. The audit calls them A1 to A3.

BugWhat goes wrongWhere
A1, gate upside downAnyGrasp should work only while the state machine is EXECUTING. The check is written backwards, so it works only while the state machine is IDLE, the one time nobody wants proposals. Judged a typo on 2026-09-20, and seen on real frames on 22 Sep: 154 proposal sets while IDLE, none while EXECUTING (T0.12)anygrasp_detection_node.py:182
A2, only listens in one stateThe state machine throws away proposals unless it is EXECUTING. That part is correct. It only looked wrong next to A1grasp_state_machine.cpp:183
A3, the switchUSE_SIMPLE_EXECUTE = true skips the whole AnyGrasp path, so A1 never shows up as a failuregrasp_state_machine.cpp:41

A way to picture it. The simple path is reaching for a box on a shelf with your wrist locked: walk up, stretch out, squeeze. The AnyGrasp path is looking at the object first, deciding where your fingers should go and turning your hand to match. The second is better, but the first is how you check that your arm, eyes and hand work at all.

The decisions

Some are settled, some are open. You do not have to settle the open ones today. Each card says what you would need to know first.

Does M1 grasp with the simple path or with AnyGrasp?

open
Why it matters
M1 is "the arm picks something up". On the simple path, AnyGrasp never runs, so M1 could pass without it. The plan today still makes the first hardware grasp (T1.11) wait for the AnyGrasp fixes (T1.8, T1.10).
Options
A. Bring up on the simple path first, then add a task to switch AnyGrasp on after the first grasps work. The AnyGrasp fixes come off the critical path.
B. Fix AnyGrasp first and do the first grasps with it, as the plan says now.
Leaning
A. It changes one thing at a time, which is the point of bring-up. Decided on 2026-09-20: the switch stays true for bring-up (CHANNEL_CONTRACT §6 B-1). The plan's dependencies just never caught up.
To decide, know
Whether the paper needs AnyGrasp grasps, or only a working grasp. And how much time is left before M1 (1 Nov).

T1.8, T1.10, T1.11, stretch goal S1

How does a grasp end?

decided, not built
Why it matters
After a grasp, the gripper stays closed until a "release" message arrives. Nothing sends that message today, and nothing sends "done" either. For the five grasp attempts in T1.12, someone would have to send it by hand each time.
Decided
The state machine sends /manipulation/done when a cycle ends. The glasses side sends /manipulator/release when you say "release" (CHANNEL_CONTRACT §6 A-1, B-5).
Gap
No task owns building either one. A small task or two is needed.

Which AnyGrasp program is the real one?

open
Why it matters
There are two. The detection program looks at each frame fresh, and the launcher starts this one. The tracking program follows grips across frames, and it is the one the only working session on 2026-08-25 used. Their gates differ too: detection's is upside down (A1), tracking's is commented out, so it runs all the time.

State of affairs

  • works

    The state machine runs on the simulated arm, and the bench checks it (bench/state_machine_sim.sh).

  • works

    The e-stop program sends its stop on Ctrl+C, kill and a closed terminal (T1.2, part done).

  • works

    The AnyGrasp Python setup rebuilds from a script and its demo passes (T1.10, half done).

  • works

    The wrist camera, replugged on 22 Sep. A 10 s recording replays through SAM 3 and AnyGrasp (bench/anygrasp_replay.sh, T0.12). SAM 3 finds the box on real frames.

  • broken

    The AnyGrasp path: the three bugs above (T1.8).

  • broken

    Thread safety: two locks share one wake-up signal, and the box position is read without its lock. This is undefined behaviour, not just untidy code (T1.9).

  • broken

    The launcher promises an e-stop key it does not have, and the arm driver starts twice (T1.2).

  • broken

    On the simple path, two position conversions can crash the node if a transform is missing (:680, :700).

  • untested

    Any grasp on the real arm. The home pose on the real arm. The prompt word is fixed to "box", so voice cannot change the target yet.

Words you will meet

Topic
A named channel one program writes to and others read from. Programs never call each other directly.
Mask
An image the same size as the camera's, marking which pixels belong to the object.
Centroid
The centre point of the mask. Here it is sent as pixel column, pixel row and depth in metres.
Depth image
An image where each pixel holds a distance instead of a colour.
Pose
A position plus an angle. "Where the gripper is and which way it points."
Frame, TF
A coordinate system. The camera, the gripper and the arm's base each have one. TF is the ROS tool that converts a point from one frame to another.
Cartesian step
A straight-line move of the gripper, as opposed to letting each joint swing freely.
MoveIt
The motion planner. You give it a target pose, it works out joint angles and a collision-free path.
Grasp candidate
One proposal from AnyGrasp: a gripper pose, a width and a quality score.
State machine
A program that is always in exactly one named state and moves between them on events.

How to learn this, hands on

  1. Read workerLoop() in grasp_state_machine.cpp, lines 590 to 745, with this page open beside it. It is the whole story above in about 150 lines.

  2. On the lab box, run ./bench/state_machine_sim.sh. It starts the state machine against a simulated arm on a private channel, so nothing real moves. Watch it print IDLE, SELECTING and EXECUTING.

  3. Change one constant in a scratch branch, for example the 4 cm step at :32, rebuild with ./build.sh, and see the simulated arm take bigger steps.

  4. Then pick the open decision above. By then the options should read differently.
