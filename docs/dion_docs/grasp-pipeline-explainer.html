How the Arm Grasps

A walk through one grasp, from the launch command to the gripper closing. Each stop names a file and the lines to open. Read it with the code beside it, top to bottom.

In one line: the wrist camera sees the object, SAM 3 says where it is in the image, and the state machine moves the gripper toward it 4 cm at a time. When the object is closer than 18 cm, it makes one last 10 cm move, closes the gripper and goes back to the home pose.

home pose checked on the real arm full grasp runs on the simulated arm gripper opens and closes on the real arm never grasped on the real arm

Three ideas first

You need these to read any of the code. The rest of the vocabulary is in Words you will meet at the bottom.

IdeaWhat it means here
Programs talk through topicsEach program (a ROS "node") runs on its own. It writes messages to named channels like /object_centroid_2d, and any program can read them. Nobody calls anybody directly. So to follow the flow, follow the topic names.
The state machine is the brainOne C++ program decides every arm move. It is always in one of three states, IDLE, SELECTING or EXECUTING, and loops through them.
Every point has a frame"10 cm forward" means nothing until you say forward from what. The camera, the gripper and the arm's base each have their own axes. A library called TF converts a point between them. The camera frame's z axis points straight out of the lens.

The picture

Solid lines run today. Grey dashed lines are wired but switched off. Red dashed lines are messages that something waits for but nothing sends yet.

The walkthrough

1

The launcher starts everything

Openlaunchers/start_camera_arm_sam3_grasp.pylines 85 to 159

This is a plain Python script. It does nothing clever. It starts the other programs one after another as separate processes, and stops them all on Ctrl+C (shutdown(), line 63).

  • :87-100

    Camera driver. Starts the RealSense driver with the wrist camera's serial number from shared/global_config.yaml. Two cameras are plugged into the box, so without the serial it could open the wrong one (T1.13).

  • :103-107

    Arm bring-up. Stop 2.

  • :110-121

    SAM 3. Stop 4. Runs in its own Python environment through uv.

  • :123-145

    AnyGrasp, commented out. Nothing reads its output while the simple path is on, so it would only take the GPU.

  • :148-152

    Viewers. A grasp viewer and RViz. They only draw. They change nothing.

  • :155-159

    State machine, last, after a 5 second wait so the others are up. Stop 5.

Never run this script on the real arm. The state machine moves the arm to home a few seconds after it starts, without asking. For the first real-arm runs, start each part by hand instead (T1.24, docs/dion_docs/GRASP_BRINGUP_STEPS.md step 3). The docstring at the top (lines 6 to 14) is out of date: it still says a stand-in mask publisher starts at step 2. The code starts SAM 3.

2

Arm bring-up: driver, model, MoveIt

Openarm/arm_bringup/launch/arm_bringup.launch.py

This launch file includes four others from the vendor code under arm/vendor/. You do not need to read inside them. Know what each one is for:

PartJob
rm_driverTalks to the arm over the network (192.168.1.18, port 8080). The only program that actually moves motors. It reads commands from topics like /rm_driver/movej_cmd
rm_descriptionLoads the arm's 3D model and publishes where every link is right now. This is what TF uses
rm_controlTurns a planned path into a stream of commands for the driver
move_groupMoveIt. Give it a goal, it plans a path that avoids collisions
3

Where the camera and gripper sit on the arm

Openarm/vendor/rm_description/urdf/rm_65_w_gripper.urdf.xacrolines 8 to 24

The model file says where things are bolted on. Two lines matter for grasping:

  • :15-18

    grasp_frame is a point 14.75 cm out from the last link (Link6), between the gripper fingers. When MoveIt is told "put the gripper here", this is the point it puts there.

  • :23-24

    The camera is also fixed to Link6, offset a few centimetres. Because both hang off the same link, TF always knows where the camera is relative to the gripper and the base, wherever the arm moves.

That is the whole trick behind the next stops. The camera sees the object in camera coordinates. TF turns that into arm-base coordinates. MoveIt plans in arm-base coordinates.

4

SAM 3 finds the object

Opengrasp/segmentation/sam3_ros_node.pywhole file, 200 lines

For every camera frame, SAM 3 looks for the prompt word and says which pixels belong to it. The output the arm uses is one point: the object's centre.

  • :28-37

    Topic names, read from the config files. Reads colour and depth, writes the mask and the centroid.

  • :43

    The prompt word, text_prompt: "box" in grasp/grasp_config.yaml:34. Fixed. Voice does not change it yet.

  • :106

    rgb_depth_callback runs once per frame pair. Everything below happens inside it.

  • :117-127

    Run the model, keep the best-scoring mask and its centre pixel.

  • :139

    Publish the mask on /camera/sam/mask. Only AnyGrasp would read it.

  • :150-158

    Depth: take every depth reading inside the mask, drop the zeros (pixels with no reading), use the median. Depth images store millimetres, so multiply by 0.001 for metres (depth_scale_m, shared/global_config.yaml:84).

  • :161-167

    Publish the centroid on /object_centroid_2d. This is the message the state machine uses.

164  pt.point.x = float(cx_px)  # pixel column
165  pt.point.y = float(cy_px)  # pixel row
166  pt.point.z = z             # depth in metres

Odd but true: x and y are pixels, z is metres, all in one message. Every reader of this topic has to know that.

The stand-in. grasp/tools/dummy_mask_publisher.py does the same job without the model, for testing (T1.16). It claims every pixel is the object, so it publishes the image centre (line 80) and the median depth of the whole frame (line 72). Merged into dev on 6 Oct. Put one object in front of the camera on a clear table when you use it.

5

The state machine wires itself up

Opengrasp/grasp_state_machine/src/grasp_state_machine.cpplines 92 to 224

From here on, line numbers without a file name are in this file.

  • :92-97

    create() builds the node, then starts workerLoop() on its own thread. So two things run at once: ROS delivers messages to the callbacks on one thread, and the worker loop moves the arm on another. They share data through variables guarded by locks (mutexes).

  • :123-136

    Reads the tuning values (stop 6) from ROS parameters. param() at 166 has no fallback: if a value is missing, the node stops at start-up rather than move the arm on a guess. That is why it must be started with grasp_state_machine.launch.py, which loads the config files.

  • :138-148

    Reads: camera calibration, AnyGrasp's grip poses, and the centroid.

  • :150-159

    Writes: two gripper commands (open, close), its current state on /pipeline_state, and /manipulator/return_to_user after a grasp.

  • :181-193

    Camera calibration arrives once. It gives fx, fy (focal length in pixels) and cx, cy (the image centre). Needed to turn pixels into metres in stop 9.

  • :206-212

    centroidCallback: store the newest centroid, set has_centroid_, wake the worker. Only the newest one is kept.

  • :217-224

    publishState: remember the state and announce it.

6

The tuning numbers

Opengrasp/grasp_config.yamllines 54 to 71

Every distance in the behaviour comes from here. Until T0.14 (6 Oct) these were constants at the top of the C++ file. Now they are a config file, so changing one needs no rebuild. The C++ keeps the old upper-case names for the variables they load into. The ones the simple path uses:

KeyValueMeaning
approach_step_m0.04 mEach SELECTING step moves the gripper 4 cm
approach_step_final_m0.10 mThe last move before closing is 10 cm
max_approach_steps50Give up approaching after 50 steps
execute_depth_thresh_m0.18 mCloser than this, stop creeping and grasp
centroid_target_offset_x_px55 pxAim to put the object 55 pixels right of the image centre, not at it. Most likely because the camera sits beside the gripper [inferred]
use_simple_executetrueWhich way to finish. True skips AnyGrasp. Kept true for bring-up (CHANNEL_CONTRACT B-1)

The others (angles, stability window, slerp) belong to the AnyGrasp path and do nothing today. The gripper's own numbers (open position, close speed and force) are not in this file yet. They are still written into openGripper() and closeGripper() in the C++ (stop 11).

7

Start-up: walls, then home

Openlines 604 to 610, then 302 to 365

The worker loop starts here. Read workerLoop() (604 to 756) as the spine of the program. Everything else is a helper it calls.

607  sleep 2 s
608  addSafetyWalls();
609  homeWithRetry();
610  publishState(State::IDLE);
  • :302-354

    Safety walls. Adds four invisible boxes to MoveIt's world: walls at the sides and front, and a table. MoveIt then refuses any path through them. They exist only in the planner. Nothing physical stops the arm.

  • :356-365

    Home, retried forever until it succeeds or the node shuts down. It calls moveToHome() in mtc_planner.cpp:71, which asks MoveIt to reach six joint angles at 10% speed.

The six angles are HOME_JOINTS in grasp/grasp_state_machine/include/grasp_state_machine/mtc_planner.hpp:51: 0°, 0°, 45°, 0°, 90°, 90°. Checked on the real arm on 23 Sep (T1.7), every joint within 0.02°. RETURN_JOINTS (line 63) is now the same pose.

8

IDLE: wait for the object

Openlines 622 to 638
IDLE→ SELECTING→ EXECUTING→ IDLE

The loop clears has_centroid_ and sleeps until centroidCallback (stop 5) wakes it with a new centroid. Then it goes home again, so every attempt starts from the same pose.

In practice SAM 3 publishes a centroid on almost every frame, so IDLE lasts a fraction of a second once an object is in view. That is also why one launch cannot simply loop: the next frame would start a new approach. T1.25 adds a gate, so a centroid only counts after an explicit "new target" request.

9

SELECTING: creep toward it

Openlines 641 to 675, then selectingStep() at 381 to 435

The loop at 644 runs up to 50 times. Each pass checks the depth first:

  • :657-663

    Object closer than 18 cm? Leave the loop and go to EXECUTING.

  • :664-668

    Otherwise take one step. If the step fails, give up and go back to IDLE (673).

One step, in selectingStep():

  • :386-397

    Ask where the gripper is now, and express it in the camera's frame.

  • :402-403

    How far is the object from where we want it in the image, in pixels?

  • :406-407

    Turn pixels into metres sideways. A pixel covers more ground the further away the object is, so multiply by depth and divide by focal length.

  • :408-415

    Add 4 cm forward (camera z). Then scale the whole move so its total length is exactly 4 cm.

  • :421

    Convert that goal into the arm base's frame.

  • :429

    Ask for a straight-line move there. Stop 10.

Worked example. Using the calibration the bench test uses (test_state_machine_sim.py:44): fx 607, cx 332. The object's centre is at pixel column 400, 30 cm away.

Target column332 + 55 = 387
Error400 − 387 = 13 px
Sideways, in metres13 ÷ 607 × 0.30 = 0.0064 m
Forward0.04 m
Length of that move√(0.0064² + 0.04²) = 0.0405 m
Scaled to 4 cm6.3 mm sideways, 39.5 mm forward

So most of each step goes forward, with a small sideways correction. Repeat until depth reads under 0.18 m.

10

One straight-line move

Opengrasp/grasp_state_machine/src/mtc_planner.cpplines 106 to 133

Every small move goes through moveCartesianStep. "Cartesian" means the gripper travels in a straight line, rather than each joint swinging to its new angle.

  • :108-110

    10% of top speed and acceleration. Start from where the arm is now.

  • :113

    MoveIt plans the line in 1 cm pieces.

  • :114-118

    If it can only plan less than 80% of the line, for example because a wall is in the way, refuse.

  • :122-128

    Add timing so the motion is smooth.

  • :132

    Send it to the arm and wait until it finishes.

Home and return use a different call, moveToHome() at line 71. That plans freely in joint space, so the gripper's path there is not a straight line.

11

EXECUTING: last move and close

Openlines 678 to 735
  • :678-683

    Announce EXECUTING. Copy the latest centroid so it cannot change mid-move. Open the gripper (openGripper() at 229: position 1000 is fully open, then wait 1.5 s).

  • :685

    The switch. use_simple_execute is true, so we take this branch.

  • :688-709

    Same maths as a SELECTING step, but 10 cm instead of 4.

  • :718

    Overwrite the goal's height with the current height. The gripper moves level and never dips toward the table.

  • :722-726

    Make the move. If it fails, the worker loop ends (return). The node stays running but does nothing more.

  • :727

    Close the gripper (closeGripper() at 239: speed 200, force 150, then wait 1.5 s). The close stops when the grip force passes the force value, out of 1000 (about 1.5 kg). Both gripper commands were checked on the real arm on 6 Oct, closing on air (T1.22). Closing on a box is next.

  • :729

    Go to the return pose. Since 5 Oct that is the home pose.

  • :732-734

    Announce /manipulator/return_to_user.

  • :735

    return again. The loop ends after one grasp, holding the object. Lines 752 to 754, which would go home and start over, are never reached on this path. T1.14 replaces this (see Decisions).

The other branch (737 to 746) is the AnyGrasp path. It waits for grip poses, picks one, waits until it holds still for 5 frames, then moves the gripper to exactly that pose and angle. It has never run. It is blocked by three bugs (T1.8) and switched on in T1.17. Skip it for now.

12

After the grasp, and what is missing

Opennav/object_approach/object_approach_node.py:88-91, :123-135launchers/grasp_orchestrator.py:69, :111-120

The arm now holds the object at home. Two messages are supposed to come next. Neither is sent by anything:

MessageWho waits for itWho should send it
/manipulation/doneNavigation (object_approach_node.py:88), to know the grasp is overThe state machine, after it opens the gripper on release. T1.14
/manipulator/releaseNavigation (:91) deletes its marker. The orchestrator (:69) opens the gripperThe glasses, when you say "release". T2.6

So today, after a grasp, the gripper stays closed until someone sends the release message by hand. And the only program that would open the gripper on release is the orchestrator, which we never run on the real arm. Decided 6 Oct: the state machine takes over that job (T1.14), and the glasses learn to send "release" and "new target" as two separate messages (T2.6).

Problems you will pass on the way

You will see these while reading. None of them stops a single simple grasp on a good day. Each has a task.

WhereWhat goes wrongTask
:206-212Any centroid starts a cycle. SAM 3 publishes one on every frame, so a loop back to IDLE would start a new approach at onceT1.25
:725, :735The worker loop ends after one grasp, or after one failed final move. Restart everything to try againT1.14
:694, :714Two frame conversions have no error handling. If TF is missing a link, the node crashes. The same calls in selectingStep() are guardedT1.9
:627-634, :654One wake-up signal shared by two different locks, and the depth read without its lock. In C++ this is undefined behaviour, not just untidyT1.9
:648-653The age check on the centroid is commented out. The arm acts on the last centroid even if it is oldT1.25
:197, grasp_config.yaml:66The AnyGrasp path: the producer and the consumer only work in opposite states, and the switch hides itT1.8

Decisions

One launch does more than one grasp

decided

Decided 6 Oct. After the return, the state machine waits for release, opens the gripper, publishes /manipulation/done and goes back to IDLE. That replaces the return at line 735 (T1.14). It needs the trigger gate first (T1.25), or the next camera frame would start a new approach while the gripper still holds the object. The first real grasps keep the one-shot return, so the arm cannot run twice by accident.

The state machine opens the gripper on "release"

decided

Decided 6 Oct. Today only the orchestrator does, and it shuts itself down right after. The state machine listens for /manipulator/release and calls its own openGripper(). It already owns both gripper commands, and it knows when a grasp has finished, so it can ignore a release that comes too early (T1.14). The glasses never send words to the state machine. They send "release" and "new target" as separate messages (T2.6, was T1.15).

Simple path first, AnyGrasp later

decided

Decided 23 Sep. The first real grasps (T1.11, T1.12) use the simple path. AnyGrasp is fixed (T1.8, T1.10) and switched on afterwards (T1.17), so only one thing changes at a time.

Return pose is the home pose

decided

Decided 5 Oct. Home is the only pose checked on the real arm. A real hand-to-user pose is future work, T1.20.

Watch it run, safely

On the lab box, ./bench/state_machine_sim.sh runs this exact program against a simulated arm on a private channel. Nothing real moves. It feeds fake centroids and checks each state in turn. The test that drives it is bench/nodes/test_state_machine_sim.py. Reading that test is a good second pass: it lists what the program should do, in order, as checks.

To see a tuning value matter, change approach_step_m in grasp/grasp_config.yaml on a scratch branch, rerun, and watch the simulated arm take bigger steps. No rebuild needed: the launch file reads the config from the repo.

Words you will meet

Node
One running program in ROS.
Topic
A named channel one program writes to and others read from.
Callback
A function ROS calls for you when a message arrives on a topic you read.
Mask
An image the same size as the camera's, marking which pixels belong to the object.
Centroid
The centre of the mask. Here: pixel column, pixel row, and depth in metres.
Depth image
An image where each pixel holds a distance in millimetres instead of a colour. Zero means no reading.
Intrinsics
The camera's calibration: focal length and image centre, in pixels. Used to turn pixels into metres.
Pose
A position plus a direction. Where the gripper is and which way it points.
Frame, TF
A coordinate system, and the tool that converts points between them.
Cartesian move
A straight-line move of the gripper.
MoveIt
The motion planner. Give it a goal, it finds joint angles and a path that avoids collisions.
Mutex, lock
A guard that stops two threads changing the same variable at once.
Grasp candidate
One proposal from AnyGrasp: a gripper pose, a width and a score.
